# Distributed task execution (`@vzn/vx-dte`), 2026-10

One run spread over agents that the user's own CI spawns. The agents
reach it through a relay that anyone can host. This page lists every
decision VZN has made. Each one is marked shipped or planned, and this
page changes in the same PR as the item it describes.

## Agents

- Shipped: an agent is described by the machine it reports (cores,
  memory). `max` and `adapter` are optional, and ids look like `small#1`.
- Shipped: the orchestrator runs no tasks by default (`local` is 0).
  `--parallel` affects only the orchestrator.
- Shipped: agents are spawned by the run's busy width over time, with no
  cap. That width is the work spread over the critical path, core-seconds
  over its length (`vx-dte/src/width.ts`, 2026-10-22: the level held for
  half the span let one long task starve the wide part).
- Shipped: no agent is asked for work that ends before it could join.
  Once an agent the run asked for has joined, the shortest such warm-up
  is what the next one takes at the least; while agents are online or
  starting, a demand whose remaining critical path is shorter starts
  none (`endsInMs`, `Orchestrator.warmUpMs`), and new agents are started
  for the width from that warm-up on (`busyCores`'s `fromMs`): a wide part
  that ends before they join is the joined agents'. Retiring needs no warm-up
  rule: idle agents are kept up to the peak of what is left, so none
  leaves to be replaced by a smaller one later.
- Shipped: an agent that never joins is marked `failed  <reason>`. When
  none can start, the run fails and says why.
- Shipped: an idle agent the rest of the run does not need gets `exit`
  and leaves (`left` in the footer). Each demand keeps idle agents,
  biggest first, up to the peak of what is left: keeping them only up to
  the width still to come let one leave in a lull and started another for
  the wide part after it. Starts and leaves count the cores agents report,
  and a starting agent's declared ones (`Orchestrator.cores`). One a
  remaining task needs for its size (`above`) stays
  (`vx-dte/src/plugin.ts`, `Orchestrator.retire`).

## Packing and sizing (history only)

- Shipped: an agent fills itself by comparing its cores and memory with
  each task's measured need. A task with no history gets a whole agent.
- Shipped: a task that reached at least 90% of its agent's cores or
  memory moves up one size on the next run. It keeps moving up until it
  fits or no bigger size exists.
- There is no `exec.resources`: history is the only source.
- History keeps the placement label, the agent's cores and memory, and
  the peak and average cores and memory. The orchestrator writes them
  (schema v44).
- Shipped: core seams only. `vx-schedule-history` carries each task's
  measured need in the default branch's timings blob and hands it to
  core (`importTimings`, schema v45); core's `resourcesFor` answers it
  for a task never run on this machine, and `vx-dte` reads it from core.
  No plugin imports another.
- Shipped: `vx-dte` reads the needs again once the import lands: core's
  `ctx.onRefine` calls it when another plugin refines (the schedule
  plugin's fetched timings), and the tasks not yet placed pack by them.

## Leases and heartbeat

- Every request to the relay counts as a heartbeat (PROTOCOL.md).
  Shipped: every six heartbeats (`HELD_EVERY`) while an agent holds
  tasks, it sends `held`, the tasks it runs and the ones in its queue. At
  one per heartbeat, `held` was most of a run's relay traffic
  (2026-10-22); the relay's heartbeat still finds a dead agent.
- Shipped: each task sent to an agent is leased to it for three `held`
  periods, and each `held` naming it renews the lease. When the lease
  expires, the task goes back to ready. Only the current lease holder's
  result is accepted, so a lost agent's late result is dropped.

## Retry on agent faults

- Shipped: an agent fault means the relay lost the agent (it left, died
  or froze), its lease on the task expired, or it could not run the task
  (a full disk, a failed unpack: it sends `fault`). A task it began runs
  again on another agent, and the faulty agent gets no more work. Such a
  retry does not count against the task's `retries`.
- Shipped: a lost agent frees its place under its size's `max`, so the
  run starts another for what is left (a planned agent's job is spent and
  is not started again). With none online, none starting and no share
  here, the run fails rather than wait: `small#1 was lost and no agent is
left`. Agents that join on their own (no adapter) may still join, so
  such a run waits.
- Shipped: a run its cache answers whole starts no agent: agents start
  at the first task that reaches the executor.
- The limit is 2 agents. After faults on two agents that began it, the
  task fails and names both: `t1: failed on 2 agents: small#1 lost,
small#2 ENOSPC`.
- A fault before the task started (queued or prefetched) sends the task
  back to ready and does not count.
- Shipped: a failed checkout or install (`git worktree add`, `prepare`)
  fails that agent. The first one in a run frees its place, so another
  agent starts (a network blip); after a second, none more are started.
  The run fails when no agent is left:
  `no agent could start: small#2 prepare exited 4: …`.
- A non-zero exit is a real failure, where only the task's `retries`
  apply.

## Lost relay

- Shipped: the run fails, with no local fallback, and finished tasks keep
  their cache. A hung orchestrator is left to the CI timeout.

## Relay

- No framework and zero dependencies: one fetch-handler core over a small
  storage interface.
- Shipped: two thin entries. `bun.ts` keeps state in memory. `worker.ts`
  holds each run in one Cloudflare Durable Object (`wrangler.jsonc`,
  deployed by `wrangler`: the Deploy to Cloudflare button parses no
  other config).
- Shipped (2026-10-22, owner): a run id is a channel the orchestrator
  claims. Its join names a P-256 key made for the run; the relay keeps it
  and takes each later request as the orchestrator only signed by it
  (once, within two minutes), so no other side acts as it, whatever
  adapter started it. The orchestrator checks each agent the moment the
  relay says it joined, before or after the claim, and `remove`s one
  without the run's key; the agent's next poll reads why.
- Shipped (2026-10-22, owner: "stores nothing, knows nothing, only
  relays"): a run is a hash of its id and claims, no message is stored
  (a restart loses a participant with a full queue), an agent's info goes
  once told, and a closed run keeps only its hash a day. Next, after
  Tailscale's DERP: per-participant rate limits and size padding.
- Shipped (2026-10-22): websockets on the Durable Object, hibernated
  between messages. The run is in the object's storage, the runtime
  answers `ping` without waking it, and an alarm at the earliest
  participant's three-heartbeat deadline, not a timer, finds the silent.
- Shipped: the package directory is the template of a Deploy to Cloudflare
  button. The user fills in only `ALLOW`, entries
  `issuer:owner/repo:workflow`: a repository per issuer, a workflow per
  repository (owner, 2026-10-22). The audience defaults to the
  URL the worker is reached at, which is unknown until the first deploy.
- Shipped (2026-10-22): the Bun relay offers websockets too, since
  `Bun.serve` has them for free. Polling stays the fallback: for a relay
  that offers none, and for a participant whose socket closed, which
  then learns from HTTP whether it is still in the run.
- Planned: a poll is a long-poll where one request carries results, the
  heartbeat and the next batch. Polling prefetches and backs off when
  idle, and must never add latency (tested against websockets).

## Relay encryption

- Shipped: the Noise Protocol Framework (revision 34) on WebCrypto, no
  dependency, held to cacophony's test vectors. One handshake per agent,
  the agent the initiator, prologue `vx-dte\0<run>`. With the run's key:
  `Noise_NNpsk0_25519_AESGCM_SHA256` (`-> psk, e` / `<- e, ee`), psk =
  SHA-256(key); the agent's join info is message 1's payload. Each body
  after is Noise transport messages naming their nonce (Noise §11.4, the
  relay may reorder): a changed body loses its agent, a replayed nonce is
  dropped. Ephemeral keys only (forward secrecy). `VX_DTE_SECRET`, when
  set, wins; else an adapter's agents get one made per run (`local()`,
  `docker()`); with no adapter it is required. The full task env travels,
  encrypted.
- Shipped: GitHub, keyless (`githubProof`): `Noise_NN_25519_AESGCM_SHA256`,
  bound by OIDC tokens. The agent's audience is
  `vx-dte:<sha256 of join, run, message 1>`, the orchestrator's
  `vx-dte:<sha256 of hello, run, handshake hash>`; each side checks the
  other's as GitHub's and of the same `repository_id`. An adapter marks
  its agents `keyless`.
- Shipped: the relay binds a run to its repository (`repository_id`,
  `project_id`), not its pipeline: agents run in a GitLab child pipeline
  or a dispatched GitHub workflow. The run's own key admits agents.
- Shipped: GitLab: `vx dte plan` makes the run's key and passes it as an
  artifact (`access: none`, `expire_in` = the pipeline timeout).

## Files

- Shipped: no file travels through the relay; it carries only orders and
  status. Every task's files and output go through the workspace's cache.
- Shipped (core seam): `ExecutorContext.artifacts` and
  `CommandContext.artifacts` (`TaskArtifacts`). `save(key, task, run)`
  keeps the files a task's outputs match and its output as entry `key`,
  here and on each remote the workspace writes, masking the task env's
  secrets. `restore(key, task)` lays them into the workspace from the
  local store or the first remote holding it. A key restored and then
  saved is not uploaded again. A verb writes the remote under a run's
  rules: on CI, or when the workspace's `cache.policy` names it.
- Shipped: an order carries the task's key and its dependencies' keys.
  The agent restores the dependencies it lacks, runs the task, and saves
  under the task's key, or under a key of the run and task for an
  uncached or failed task, so no hit ever serves it. `end` carries the
  key and the result head (exit, time, usage, violations); the
  orchestrator restores by the key.
- Shipped: an agent reads the cache as the run does (M, 2026-10-21
  17:33-17:35). `welcome` carries `CacheFacts`: the run's refs, so the
  agent works out the same read scope, and the access each remote lends
  (`RemoteCacheLayer.lend`, an OIDC exchange's token, never a stored
  secret). The server's token decides where it may write. A `cache`
  message lends again before the first token ends. An agent's plugin uses
  a lent token over its own OIDC exchange, since the server files a write
  by the token (an agent's own filed tasks where the run could not read
  them, 2026-10-22); only a token of its own set by hand wins. Each task gets only
  the env its config passes, not the agent's whole env.

## Display

Core renders, and plugins hand it data.

- Shipped: a task's id carries its agent, `app#build@small#1`, the
  agent colored per agent. Local tasks get no suffix.
- Shipped: the running list shows agents. Plugin blocks, which can span
  several lines, render both live and in the summary.
- Shipped: a task waiting in an agent's queue, or for an agent, has no
  row and counts as `scheduled` on the tasks line; its row and clock start when the agent begins it
  (the agent sends `start`). Agent cores and memory show only in the
  final summary.
- Decided (owner, 2026-10-22): no live log streaming. A task's log
  replays in the orchestrator when the task ends: a CI orchestrator has
  no interactive terminal, so lines of tasks on many agents would
  interleave.
- Shipped: `vx last` shows where each task ran, and telemetry plugins get
  placement and agent stats.

## Adapters

- Shipped: `local()` runs agents in git worktrees. Use
  `prepare: 'bun install'` when a worktree needs dependencies. The
  worktrees are removed by a detached shell after vx exits, so a stop
  is not held up by them (a 300k-file tree took 2.7 s).
- Shipped: `github({ workflow? })`. One `vx-agent.yml` (inputs: run,
  relay, sha, size, and the agents as JSON; `runs-on` by size; a matrix
  over the agents) is dispatched once per size for the agents one demand
  starts: live dispatch is the default. Agents check out the run's
  commit. They are `keyless` (GitHub OIDC), and the relay token defaults
  to an OIDC token for the relay's URL. The relay admits agents by repo
  and `VX_DTE_RUN`.
- Shipped (owner, 2026-10-22): a run id is a random (v4) UUID, which the
  relay and vx check, so no one can guess one: `uuidgen` on GitHub, the
  plan's on GitLab.
- Shipped (no API token): `gitlab({ include, tags? })` and `vx dte plan`.
  The plan writes `vx-agents.yml` (one job per agent, each size's `max`),
  `vx-dte.env` (the orchestrator job's `VX_DTE_RUN`, a random UUID), `.vx/dte/plan.json` (the agents, for
  the orchestrator) and the run's secret `.vx/dte/secret`. Agent jobs fetch the plan job's
  artifacts through `needs: pipeline: $PARENT_PIPELINE_ID`. `tags` routes
  each size to its runners.
- Shipped (live, `VX_DTE_GITLAB_TOKEN`): the first wave is automatic and
  the rest `when: manual`. `vx dte plan` takes the run's selection
  (`vx dte plan build --affected`), reads its graph from
  `vx run <args> --dry=json` and history, and sizes the first wave as the
  run's demand would at its start (`toStart`); a task with no history
  takes a whole agent. The orchestrator finds the child
  through its pipeline's `vx-agents` bridge (waiting up to a minute for
  it), plays a job when demand starts that size, and cancels unplayed
  jobs at the end.
- GitLab design. Setup stays in the user's GitLab YAML, because the
  runner already clones: `gitlab({ include: '.gitlab/vx.yml' })` (the
  option name is not final). Generated agent jobs extend exactly one
  template, `.vx-agent`, which is required. The user composes it however
  they like (`.vx-agent: { extends: .vx, … }`). vx defines no other
  template names.
  - The main pipeline has three of the user's own jobs. `vx-plan` writes
    `vx-agents.yml`. `vx-agents` triggers it as a child pipeline, without
    `strategy: depend`. `vx` is the orchestrator, and its script is the
    user's own `vx run …`. `vx dte plan` takes that run's selection, not
    its command.
  - The child pipeline holds only agent jobs
    (`include: [{ local: <file> }]`, `extends: .vx-agent`).
  - Default, no API token: the plan writes every agent the run will need,
    sized from history, as automatic jobs. They all start at once and warm
    up alongside the orchestrator, since agents may join before it.
    Keep-alive and exit go through the heartbeat.
  - Opt-in live spawning: when `VX_DTE_GITLAB_TOKEN` is set (a project
    or personal access token with `api` scope, as a masked CI/CD
    variable both the `vx-plan` and `vx` jobs see), the plan writes the
    first wave as automatic jobs and the rest as `when: manual`. The
    orchestrator finds the child pipeline through the API as its own
    pipeline's downstream pipeline (to verify on gitlab.com), plays jobs
    there live, and cancels the unplayed ones at the end. On GitHub, live
    spawning is the default (`workflow_dispatch` per wave).
  - Generated agent jobs, and every docs example, call the binary
    directly through the repo's package manager as the lockfile plugin
    knows it (`pnpm exec vx …`, `npx @vzn/vx …`, `bunx @vzn/vx …`), never a
    `package.json` script.
