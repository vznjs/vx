vx now runs any language's projects, every run starts from one lock,
and pull requests build on what main already cached. Until now core read
`package.json` everywhere, so vx could only ever be a JavaScript tool.
Now core knows only directories and configs, JavaScript is a plugin,
and runs evaluate nothing.

It is a big one for breaking changes too. Before 1.0 old names simply
stop working, so read the [list at the end](#breaking-changes) before
you update.

Enjoy the release!

## A core that knows no language

A task runner should not care what language a task builds. Yet our core
read `package.json` to find projects, folded it into every cache key and
drew dependency edges from it. A Rust or Python folder could not be a
first-class project.

Now a project is any directory with a `vx.config`. What JavaScript
needs, the members, the edges and `package.json` as an input, comes from
`pnpm()`, `bun()`, `npm()` or `yarn()` in `@vzn/vx-lockfile`. The edges
are exactly what your lockfile installed, so a dependency bump re-keys
only the tasks that use it. You don't write any of this: `vx init` adds
the right plugin, and in a repo with no `package.json` it writes a
workspace with one project, the root.

```sh frame="terminal"
$ vx init
vx init: no package.json, so no scripts to map: a workspace with one project, the root.
wrote .vx/workspace.ts, vx.config.ts, .vx/.gitignore, .vx/.gitattributes.

vx lock: locked 1 project config → .vx/projects.lock.json
$ vx run build
└─ //#build ── (14ms) restored-local
```

Drop the plugin and a `^build` is refused rather than replaying stale
bytes. More in
[A lockfile bump should re-key two tasks, not sixty](../../blog/lockfile-aware-keys/).

## Runs read only the lock

Every run used to evaluate every `vx.config.ts` and check the graph
first, even when nothing changed. That is work you pay for on each run,
and it made a run's view of the configs depend on whatever was on disk.

Now `vx lock` evaluates the configs once, checks the graph rules and
writes `.vx/projects.lock.json`. Runs, `vx show` and `vx info` read that
file and evaluate nothing. Beside each config, `vx lock` writes a
readable `vx.lock.json`, so a config change shows up in review as data.
Run `vx lock` after you edit a config or update dependencies; on CI,
check it first:

```sh frame="terminal"
$ vx lock --check
$ vx run ci --all
```

See [When to run vx lock](../../guides/ci/#when-to-run-vx-lock).

## Everything vx keeps lives in .vx

vx files were scattered over the repo root, and the root was guessed.
Now `.vx/` holds it all: `workspace.ts` is the config and also marks
the root, the lock sits beside it, and local cache lives in
`.vx/cache`, kept out of git by its own committed `.gitignore`. Your
root `.gitignore` stays untouched.

```sh frame="terminal"
$ ls -a .vx
.gitattributes  .gitignore  projects.lock.json  workspace.ts
```

A global `vx` hands off to the project's own `@vzn/vx`, so everyone on
the team runs the version the repo pins.

## Pull requests reuse main's cache

A pull request should start from what main already built, and must not
write into the cache main reads. Cache scopes now do exactly that: a
named scope reads the default keys, then its own, and writes only its
own. On GitHub Actions, `github()` from `@vzn/vx-ci` sets the scope
`pr-<n>` for you. Off CI, a run reads the remote and writes nothing.

```sh frame="terminal"
$ vx run ci --affected=origin/main
```

See [Cache scopes and tokens](../../guides/ci/#cache-scopes-and-tokens).

## A run says how long it has left

A progress bar that counts tasks tells you little when one task takes a
minute and the rest take a second. vx now learns how long each task
usually takes and forecasts from that.

A task's usual duration is the median of its last five timings on this
branch, else on any branch. Timings are shared by every worktree of the
repo, so a fresh worktree forecasts on its first run. The `time` row
shows `~3s left`, sized by the longest unfinished chain and the work
left over your workers, and each running row shows the task's usual
duration while its elapsed time counts toward it:

```sh frame="terminal"
3.33s running ~5.2s  solid-js#types
time  1.41s · ~3s left
```

`--branch` or `VX_RUN_BRANCH` sets the branch a run records and forecasts
from, and `vx last --stats --branch main` shows each task's usual
duration there.

## Other noteworthy changes

- `vx cache clean` clears this repo's cache; `--older-than`,
  `--max-size`, `--global` and `--dry-run` shape it. It never touches
  your config or lock.
- A task no longer sees vx's own environment, on Linux and macOS. More
  in [A task sees only the env it names](../../blog/env-isolation/).
- `cache.outputs.clean: false` keeps a task's outputs on a miss, for
  tools that update their output in place.
- `vx upgrade` checks npm's signature before it installs.

## Breaking changes

Every cached task misses once. Then:

- `vx.workspace.ts` → `.vx/workspace.ts` (relative imports gain a
  `../`); `vx-lock.json` → `.vx/projects.lock.json`. Run `vx lock`.
- `package.json` edges and keys come only from a `@vzn/vx-lockfile`
  plugin; `NamedProject` → `DiscoveredProject`.
- `--frozen`, `--no-frozen`, `run.frozen` and `VX_RUN_FROZEN` → removed.
- `vx cache prune` → `vx cache clean`; `vx prune` → removed.
- `vx init` hands a repo with a `package.json`, `turbo.json` or
  `nx.json` to `@vzn/vx-migrate`.
- Workspace keys, `VX_*` variables and flags follow one path per
  setting: `cacheScope` → `cache.scope`; `--cache` → `--cache-policy`;
  `--download` → `--cache-download`; `vx migrate` →
  `bunx @vzn/vx-migrate`; `vx stats` → `vx info`.
- Cache scopes `'trusted'` and `'read-only'` → plain names; a read-only
  run is `cache.policy: 'remote:r'`. A cache plugin returns only a remote.
- `@vzn/vx-mcp` and `vx mcp` → the agent skill
  (`npx skills add vznjs/vx/packages/vx/skills/vx`).

What to do for each: [Upgrading](../../guides/upgrading/).

## How to update

```sh frame="terminal"
npm install -D @vzn/vx@latest
npx @vzn/vx lock
```

A standalone binary updates itself with `vx upgrade`.
