The pages before this one explain what a cache key is, what goes into it
and which keys an edit moves. This page lets you check that on files you
edit yourself. It runs vx's real planner in your browser: the same source
code the `vx` command runs, bundled for a web page, and held to the
command by tests that plan the same files both ways and compare every key.

The playground plans. It does not run commands. It evaluates each
`vx.config.mjs`, builds the task graph, computes every task's key and asks
a cache whether it holds that key, which is what `vx run --dry` does. Then
it pretends the run happened and saves every key, so the next run can hit.
Nothing is built, and no command runs.

After using it you should be able to predict, before you run, which keys
an edit moves.

## Planning comes before running

Before a runner starts any task, it works out the whole run. It reads each
package's config, builds the [task graph](../glossary/#task-graph),
computes each task's [cache key](../glossary/#cache-key) from its declared
inputs and the keys of the tasks it waits for, and looks each key up. A key
it finds is a hit: the stored result is restored and the task does not
run. A key it does not find is a miss: the task runs.

All of that happens before the first command starts, so a runner can show
it without running anything. That is a dry run, and it is what this page
does.

## The workspace

The workspace is the toy monorepo from
[What is task orchestration?](../what-is-task-orchestration/): `utils`;
`ui` and `api`, which use `utils`; and `app`, which uses `ui` and `api`.
Each has a `build` and a `test`, wired by `^build` and `build`. `app` also
has `app#docs`, which nothing waits for. That makes nine tasks.

Every task declares the files it reads. Each `build` reads `src/**`, and
each `test` reads `src/**` and `test/**`. `api#build` also declares the
`API_URL` environment variable. Without JavaScript, the table below is the
graph and its inputs. With JavaScript on, it is the playground.

## Try it

Run each step in order. The status line under the controls says what
each run did, and the table shows every task's key, whether the simulated
cache holds it, and whether the key moved since the run before.

1. **Run.** The cache is empty, so all nine tasks miss. Every key is new.
2. **Run again,** with no edit. No key moves, and every key is in the cache
   now, so all nine tasks hit.
3. **Edit `packages/ui/src/button.tsx`** (pick it in the file list and
   change any character), then run. Four keys move: `ui#build` and
   `ui#test` read the file, `app#build` waits for `ui#build`, and
   `app#test` waits for `app#build`. Those four miss. The other five hit:
   nothing they read changed.
4. **Add a file that no config mentions,** such as
   `packages/ui/README.md`, and run. No key moves, and every task hits. No
   task declared the file, so no key reads it. That is safe here, because
   no command reads it either. When a command does read a file its task
   does not declare, the hit is stale:
   [Correctness](../correctness/) shows that failure and how the sandbox
   catches it.
5. **Break a config.** Delete the last `}` of
   `packages/api/vx.config.mjs` and run. The error names the project and
   the file, and gives the message the evaluation threw. The table keeps
   the last good run and is marked stale. Undo the edit, or press Reset,
   which also empties the cache.

Some other things to try: change `API_URL` and see which four keys move,
stop declaring `test/**` in one package's `test`, or ask for a task no
package declares, such as `lint`.

## What it does not model

- **Running.** No command runs and nothing is written. A hit here means
  the key is in the simulated cache, which holds every key an earlier run
  on this page planned.
- **Plugins.** The workspace has no `vx.workspace.ts`, so no plugin
  changes a key, the graph or the order.
- **Git.** Every file counts as committed. The planner takes each file's
  hash the way git would, so a file's contribution to a key is what it
  would be in a real repository.

## How vx does it

- **The same code.** The planner on this page is core's own source: its
  workspace discovery, config validation, task graph, key derivation and
  scheduler. Where core reads the disk, a small layer reads the files you
  are editing instead, and the hash and glob matching Bun provides are
  ported to run in a browser.
- **The same config evaluation.** Each `vx.config.mjs` runs in a Web
  Worker, as a module that can import only `@vzn/vx`, and must finish
  within two seconds. Its default export is the config, as it is for vx.
- **Held to the command by tests.** The site ships the bundle that core's
  tests build. Those tests commit this page's workspace to a git
  repository, run `vx run build test --all --dry=json` over it, and check
  that the planner here gives every task the same key and cache status,
  before and after an edit to `packages/ui/src/button.tsx`
  ([the design](../../design/playground-ui-2026-09/)).

## How the others show a plan

- **Turborepo** prints a dry run with `turbo run --dry`, and
  `--dry=json` gives each task's hash and whether it is cached. Its
  caching guide points to `--dry` and `--summarize` for finding out why a
  hash changed
  ([troubleshooting](https://turborepo.com/docs/crafting-your-repository/caching#troubleshooting)).
- **Nx** draws the graph of projects and tasks
  ([explore the graph](https://nx.dev/docs/features/explore-graph)).
- **Bazel** answers questions about the actions a build would run, with
  their inputs and outputs, through `bazel aquery`
  ([action graph query](https://bazel.build/query/aquery)).
