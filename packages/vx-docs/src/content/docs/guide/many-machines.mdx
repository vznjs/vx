You build `utils` in the morning. CI builds it again. A teammate builds it
a third time.

<Diagram {...P.threeBuilds} />

Each machine keeps its results to itself, so each one repeats the work.

## Same inputs give the same key on every machine

<Diagram {...P.sameKey} />

A cache key is a fingerprint of what a task reads: its files, its command
and its settings. Nothing in it names a machine. So a result stored under a
key is right for that key anywhere. Put the store where every machine can
reach it, and you have a [shared cache](../../glossary/#remote-cache).

## Only CI writes to the shared cache

<Diagram {...P.whoWrites} />

A shared cache shares mistakes too. A laptop has leftovers: a file you
never committed, a tool you patched by hand. A wrong result from it would be
replayed on every machine. CI builds from a clean checkout every time, so
let CI write and laptops read.

## A worker gets only what the task declares

<Diagram {...P.worker} />

You can also send a task to another machine, a worker, and get the output
back. That is [remote execution](../../glossary/#remote-execution).
The worker has only the files the task declares. A file the task reads but
never declared is missing, so the task fails loudly instead of passing by
luck.

## In vx

A plugin in `vx.workspace.ts` adds a shared cache and workers; vx itself
runs no server:

```ts
// vx.workspace.ts
import { defineWorkspace } from '@vzn/vx'
import { reapi } from '@vzn/vx-reapi'

export default defineWorkspace({
  plugins: [reapi({ endpoint: 'grpcs://cache.example.com:443', execute: true })],
})
```
