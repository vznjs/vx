One config holds most of the words on this page. Find each one in it:

```ts title="packages/web/vx.config.ts"
export default defineProject({ //           a project
  tasks: {
    build: { //                             a task
      dependsOn: ['^build'], //             a task dependency
      exec: { command: 'vite build' },
      inputs: { files: ['src/**'] }, //     inputs make the cache key
      outputs: { files: ['dist/**'] }, //   outputs go in the cache
      cache: true,
    },
  },
})
```

## Where tasks live

### Workspace

**Your whole repository, as vx sees it.** It starts at the folder holding `.vx/workspace.ts` ([workspace](../docs/workspace/)).

### Project

**A folder with a `vx.config.ts`**, such as `packages/web`. Usually a package, in any language ([workspace](../docs/workspace/)).

### Task

**One command for one project.** Its id is `project#task`, such as `@demo/web#build` ([tasks](../docs/tasks/)).

### Task dependency

**A task that must finish first.** `dependsOn: ['^build']` means: build the projects I depend on before me ([dependencies first](../docs/tasks/#build-a-projects-dependencies-first)).

### Task graph

**Every task a command will run, joined by its dependencies.** Read it when a run surprises you: `vx run build --dry` ([graph explorer](../docs/graph-explorer/)).

### Project graph

**The projects and which ones depend on which.** A lockfile plugin reads it from your package manager ([lockfiles](../docs/lockfiles/)).

### Lock

**Your configs, evaluated once.** `vx lock` writes `.vx/projects.lock`. Every run reads that file, never the configs ([check the lock](../docs/ci/check-the-lock/)).

<Quiz q="You add a task to packages/web/vx.config.ts. What do you run before vx run sees it?">
  `vx lock`. Runs read only `.vx/projects.lock`, so the lock must include the new task.
</Quiz>

<Takeaway>name every part of a workspace, from `.vx/workspace.ts` down to one task.</Takeaway>

## Running tasks

### Up to date

**A task whose outputs are already in place.** vx runs nothing and copies nothing for it ([caching](../docs/caching/)).

### Affected

**The projects a change can reach**: the ones you edited, plus everything that depends on them. `vx run test --affected` runs only those ([run what changed](../docs/running/run-what-changed/)).

### Persistent task

**A task that never exits**, such as `vite dev`. `exec.persistent.readyWhen` tells vx when it is ready for the tasks after it. Never cached ([dev servers](../docs/dev-servers/)).

### Critical path

**The longest line of tasks that each wait on the one before.** No run ends sooner than it. The `@vzn/vx-history` plugin starts that line first ([history server](../docs/servers/history/)).

<Takeaway>tell up to date from affected, and know why a dev server is never cached.</Takeaway>

## Caching

### Inputs

**Everything that can change a task's result**: files, config, env, and the tasks before it. You list the files. vx never guesses them ([caching](../docs/caching/)).

### Outputs

**The files a task makes**, such as `dist/**`. vx stores them, and the task's terminal output too ([caching](../docs/caching/)).

### Cache key

**A short code made from a task's inputs.** Same inputs, same key, same outputs. vx's key is a 16-character xxHash3 digest ([how vx decides](../docs/caching/#how-vx-decides)).

### Hit and miss

**A hit** finds the key and puts the stored outputs back. **A miss** runs the task, then stores what it made ([how vx decides](../docs/caching/#how-vx-decides)).

### Stale hit

**A hit that serves the wrong files**, because the task read something missing from its inputs. The run looks green. It is the worst thing a cache can do ([sandboxing](../docs/sandboxing/)).

### Remote cache

**A cache shared between machines**, so CI and your laptop reuse each other's results ([remote cache](../docs/remote-cache/)).

<Quiz q="A task reads .env, but .env is not in its inputs. You change .env. What happens?">
  A stale hit. The key did not change, so vx restores the old outputs. Add `.env` to the inputs.
  A sandbox would have failed the task when it read the file.
</Quiz>

<Takeaway>explain why a task ran or was skipped, and spot a stale hit before it bites.</Takeaway>

## Beyond one machine

### Sandbox

**A task run where it sees only the files you grant.** A read outside them fails the task and names the file, so a missing input cannot hide. Set `exec.sandbox` ([sandboxing](../docs/sandboxing/)).

### Distributed task execution

**One run spread over several CI machines.** You start one job; it starts **workers** and hands each one tasks ([Distributed task execution](../docs/distributed-task-execution/)).

### Worker

**A CI job that runs tasks for a Distributed task execution run.** Its results come back through the remote cache ([Distributed task execution](../docs/distributed-task-execution/)).

### Relay

**The server that passes messages between a run and its workers.** You host it ([DTE server](../docs/servers/dte/)).

### Remote execution

**Running a task on a build farm** and bringing its outputs back. `exec.remote`, through the `@vzn/vx-reapi` plugin ([remote execution](../docs/remote-execution/)).

### Plugin

**A package that changes part of a run**: where tasks run, where the cache lives, what gets reported. Listed in `.vx/workspace.ts` ([plugins](../docs/plugins/)).

<Takeaway>pick the right tool when one machine is not enough: sandbox, workers or a build farm.</Takeaway>
