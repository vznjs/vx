vx is fast because it does **less work**, and the work it skips is proven safe to skip.

```sh
vx run build
```

<Concept term="Up to date">
  The task's outputs are already on disk and match its key. vx does nothing for it: no copy, no
  command.
</Concept>

## Every task ends one of three ways

<Diagram {...threeOutcomes} />

Only a **new key** runs the command. The other two outcomes cost milliseconds.

<Quiz q="You delete dist/ in @demo/web and change nothing else. What does vx do?">
  It restores `dist/` from the cache. The key is the same, so the old result is still right.
</Quiz>

<Takeaway>read a run's task lines and tell which tasks did work.</Takeaway>

## Know what changed without reading files

<Concept term="Cache key">
  A short code made from everything a task reads. Same inputs, same key.
</Concept>

Git already knows an ID for every committed file. vx asks git once per run and builds each key from those IDs.

If you edited nothing, vx reads no source file to build a key. A file you edited is read once and gets the ID git would give it.

<Quiz q="You commit your edit. Does the next run rebuild?">
  No. The edited file already had git's ID for its content, and committing keeps that ID. The key stays
  the same.
</Quiz>

<Takeaway>commit freely: a commit alone never changes a key.</Takeaway>

## Start the right task first

vx runs every ready task it has a free worker for. When more tasks are ready than workers, it starts the one **most other tasks wait on**.

<Diagram {...readyFirst} />

Add the `@vzn/vx-history` plugin and vx orders tasks by the longest path of waiting work left, learned from past runs ([plugins](../../docs/plugins/)).

<Takeaway>see why a long line of dependent builds starts before a lone lint.</Takeaway>

## Nothing runs in the background

- **No daemon.** No background process, no stale state, no socket to break.
- **No config evaluated in a run.** `vx lock` evaluates every `vx.config.ts` once into `.vx/projects.lock`. A run reads only that file.

<Aside type="tip">Commit `.vx/projects.lock`. CI then starts from the same lock you ran.</Aside>

<Takeaway>expect every `vx run` to start the same way, with nothing left over from the last one.</Takeaway>

<Deeper level="patterns" title="Keep your own workspace fast">

### List only what a task reads

A file outside `inputs.files` never moves the key. A smaller list means fewer rebuilds.

```ts title="packages/web/vx.config.ts" mark={4}
build: {
  dependsOn: ['^build'],
  exec: { command: 'vite build' },
  inputs: { files: ['src/**', 'index.html', 'vite.config.js'] },
  outputs: { files: ['dist/**'] },
  cache: true,
},
```

<Takeaway>trim a task's inputs to what its command reads.</Takeaway>

### Let the sandbox check your list

With `exec.sandbox`, a task sees only the files you grant. A read outside them fails the task and names the file ([Sandboxing](../../docs/sandboxing/)).

<Takeaway>keep a short input list and let a failed read tell you what it missed.</Takeaway>

### Ask why a task ran

```sh
vx why @demo/web#build
```

It names the input that changed ([Caching](../../docs/caching/)).

<Takeaway>find the file behind any rebuild.</Takeaway>

<Deeper level="details" title="Under the hood">

### What else vx does

1. **`^build` skips the gaps.** It walks past projects with no `build` to the nearest one that has it. No filler tasks.
2. **The key sees the evaluated config.** Imports, presets and computed values all count.
3. **Outputs belong to their task.** vx clears declared outputs before a task runs, so no stale file survives.
4. **Overlapping outputs are refused** (`run.rules.exclusiveOutputs`, on by default).

### The mechanics

- **Hashes come from git's index.** One `git ls-files -s` lists every tracked file and its ID. A `git status` beside it finds edited and new files. Clean-tree key derivation costs zero source-file reads.
- **Bitset graph maths.** Task priority uses packed bitsets. On a 3,270-task graph, 8.5 s became a few milliseconds.
- **A scheduler that never re-scans.** Ready tasks come off a heap. A finished task updates only its direct dependents.
- **Restores check first.** Outputs already in place cost one stat per file: no writes.
- **Plain files in the local cache.** A restore copies files out, with a clone where the disk supports it. Nothing to unpack.
- **Uploads off the critical path.** A remote cache upload packs its archive in the background.

### What vx leaves out on purpose

- **No traced inputs.** A trace shows what a task read once, after it ran. The key is needed before it runs.
- **No daemon.** The cold and nothing-changed numbers above are without one.
