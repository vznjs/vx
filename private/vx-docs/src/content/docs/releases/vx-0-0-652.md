A task vx has seen flake gets one more try instead of failing the run.
A sandbox can now close a task off from everything outside the
workspace. Caching is one switch, `cache: true`.

This release is breaking. Read the [breaking changes](#breaking-changes) first.

## Caching is one switch

`cache` held a task's outputs and the stability rule for its inputs.
Declaring what a task writes meant turning caching on, and the stability
rule lived away from the inputs it judges.

Now `outputs` sits at the task's top level and `inputs.stability`
inside `inputs`. `cache: true` is only the switch, and still needs
`exec`, `inputs` and `outputs`. A task may declare outputs without
caching them; vx never saves, restores or cleans those.

```ts
import { defineProject } from '@vzn/vx/config'

export default defineProject({
  tasks: {
    build: {
      exec: { command: 'mkdir -p dist && cp src/a.js dist/' },
      inputs: { files: ['src/**'] },
      outputs: { files: ['dist/**'] },
      cache: true,
    },
  },
})
```

The old shape is refused where it stands:

```sh frame="terminal"
$ vx lock
✗ vx lock  lock not written

  app/vx.config.ts:7:7
  tasks.build.cache must be true or false
```

vx installs no tools: a task calls whatever is on PATH, and keys on its
version with `inputs.runtime`.

See [Caching](../../docs/caching/).

## A known-flaky task gets one more try

A flaky test failed the run, and someone pressed "re-run". vx already
knew which tasks were flaky; it did nothing with that.

Now a cached task whose exact key has failed and then passed before gets
one more attempt when it fails. Any other failure is final, and a
timeout is never retried. `retries` on a task, even `retries: 0`, turns
it off.

On CI, `@vzn/vx-history` with a history server shares that record, so
a fresh machine retries a task another machine saw flake. Under
`@vzn/vx-dte` the retry runs on a different worker. `vx last --log`
shows every attempt:

```sh frame="terminal"
$ vx last --log twice#test
── attempt 1 of 2 · exit 2 ──
said-before-exit
── attempt 2 of 2 · exit 2 ──
said-before-exit
```

See [Flaky is a claim](../../blog/flaky-tasks/).

## Close a task off from the machine

A sandboxed task could read anything outside the workspace, so a build
could lean on `/usr`, `~/.cache` or the system toolchain unseen.

`exec.sandbox: { hermetic: true }` moves the read wall to `/`. Outside
the workspace the task reads only what `allow.read` names. A program the
host has but no grant reads is named as such:

```sh frame="terminal"
$ vx run check --all
/usr/bin/sh: 1: cat: not found
[vx] exit 127 is the shell's "command not found": cat is /usr/bin/cat on the host, but no sandbox grant reads it, so inside the sandbox it is not there — add it (or its directory) to exec.sandbox.allow.read
```

A sandboxed task also reads the declared `outputs` of every task it
depends on, in any project, never their sources. One `tools` project can
build a tool every other project runs.

See [Sandboxing](../../docs/sandboxing/).

## Distributed runs plan giant workspaces and size their workers

On thousands of tasks, the machine running `vx run` under `dte()` spent
more CPU planning than the workers spent on short tasks. Now each
task's dependencies are read once, and placing a task reads each worker
once.

After a run, `dte()` plays it again and says which workers it needed:
`best` per declared size, `more` past a size's `max`, `any` shape per
platform. They show in the run's footer and, with `@vzn/vx-ci`, in the
GitHub job summary under "Workers to declare".

See [Distributed task execution](../../docs/distributed-task-execution/).

## Other noteworthy changes

- `exec.sandbox.weakerNetworkIsolation` applies per task on macOS.
- Each sandboxed task gets its own network proxy, and a network deny
  applies to that task alone.
- A save leaves out a FIFO under a task's outputs and says so.
- A `--filter` or verb argument holding a control character is refused.
- A removed current directory is said in one line, not a stack.
- The [Conformance](../../conformance/) page runs its cases against Nix too.

## How to update

```sh frame="terminal"
vx upgrade
```

## Breaking changes

Run `vx lock` after changing your configs.

- `cache: { outputs }` → `outputs` at the task's top level; `cache: { inputStability }` → `inputs.stability`; `cache` → `true` or `false`.
- Workspace defaults: `cache.inputStability` → `inputs.stability`, `cache.outputs.clean` → `outputs.clean`.

See also [Upgrading](../../guides/upgrading/).
