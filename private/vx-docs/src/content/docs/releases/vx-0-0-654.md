A run now reads every project, edge and mapped task from the lock, and
nothing else.

Distributed task execution ends when the critical path
does, holds less CPU, and says how much it held.

A sandboxed task can no
longer pass while blind to a file its key holds.

This release is breaking. Read the [breaking changes](#breaking-changes) first.

## Runs follow the lock

`vx lock` froze each `vx.config.ts`, but a plugin's `project` and
`discover` stages still ran on every run.

With `turbo()` or `nx()`, a run
read `turbo.json`, the manifests and git `HEAD` again, so what ran could
differ from what the lock held.

Now `vx lock` runs both stages and records what they return: each
project, its edges, and every task a plugin maps.

A run calls no `project` or
`discover` hook and reads only the lock. After you change a file a plugin reads,
run `vx lock`; `vx lock --check` names what moved.

```ansi
$ vx lock --check
[38;2;239;68;68m✗[0m [1mvx lock --check[0m  packages/app: the `project` stage maps it differently from the lock here — a file the plugin reads, or the environment, changed; run 'vx lock'

  [38;2;203;213;225mtasks.build.inputs.files[1]: "package.json" → "tsconfig.json"[0m
  [38;2;203;213;225mtasks.build.inputs.files[2]: (none) → "package.json"[0m
```

`--affected` selects a project whose locked config, name or edges
changed.

See [`vx lock`](../../cli/lock/).

## Distributed task execution ends on time

A run with known task times could still end past its critical path, and
a big worker stayed up for one small task while most of its cores sat
idle.

Now a run ends by its critical path plus one warm-up. When a big
worker's big work is over, its last task moves to a smaller worker that
joins just then.

Workers needed at once start as fewer, bigger ones, and
a task goes only on a size with room for its cores and memory.

The footer weighs a run's cost. `ideal` adds the least CPU a run ending
then holds; `total` adds the CPU the workers held, idle or not, warm-up
included.

```ansi
$ VX_DTE_RUN=$(uuidgen) vx run build --all
  [2mworkers [0m  [38;2;96;165;250mlinux.small[0m[2m#[0m[38;2;167;139;250m1[0m  stopped  3 done · warm-up 0.1s
  [2m        [0m  [2m               cpu peak 0.0 · used avg 0.0 cores · machine avg 0.1 · booked avg 0.3[0m
  [2m        [0m  [2m               cpu utilization machine 5% · tasks 0% · worker 2%[0m
  [2m        [0m  [2mideal          3.2s: each task as long as it took, placed perfectly, holding 0.3 core-s at least[0m
  [2m        [0m  [2mbest           1 × linux.small (2c/8G linux-x64): 3.2s, the fewest of its sizes[0m
  [2m        [0m  [2many            1 × (2c/8G linux-x64): 3.2s, of any cores, the least core time[0m
  [2m        [0m  total          cpu utilization machine 5% · tasks 0% · worker 2% · held 6.4 core-s
```

When a run ends late, a `drift` line says why, along the chain that
ended it: workers joining, waiting for room, sending inputs, and time
after the last task.

See [Distributed task execution](../../docs/distributed-task-execution/).

## The sandbox refuses a file it would hide

A sandboxed task that keyed `tsconfig.base.json` at the workspace root,
with no read grant for it, ran blind to it.

A tool that stats a config
before it opens it left no violation, so the task passed and its wrong
output was cached.

Now vx checks the key's files outside the project against the sandbox's
grants before the command starts. A file no grant reaches fails the
task, unrun, with the grant to add.

```ansi
$ vx run build --filter packages/lib
[2m┌─[0m [1m[38;2;244;114;182mpackages/lib[0m[2m#[0m[1m[38;2;244;114;182mbuild[0m [2m>[0m [1m[38;2;239;68;68mfailed (exit 1, 1 sandbox violation)[0m

[2m$ mkdir -p dist && cat ../../tsconfig.base.json > dist/tsconfig.json[0m

[2m├─[0m [1m[38;2;239;68;68mSANDBOX[0m [2m───────────────────────────────────────────────────[0m

vx: hidden by the sandbox, held by the key: /home/user/acme/tsconfig.base.json
vx: the sandbox hides a file this task's key holds, so it was not run: /home/user/acme/tsconfig.base.json. Grant it, e.g. `allow: { read: ['../../tsconfig.base.json'] }`.

[2mfix: exec.sandbox.allow: { read: ['../../tsconfig.base.json'] }[0m

[2m└─[0m [1m[38;2;244;114;182mpackages/lib[0m[2m#[0m[1m[38;2;244;114;182mbuild[0m [2m──[0m [2m(0ms)[0m [1m[38;2;239;68;68mfailed (exit 1, 1 sandbox violation)[0m
```

See [Sandboxing](../../docs/sandboxing/).

## Other noteworthy changes

- `vx lock` refuses a glob no file can match: a backwards class (`[z-a]`), surrounding whitespace, a control character, or braces expanding past 1024.
- When only literal outputs matched, vx names the wildcard globs that matched nothing: a later hit restores only the literal files.
- A run that removes a committed file under its outputs saves nothing, since no hit could replay the removal.
- A damaged `cache.db` page or a FIFO in an output tree degrades to a miss; a long Ctrl-Z no longer lifts a task's timeout.
- `vx last --live --follow` exits 1 when its run is lost or killed.
- Discovery no longer follows a symlinked directory.
- A `.vx/dependencies.lock.json` written by a newer vx is refused.
- `dte()` machine names may hold a dot again (`c5.large`).
- `turbo()` keys `package.json` past negated inputs; `nx()` reads `??` outputs and refuses kebab-case or alias output options it cannot map.
- Hardening closed stale cache hits through linked outputs, NFD and NFC sibling projects, `.gitattributes` files and lockfile plugins.

## How to update

```sh frame="terminal"
vx upgrade
```

## Breaking changes

Run `vx lock` after upgrading. Every cached task misses once.

- `.vx/projects.lock.json` → version 6, holding the `project` and `discover` stages. A plugin's change to projects, edges or mapped tasks reaches runs only through `vx lock`.
- Cache format → `vx-cache-v55`: the local cache starts empty once.

See also [Upgrading](../../guides/upgrading/).
