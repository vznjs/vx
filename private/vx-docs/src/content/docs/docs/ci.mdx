On CI, vx does two things. A push to `main` runs every task. A pull
request runs only the projects it changed and the projects that depend
on them.

This page sets that up on GitHub Actions. You need no server and no
token, only a repository where `vx run` already works on your machine
([Quickstart](../../quickstart/)).

## GitHub Actions

### 1. Install the CI plugin

```sh
bun add -d @vzn/vx-ci
```

### 2. Declare it

`vx init` already wrote `.vx/workspace.ts` with your lockfile's plugin.
Add `github()` beside it:

```ts
// .vx/workspace.ts
import { defineWorkspace } from '@vzn/vx/config'
import { github } from '@vzn/vx-ci'
import { bun } from '@vzn/vx-lockfile'

export default defineWorkspace({
  plugins: [
    // Reads bun.lock, so `^build` builds a package's dependencies first.
    bun(),
    // On GitHub Actions: the job summary, and the pull request's base for
    // --affected. Anywhere else it does nothing.
    github(),
  ],
})
```

Then update the lock and commit:

```sh
vx lock
git add .vx package.json bun.lock
git commit -m "ci: run vx on GitHub Actions"
```

### 3. Add the workflow

```yaml
# .github/workflows/ci.yml
name: ci
on:
  pull_request:
  merge_group:
  push:
    branches: [main]
jobs:
  ci:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: bun install --frozen-lockfile
      # Fails if someone changed a vx.config.ts and did not run vx lock.
      - run: bun vx lock --check
      # main and a merge queue run every task. A pull request runs
      # only the projects it changed and the projects that depend on them.
      - run: >
          bun vx run ci
          ${{ github.event_name == 'pull_request'
            && '--affected'
            || '--all' }}
```

`ci` is a task you define in your `vx.config.ts`, usually a group that
depends on your `build`, `test` and `lint` tasks
([Tasks](../tasks/)). Any task name works.

### 4. Push

Open a pull request: its run builds and tests only what it changed.
After it merges, the run on `main` runs everything.

Each run writes a summary on the workflow run's page:

> ## ❌ vx run
>
> **5** tasks · **2** executed · **2** cache hits (1 up-to-date, 1 restored, 1 from remote) · **1** failed · 21.4s
>
> ### Failures
>
> - **@acme/web#build** — exit 2
>
> | Task | Status | Duration |
> | --- | --- | --- |
> | @acme/web#build | ❌ failed | 3.1s |
> | @acme/web#test | ✅ ran | 4.2s |
> | @acme/api#build | ☁️ restored remote | 0ms |
> | @acme/ui#build | ✔️ up-to-date | 0ms |
> | @acme/ui#lint | ⏭️ skipped | 0ms |
>
> <sub>vx 0.0.21 · `vx run ci --all` · 3/5 passed · 1 up-to-date · 1 restored</sub>

A task that fails on inputs it passed on before is marked flaky in the
log:

```ansi

```

### When to run `vx lock`

Every run reads `.vx/projects.lock.json`, not your `vx.config.ts` files.
Run `vx lock` and commit the lock after you change any of these:

- a `vx.config.ts` or `.vx/workspace.ts`
- a file a config imports
- your dependencies

Make `vx lock --check` the workflow's first vx step. When someone
forgot, it fails and names the project.

### Sandboxed tasks

A task that declares `exec.sandbox` needs the OS sandbox on the runner.
Add `- run: bun vx setup github` after `bun install`
([vx-ci](../../plugins/vx-ci/#the-sandbox-runtime-vx-setup)).

### Common problems

- **`--affected has no base here`.** The clone has no base branch and no `origin` to fetch it from. Set `baseBranch` in `.vx/workspace.ts`, or pass `--affected=<ref>`.
- **`nothing affected since <ref>` on every push.** On a push to `main`, `origin/main` is the commit itself. Run `--all` on `main`, as the workflow above does: the cache skips what did not change.
- **The whole log lands in the job summary.** Don't redirect vx's output into `$GITHUB_STEP_SUMMARY`. `github()` writes the summary.

## GitLab CI

Declare `gitlab()` instead of `github()`:

```ts title=".vx/workspace.ts"
import { defineWorkspace } from '@vzn/vx/config'
import { gitlab } from '@vzn/vx-ci'
import { bun } from '@vzn/vx-lockfile'

export default defineWorkspace({ plugins: [bun(), gitlab()] })
```

Run the same two lines as the GitHub workflow:

```sh
bun vx lock --check
bun vx run ci --affected   # --all on the default branch
```

In a merge request, `gitlab()` gives `--affected` the request's diff
base. Each plugin does nothing outside its own CI, so you can declare
both.

For sandboxed tasks, run `bun vx setup gitlab` before vx.
