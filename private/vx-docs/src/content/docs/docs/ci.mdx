On CI, a pull request runs only the projects it changed. A push to `main` runs every project. One command does both:

```sh
vx pipeline pr
```

## Save the two runs

<Concept term="Pipeline">
  A run saved under a name in `.vx/workspace.ts`. `vx pipeline pr` runs the one named `pr`. Your
  machine and CI run exactly the same thing.
</Concept>

Add the CI plugin:

```sh
bun add -d @vzn/vx-ci
```

Then declare it and two pipelines:

```ts title=".vx/workspace.ts" ins={2,6,7-10}
import { defineWorkspace } from '@vzn/vx/config'
import { github } from '@vzn/vx-ci'
import { bun } from '@vzn/vx-lockfile'

export default defineWorkspace({
  plugins: [bun(), github()],
  pipelines: {
    pr: { tasks: ['lint', 'test', 'build'], affected: true },
    main: { tasks: ['lint', 'test', 'build'] },
  },
})
```

`affected: true` is the only difference: `pr` runs what the branch changed. `github()` finds the pull request's base and writes the job summary. Off GitHub Actions it does nothing.

Run `vx lock` and commit:

```sh
vx lock
git add -A
git commit -m "ci: run vx on GitHub Actions"
```

<Takeaway>run CI's exact checks on your own machine: `vx pipeline pr`.</Takeaway>

## GitHub Actions

```yaml title=".github/workflows/ci.yml" mark={17-18}
name: ci
on:
  pull_request:
  merge_group:
  push:
    branches: [main]
jobs:
  ci:
    runs-on: ubuntu-latest
    permissions:
      contents: read
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: bun install --frozen-lockfile
      - run: bun vx lock --check
      - run: >
          bun vx pipeline ${{ github.event_name == 'pull_request' && 'pr' || 'main' }}
```

`vx lock --check` fails the job when a config changed without `vx lock`. The last step picks `pr` on a pull request, `main` everywhere else.

Push, and open a pull request to see it run.

<Takeaway>run vx on every pull request and every push to `main`.</Takeaway>

## Predict what a pull request runs

<Concept term="Affected">
  A task is affected when the change touches its project, or a task it depends on is affected.
</Concept>

Pick a file. The tasks light up as `vx pipeline pr` ran them:

<AffectedPicker />

Two steps decide. **Affected** picks the tasks; then the **cache** skips each one whose inputs did not change.

<Quiz q="A pull request edits packages/ui/src/index.ts. Does @demo/web#test run?">
  Yes. `@demo/web#test` depends on `@demo/ui#build` (`^build`), and that build is affected. Only
  `@demo/web#lint` stays out: nothing it depends on changed.
</Quiz>

<Takeaway>tell, before you push, which tasks your pull request runs.</Takeaway>

## Keep the lock fresh

<Diagram {...lockCheck} />

Runs read `.vx/projects.lock`, not your `vx.config.ts` files. The workflow's check fails when someone edited a config and forgot `vx lock`:

```sh
vx lock --check
```

```ansi
[38;2;239;68;68m✗[0m [1mvx lock --check[0m  [38;2;203;213;225mpackages/ui/vx.config.ts evaluates differently from the lock here — its config, a file it imports, or the environment it reads changed; run 'vx lock'[0m

  [38;2;203;213;225mtasks.build.inputs.files[1]: (none) → "package.json"[0m
```

It exits `1` and names the field that moved, before → after. Run `vx lock`, commit, push. Then the check passes:

```ansi
[38;2;34;197;94m✓[0m [1mvx lock --check[0m  [38;2;203;213;225mup to date (2 projects)[0m
```

<Takeaway>catch a forgotten `vx lock` before it reaches `main`.</Takeaway>

<Deeper level="patterns" title="Common setups">

### Fix a merge conflict in the lock

Two branches changed configs, and git left a conflict in the lock. Every run refuses it:

```sh
vx run build --all
```

```ansi
[38;2;239;68;68m✗[0m [1mvx run[0m  [38;2;203;213;225m.vx/projects.lock holds a git merge conflict: run [0m[1m`vx lock`[0m[38;2;203;213;225m, which writes it anew from the configs[0m
```

Never edit the lock by hand:

<Steps>

1. Resolve the conflicts in your `vx.config.ts` files, as for any code.

2. Run `vx lock`. It writes the lock again from the merged configs:

   ```sh
   vx lock
   ```

   ```ansi
   [38;2;34;197;94m✓[0m [1mvx lock[0m  [38;2;203;213;225m2 project configs → .vx/projects.lock, .vx/dependencies.lock[0m
   ```

3. Commit: `git add -A && git commit`.

</Steps>

`vx lock` also rewrites `.vx/dependencies.lock` and each `vx.lock.json`, so their conflicts go away too.

### Stop a pull request at the first failure

```ts mark={1}
pr: { tasks: ['lint', 'test', 'build'], affected: true, failFast: true },
```

Without it, a failure skips only the tasks that depend on it, and the rest still report.

### A nightly run that retries

```ts
nightly: { tasks: ['test', 'e2e'], retries: 1, timeout: '30m', force: true },
```

`force: true` runs every task again, ignoring the cache. Call it from a scheduled workflow: `bun vx pipeline nightly`.

### Check a plan in a script

```ts
plan: { tasks: ['build', 'test'], affected: true, dry: true, format: 'json' },
```

`vx pipeline plan` runs nothing and prints one JSON document: every task, and whether it would hit the cache.

### GitLab CI

Declare `gitlab()` from the same package. In a merge request it gives `--affected` the request's base:

```ts title=".vx/workspace.ts"
import { defineWorkspace } from '@vzn/vx/config'
import { gitlab } from '@vzn/vx-ci'
import { bun } from '@vzn/vx-lockfile'

export default defineWorkspace({
  plugins: [bun(), gitlab()],
  pipelines: {
    pr: { tasks: ['lint', 'test', 'build'], affected: true },
    main: { tasks: ['lint', 'test', 'build'] },
  },
})
```

Run `bun vx lock --check`, then `bun vx pipeline pr` in a merge request and `main` on the default branch. Each plugin does nothing outside its own CI, so you can declare both.

### Sandboxed tasks

A task with [`exec.sandbox`](../sandboxing/) needs the OS sandbox on the runner. Add `bun vx setup github` (or `gitlab`) after `bun install` ([vx-ci](../../plugins/vx-ci/#the-sandbox-runtime-vx-setup)).

### Flaky tasks

A task that fails on inputs it passed on before is marked flaky in the log:

```ansi
            [38;2;239;68;68mfailed[0m  [2mmiss[0m           [2m—[0m     [38;2;203;213;225m3ms[0m     [2m—[0m      [2m—[0m       [2m—[0m       [2m—[0m [2mlocal[0m          [38;2;244;114;182m@demo/web[0m[2m#[0m[38;2;96;165;250mtest[0m [2mflaky - passed 3× before[0m
```

<Deeper level="details" title="Every pipeline key">

### Pipeline keys

A pipeline is a saved `vx run` over every project. Each key is its `vx run` flag in camelCase: `failFast` is `--fail-fast`. Only `tasks` is required.

| Key | Takes | What it does |
| --- | --- | --- |
| `tasks` | `['lint', 'test']`, `'web#e2e'` | The tasks to run, in every project that declares each. **Required.** |
| `filter` | `['./apps/*']` | Only these projects, plus what they depend on. |
| `affected` | `true`, or a git ref | Only what a change since the base reaches. |
| `excludeDependencies` | `true`, or names | Skip all `dependsOn` edges, or only those names. |
| `env` | `{ NAME: 'value' }` | Set for vx and its plugins, never for a task. A variable already set wins. |
| `concurrency` | `4`, `'50%'` | Most tasks at once. Default: the cores. |
| `schedule` | `'most-work'`, `'critical-path'`, `'direct-dependents'`, `'ready-order'` | Which ready task starts first. Default `'most-work'`. |
| `failFast` | `true` | Stop the run at the first failure. |
| `retries` | `1` | Re-runs of a failed task. Default `0`. |
| `timeout` | `'10m'` | Time limit per task. Default none. |
| `branch` | `'nightly'` | The branch the run records in history. Default: git's. |
| `cachePolicy` | `'local:rw,remote:r'` | What each cache may read and write. |
| `noCache` | `true` | No cache reads or writes. |
| `force` | `true` | Run every task again; still write the cache. |
| `cacheDir` | `'.vx/cache'` | Where the local cache lives, from the workspace root. |
| `cacheDownload` | `'all'`, `'toplevel'`, `'none'` | Which outputs of a remotely run task land here. Default `'all'`. |
| `cacheConcurrencyDownload` | `32` | Remote downloads at once. |
| `cacheConcurrencyUpload` | `32` | Uploads at once, per remote. |
| `cacheConcurrencyRestore` | `16` | Local hits restoring at once. |
| `outputLogs` | `'full'`, `'errors-only'`, `'hash-only'`, `'none'` | How much task output the log shows. |
| `verbosity` | `1` | `1` adds a table of every task. Default `0`. |
| `profile` | `true`, or a file | Write a Chrome trace of the run. |
| `dry` | `true` | Print the plan; run nothing. |
| `format` | `'json'` | With `dry`, print the plan as JSON. Default `'pretty'`. |

**Who wins.** A flag you type beats its key: `vx pipeline main --filter @demo/web` runs main's tasks in `@demo/web` and what it needs. A flag's `VX_*` variable beats it too. The key beats `.vx/workspace.ts`'s own setting.

**What a pipeline cannot do.** It has no `--all` key: it always starts from every project. Nothing goes after `--`, since forwarded args are for one task. A typo in `tasks` fails at `vx lock`, not in the CI job.

Full reference: [Pipelines](../../schema/workspace/#pipelines).

</Deeper>

<Deeper level="details" title="github() and gitlab() options">

### Plugin options

Both work with no options. Each does nothing outside its own CI.

| Option | Plugin | Default | What it does |
| --- | --- | --- | --- |
| `summaryFile` | `github()` | `$GITHUB_STEP_SUMMARY` | The file the job summary goes to. |
| `title` | `github()` | `'vx run'` | The summary's heading. |
| `cacheScope` | both | `true` | Name the base commit for `affected`, and keep a branch's remote cache entries apart. `false` turns it off. |

```ts
github({ title: 'web checks', cacheScope: false })
```

</Deeper>

<Deeper level="details" title="Every error and its fix">

### Common problems

`pr` on `main` itself has no base to compare with:

```ansi title="vx pipeline pr, on main"
[38;2;239;68;68m✗[0m [1mvx pipeline[0m  [38;2;203;213;225m--affected has no default on the base branch (main): drop --affected, --all runs every project (the cache skips what did not change), or name the last good commit, --affected=<sha>[0m

  [38;2;203;213;225m--affected is [0m[1m`pipelines.pr.affected`[0m[38;2;203;213;225m in .vx/workspace[0m
```

Run `main` there. The cache still skips what did not change.

A pipeline name that does not exist names the closest one:

```ansi title="vx pipeline prr"
[38;2;239;68;68m✗[0m [1mvx pipeline[0m  [38;2;203;213;225mno pipeline named prr; pipelines: pr, main[0m

  [2mfix[0m  [1mvx pipeline pr[0m
```

A config changed without `vx lock`:

```ansi title="vx pipeline main"
[38;2;239;68;68m✗[0m [1mvx pipeline[0m  [38;2;203;213;225mpackages/web/vx.config.ts changed since the last [0m[1m`vx lock`[0m[38;2;203;213;225m — run [0m[1m`vx lock`[0m
```

- **`--affected has no base here`.** The clone has no base branch and no `origin` to fetch it from. Set `baseBranch` in `.vx/workspace.ts`, or `affected: '<ref>'`.
- **`fetching it from origin failed`.** The checkout left no credentials (`persist-credentials: false`). Fetch the base in an earlier step.
- **`nothing affected since <ref>`.** The change touches no project. That is a pass, exit `0`.
- **The whole log lands in the job summary.** Don't redirect vx's output into `$GITHUB_STEP_SUMMARY`. `github()` writes the summary.

### When to run vx lock

Run `vx lock` and commit after you edit a `vx.config.ts`, `.vx/workspace.ts`, a file a config imports, or your dependencies.
