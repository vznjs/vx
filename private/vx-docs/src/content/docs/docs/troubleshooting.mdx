vx run biuld --all

## Read what vx printed

Every message has the same three parts. Step through three mistakes in the `@demo` workspace.

<Walkthrough title="Three mistakes, one shape">
<Frame title="1. A typo in a command">

```ansi title="vx run biuld --all"
[38;2;239;68;68m✗[0m [1mvx run[0m  [38;2;203;213;225mno projects declare task(s): biuld[0m

  [2mfix[0m  [1mbuild[0m
```

The red **✗** line says what is wrong. The **fix** line is what to type.

</Frame>
<Frame title="2. A mistake in a config">

```ansi title="vx lock"
[38;2;239;68;68m✗[0m [1mvx lock[0m  [38;2;203;213;225mlock not written[0m

  [1mpackages/web/vx.config.ts:8:7[0m
  [38;2;203;213;225mtasks.build.outputs must be an object (fields: clean, files, workspaceFiles), not an array[0m

    6 |       exec: { command: 'mkdir -p dist && cp src/main.js dist/main.js' },
    7 |       inputs: { files: ['src/**'] },
  > 8 |       outputs: ['dist/**'],
      |       ^

  [2mfix[0m  [1muse `{ files: [...] }`[0m
```

vx points at the file, the line and the column. The **fix** line says how to write it.

</Frame>
<Frame title="3. A task that failed">

```ansi title="vx run build --all"
[2m┌─[0m [1m[38;2;244;114;182m@demo/web[0m[2m#[0m[1m[38;2;244;114;182mbuild[0m [2m>[0m [1m[38;2;239;68;68mfailed (exited 0, no file matched dist/web.js)[0m

[2mpackages/web $ mkdir -p dist && cp src/main.js dist/main.js[0m

[2m└─[0m [1m[38;2;244;114;182m@demo/web[0m[2m#[0m[1m[38;2;244;114;182mbuild[0m [2m──[0m [2m(10ms)[0m [1m[38;2;239;68;68mfailed (exited 0, no file matched dist/web.js)[0m
```

The last line of the task's frame says why it failed: the command never wrote `dist/web.js`.

</Frame>
</Walkthrough>

<Concept term="Refusal">
  vx stops before it runs anything, because something would go wrong. Nothing on disk changed. Fix
  the line it names and run the same command again.
</Concept>

<Takeaway>read any vx error: what broke, where, and the command that fixes it.</Takeaway>

## vx printed an error

Every refusal has a code. Paste what vx printed, or pick the step where it stopped.

<ErrorFinder />

A typo in `--filter` names the closest project:

```sh
vx run build --filter @demo/ap
```

```ansi
[38;2;239;68;68m✗[0m [1mvx run[0m  [38;2;203;213;225mno projects matched filter(s): "@demo/ap"[0m

  [2mfix[0m  [1m@demo/app[0m
```

<Quiz q="vx says no projects declare task(s): lint, but you added lint to @demo/web's config a minute ago. Why?">
  A run reads its configs from the lock, `.vx/projects.lock`. The new task is not there yet. Run
  `vx lock`, then run `lint` again.
</Quiz>

<Takeaway>find any vx error by its words or its code, and apply the fix.</Takeaway>

<Deeper level="patterns" title="Branch on the code in a script">

Add `--format json`. A refusal then prints one line on stdout:

```sh
vx run biuld --all --dry --format json
```

```json
{"ok":false,"error":{"code":"VX_E_UNKNOWN_TASK","message":"vx run: no projects declare task(s): biuld. Did you mean build?","docs":"https://vznjs.github.io/vx/cli/#vx_e_unknown_task"}}
```

- `code` never changes between versions. Check it, not the message.
- `docs` links the fix. `vx docs VX_E_UNKNOWN_TASK` prints it in the terminal.
- The exit code is `1`. stderr still carries the message in words.

`vx lock --check --format json` gives each config problem its own `code`. See [For agents](../agents/).

<Takeaway>let a script or an agent react to an error without parsing English.</Takeaway>

</Deeper>

<Deeper level="details" title="Every message, word for word">

Find the start of the message in the left column. `…` stands for the names vx fills in.

| vx prints | Fix |
| --- | --- |
| `no .vx/workspace.ts in …` | Run `vx init` at the workspace root. It writes `.vx/workspace.ts`, which marks the root. A file above your git checkout does not count. |
| `… belongs to another user, so vx does not take its directory as your workspace` | Outside git, vx ignores a `.vx/workspace.ts` another user owns. Run vx in a checkout you own. |
| `not inside a project` | Run from a package's folder, or add `--all` or `--filter <name>`. |
| `two projects are named "…": …` | Two folders have the same name: set another `name` in one's `vx.config.ts`, then run `vx lock`. |
| `… locks …, but its … is gone` | A `vx.config.ts` was deleted or renamed: run `vx lock`. |
| `… holds a line … never writes` | A merge left a conflict in the lock: see [Fix a merge conflict in the lock](../ci/#fix-a-merge-conflict-in-the-lock). |
| `… evaluates differently from the lock here` | A config changed without `vx lock`: run `vx lock` and commit the lock. |
| `vx requires git: … is not inside a git work tree` | vx needs git: run `git init` at the workspace root. |
| `vx requires git: failed to spawn 'git'` | Install git. |
| `--affected has no base here` | Set `baseBranch`, or name a commit: `--affected=<ref>`. |
| `--affected has no default on the base branch` | On `main` itself, run `--all`: the cache skips what did not change. |
| `… has unknown field "<key>"` | A typo, or a Turbo or Nx key. The message lists the fields vx allows. |
| `dependsOn cycle` | Two tasks wait for each other: remove one `dependsOn` from the loop it prints. |
| `dependsOn …, but` `no project is named …` / `… declares no task …` | Use the name it suggests, or add that task to that package. |
| `no projects declare task(s)` | A typo, or a config changed without `vx lock`. `vx show` lists every task. |
| `unknown flag` | `vx run --help` lists the flags. |
| `no projects matched filter(s)` | Every `--filter` must match a project. The message suggests the closest name; `vx show` lists them all. |
| `timed out after …` | The task ran past its time limit: raise `exec.timeout` or `--timeout` ([guide](../running/set-a-time-limit/)). |
| `waiting for another vx run (pid …)` | One run per workspace at a time. It starts when that one ends. |
| `vx: command not found` | vx is not installed: `bunx @vzn/vx init` installs it, or `bun add -g @vzn/vx`. |

Each code's full list of cases is in the [CLI reference](../../cli/#error-codes).

</Deeper>

## It ran, but not how you expected

No error, yet the result is wrong. The three cases below are the usual ones. Sandbox, CI and migration surprises have their own lists:

<CardGrid>
  <LinkCard title="Sandboxing problems" href="../../docs/sandboxing/#common-problems" />
  <LinkCard title="CI problems" href="../../docs/ci/#common-problems" />
  <LinkCard title="Migration problems" href="../migrate/#common-problems" />
</CardGrid>

### You changed `vx.config.ts` and the run ignores it

A run reads the lock, not your configs. `vx lock --check` shows what drifted:

```ansi title="vx lock --check"
[38;2;239;68;68m✗[0m [1mvx lock --check[0m  [38;2;203;213;225mpackages/web/vx.config.ts evaluates differently from the lock here — its config, a file it imports, or the environment it reads changed; run 'vx lock'[0m

  [38;2;203;213;225mtasks.build.exec.command: "mkdir -p dist && cp src/main.js dist/main.js" → "mkdir -p dist && cp src/main.js dist/app.js"[0m
```

Look at the second line: the old command, then the new one. Run `vx lock` to take it.

### A task came from the cache after you changed a file

That file is not in `inputs.files`: add it. To catch the next one,
[`exec.sandbox`](../../docs/sandboxing/), with reads granted no wider
than the inputs, refuses that read and names the file.

### A task ran again and you do not know why

`vx why <project#task>` names the file that changed
([Find why a task missed the cache](../caching/why-a-task-missed/)).
Name one project when the task is in several:

```ansi title="vx why build"
[38;2;239;68;68m✗[0m [1mvx why[0m  [38;2;203;213;225m"build" ran in 2 projects — pick one[0m

  [38;2;203;213;225m@demo/ui#build[0m
  [38;2;203;213;225m@demo/web#build[0m
```

<Takeaway>fix a run that went wrong without an error: sync the lock, widen the inputs, ask `vx why`.</Takeaway>

<Deeper level="patterns" title="More surprises, and the fix">

- **Only one package ran.** With no flag, `vx run build` runs the
  package you are in, plus what it depends on. Add `--all` for every
  package.
- **A task runs every time.** It needs `cache: true`. If it has that, a
  task it depends on may have no `inputs`: give that task `inputs` too.
  `vx-migrate` leaves a `TODO(vx-migrate)` where it could not decide.
- **`inputs matched no files`.** The globs find nothing. Paths are
  relative to the project's folder: fix them.
- **`outputs matched no files`.** The command never wrote a path its
  `outputs.files` names, or wrote no output at all, so the task fails and
  nothing is saved. Point the pattern at what the command writes
  ([Cache a task](../caching/cache-a-task/)).
- **The run did not stop at the first failure.** By default a failure
  stops only the tasks that wait for it. Add `--fail-fast`
  ([guide](../running/stop-at-the-first-failure/)).
- **`not ready after …: waiting for a line matching`.** A dev server has
  not printed its `readyWhen` line. Fix the pattern, or set
  `exec.timeout` to stop waiting.
- **A variable is empty inside the command.** Past a small essential
  allowlist (`PATH`, `HOME`, `CI` and a few more), vx passes only what
  you list. Add the name to `exec.env.passThrough`
  ([Environment variables](../../docs/environment-variables/)).
- **`dist/` is empty after a build tool's incremental run.** Its state
  file sits outside `dist/`, so it thinks the build is done. Add that
  file to `outputs.files`, or move it inside `dist/`.
- **The editor cannot find `@vzn/vx`.** Add it as a devDependency. vx
  runs a config without it.
- **A package has no `vx.config.ts`.** It gets a default `build` that
  only waits for its dependencies' builds. Its files still count, so
  editing it re-runs the packages that use it.

<Takeaway>match a strange run to its cause in one read.</Takeaway>

</Deeper>

## Platforms

vx runs on Linux with glibc (not Alpine's musl) or macOS, in a git
repository (sha1 or sha256, files or reftable refs). The
release binary needs neither Node nor Bun.

<Tabs>
  <TabItem label="Linux">
    glibc, not Alpine's musl. The sandbox needs `bubblewrap`, `socat` and
    `ripgrep`.

    In a container, run as a user other than root, or set
    `exec.sandbox.weakerWhenNested: true` on each sandboxed task
    ([Sandboxing](../../docs/sandboxing/#requirements--platform-support)).
  </TabItem>
  <TabItem label="macOS">
    The sandbox is the system's own; nothing to install.
  </TabItem>
  <TabItem label="From source">
    Bun 1.4.4 or later.
  </TabItem>
</Tabs>

<Takeaway>check that your machine runs vx and its sandbox.</Takeaway>

## Known limits

- On macOS the sandbox's report can miss records under load. Enforcement
  holds.
- A cache hit replays the first and last 8 Mi characters (8 MiB of ASCII) of
  a task's output.
- A `kill -9` of vx leaves its persistent tasks running, except a server
  that exits when its stdin closes (esbuild `--watch`).
- A daemon a task starts with `setsid` and an empty environment
  (`env -i`) outlives Ctrl-C: vx finds a task's processes by a variable
  in their environment.

<Takeaway>know the few edges vx has, so none of them surprise you.</Takeaway>
