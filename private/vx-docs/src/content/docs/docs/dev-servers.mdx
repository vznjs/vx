<Concept term="Persistent task">
  A task that never exits by itself: a dev server, a watcher. vx starts it, keeps it up while other
  tasks need it, then stops it.
</Concept>

## Start a dev server

Add `persistent` to the task's `exec`. That tells vx not to wait for the command to exit.

```ts title="packages/web/vx.config.ts" mark={7}
import { defineProject } from '@vzn/vx/config'

export default defineProject({
  tasks: {
    dev: {
      dependsOn: ['^build'],
      exec: { command: 'vite --port 5173 --strictPort', persistent: { readyWhen: 'Local:' } },
      inputs: { files: ['src/**', 'index.html', 'vite.config.ts'] },
    },
  },
})
```

`vx run dev` builds `@demo/ui` first (`^build`), then starts `vite`. In a terminal, vx stays with the server until you press <kbd>Ctrl</kbd>+<kbd>C</kbd>.

<Aside type="caution" title="No cache on a server">
A server never exits, so there is nothing to store. `vx lock` refuses `cache: true` on it:

```ansi title="cache: true on dev"

[38;2;239;68;68m✗[0m [1mvx lock[0m  [38;2;203;213;225mlock not written[0m

  [1mvx.config.ts:8:7[0m
  [38;2;203;213;225mtasks.dev: [0m[1m`cache`[0m[38;2;203;213;225m is not allowed on a persistent task — persistent tasks don't terminate, so there's no exit to cache[0m

    6 |       dependsOn: ['^build'],
    7 |       exec: { command: 'vite --port 5173 --strictPort', persistent: { readyWhen: 'Local:' }, timeout: '30s' },

```
</Aside>

<Takeaway>run your dev server as a task, with its libraries built first.</Takeaway>

## Wait until it is ready

A server takes a moment to listen. `readyWhen` is a pattern vx looks for in each line the server prints. The first match means ready.

  A part of that line no other line has, such as `'Server listening'`. It is a regular expression,
  so `'listening at .*:3000'` works too.
</Quiz>

<Takeaway>make tasks wait for the server, and fail fast when it never comes up.</Takeaway>

## Check it while it runs

A task that needs the server lists it in `dependsOn`. vx starts the server, waits for ready, then runs the task.

```ts title="packages/web/vx.config.ts" mark={2-5}
dev: { /* as above */ },
smoke: {
  dependsOn: ['dev'],
  exec: { command: 'curl -sf http://localhost:5173/ -o /dev/null && echo "page served"' },
},
```

When the run ends, vx sends the server `SIGTERM`. A server still alive 2 seconds later gets `SIGKILL`.

<Takeaway>test against a live server in one command, with nothing left running after.</Takeaway>

## Keep it running while you edit

<Concept term="Watch mode">
  `vx watch` runs a task, then runs it again each time a file changes. A dev server stays up; only
  what changed is rebuilt.
</Concept>

```sh
vx watch dev
```

Edit `packages/ui/src/index.ts` and save:

<Deeper level="patterns" title="Common setups">

### End-to-end tests, cached

Playwright tests can be cached: their key holds the server's key, so an app edit runs them again.

```ts mark={8}
dev: {
  exec: { command: 'vite --port 5173 --strictPort', persistent: { readyWhen: 'Local:' }, timeout: '30s' },
  inputs: { files: ['src/**', 'index.html', 'vite.config.ts'] },
},
e2e: {
  dependsOn: ['dev'],
  exec: { command: 'playwright test' },
  cache: true,
  inputs: { files: ['e2e/**'] },
  outputs: { files: ['playwright-report/**'] },
},
```

On a hit, `e2e` restores its report. The server still starts: it shares the project and has no sandbox, so it could change what `e2e` reads.

### An API and a web app

Each server is its own task. The web server waits for the API, and the tests wait for both.

```ts
api: {
  exec: { command: 'bun --watch src/server.ts', persistent: { readyWhen: 'Listening on' } },
  inputs: { files: ['src/**'] },
},
dev: {
  dependsOn: ['api'],
  exec: { command: 'vite --port 5173 --strictPort', persistent: { readyWhen: 'Local:' } },
  inputs: { files: ['src/**', 'index.html', 'vite.config.ts'] },
},
e2e: {
  dependsOn: ['dev'],
  exec: { command: 'playwright test' },
},
```

### A server in the sandbox

On Linux a sandboxed server lists its port in `sandbox.allow.localBinding`. A sandboxed `e2e` reaches it with `network`:

```ts
dev: {
  exec: {
    command: 'vite --port 5173 --strictPort',
    persistent: { readyWhen: 'Local:' },
    sandbox: { allow: { read: ['.'], write: ['node_modules/.vite/'], localBinding: [5173] } },
  },
  inputs: { files: ['src/**', 'index.html', 'vite.config.ts'] },
},
e2e: {
  dependsOn: ['dev'],
  // Playwright removes its output directory, which a write grant cannot be.
  exec: {
    command: 'playwright test --output test-results/run',
    sandbox: { allow: { read: ['.'], write: ['test-results/'], network: ['localhost:5173'] } },
  },
  inputs: { files: ['e2e/**'] },
  outputs: { files: ['test-results/**'] },
  cache: true,
},
```

A fully cached `vx run e2e` starts no server here: the server may write only `node_modules/.vite/`, which no `e2e` input reads.

An unsandboxed server may write anywhere in its project, so a cached `e2e` beside it still starts it. From another project, it does not.

### A server that reads your keys

`vite` takes shortcuts in the terminal (`o` + <kbd>Enter</kbd> opens the browser). Mark it `interactive` and it gets the terminal:

```ts mark={2}
dev: {
  exec: { command: 'vite', persistent: {}, interactive: true },
},
```

vx reads none of its output, so it is ready once started: no `readyWhen`.

<Takeaway>wire servers, tests and watchers together the way your app needs.</Takeaway>

</Deeper>

<Deeper level="details" title="Every option">

### Task fields

| Field | What it does | Default | Example |
| --- | --- | --- | --- |
| `exec.persistent` | Starts the command without waiting for it to exit. Tasks that depend on it start once it is ready. | not persistent | `persistent: {}` |
| `exec.persistent.readyWhen` | A regular expression tested on each line of stdout and stderr. The first match makes the task ready. | ready when started | `readyWhen: 'Local:'` |
| `exec.timeout` | How long to wait for `readyWhen`. Past it, the server fails and is stopped. | the workspace's `run.timeout` | `timeout: '30s'` |
| `exec.interactive` | Gives the task the terminal: it reads your keys. It is ready once started. | `false` | `interactive: true` |
| `dependsOn` | A task that needs the server names it here. | none | `dependsOn: ['dev']` |
| `inputs.files` | Part of every dependent's key, so an app edit re-runs cached tests. In `vx watch`, it decides when a server only a dependent needs restarts. | none | `files: ['src/**']` |

### Workspace setting

| Field | What it does | Default | Example |
| --- | --- | --- | --- |
| `run.killGrace` | How long a server may take to exit after `SIGTERM` before vx sends `SIGKILL`. Also `VX_RUN_KILL_GRACE`. | `'2s'` | `run: { killGrace: '10s' }` |

### What a config may not say

A persistent task refuses `cache` and `retries`: it never exits, so there is no result to store or retry.

An `interactive` task refuses `readyWhen`, since vx reads none of its output. `vx lock` names the line, as above.

### What the run prints

| Status | Means |
| --- | --- |
| **running** | The server is ready and still up. |
| **still running** | In `vx watch`, a cycle kept the server from before. |
| **failed (never ready: timed out)** | No line matched `readyWhen` within `exec.timeout`. |
| **failed (never ready: exited)** | The server exited before a line matched, such as a port already in use. |

### How the run ends

- `vx run dev` keeps vx in the foreground until the server exits or you press <kbd>Ctrl</kbd>+<kbd>C</kbd> (exit code 130; 143 for a SIGTERM, 129 for a SIGHUP).
- When the server you asked for exits, vx stops the other servers and names its exit code.
- A failure elsewhere skips only its dependents. Healthy servers stay up; `--fail-fast` stops everything at once.
- At the end vx sends each server `SIGTERM`, then `SIGKILL` after `run.killGrace`.

### Servers in `vx watch`

- A server starts once and stays up across cycles. Each cycle rebuilds what it depends on.
- The server you asked for restarts only when its own config changed or it died.
- A server only a dependent needs restarts when its key changed. With no `inputs.files`, that is every cycle.
- The old server always stops first, so two never hold one port.
- A failed dependency stops the server; the next good cycle starts it again.

All of watch mode: [`vx watch`](../../cli/watch/).

</Deeper>

<Deeper level="details" title="When it goes wrong">

- **`not ready after 10 s: waiting for a line matching /…/`.** The
  server has not printed its `readyWhen` line yet. Fix the pattern, or
  set `exec.timeout` to stop waiting.
- **`not ready: no line matched readyWhen /…/ within 3s; killed`.** The
  wait passed the timeout the line names: the task's `exec.timeout`, or
  the run's (`--timeout`).

  Fix the pattern to match a line the server prints, or raise that
  timeout.
- **A server outlives a `kill -9` of vx.** Nothing runs after `kill -9`,
  except a server that exits when its stdin closes (esbuild `--watch`).
- **A daemon outlives Ctrl-C.** A daemon a task starts with `setsid` and an empty environment
  (`env -i`) outlives Ctrl-C: vx finds a task's processes by a variable
  in their environment.

</Deeper>
