With `vxHistory()` from `@vzn/vx-history`, vx starts the longest path of
dependent tasks first, so a run ends sooner.

To find that path, it needs to know how long each task took last time.
Your laptop remembers its own runs. A fresh CI runner remembers nothing.

`@vzn/vx-history-server` remembers for every runner. After each CI run,
vx sends it each task's time, the cores it kept busy and its peak memory.

The next run, on any runner, asks for those numbers before it starts.

<Aside>
  The history only decides the order tasks start in. A wrong or missing
  number never changes what runs or what is cached.
</Aside>

## Set it up

### 1. Deploy the server

<Tabs syncKey="server-host">
<TabItem label="Cloudflare Workers">

The numbers go in a D1 database.

```sh
mkdir vx-history-server && cd vx-history-server
bun add @vzn/vx-history-server
```

```jsonc title="wrangler.jsonc"
{
  "name": "vx-history-server",
  "main": "node_modules/@vzn/vx-history-server/src/worker.ts",
  "compatibility_date": "2026-10-01",
  "vars": { "ALLOW": "" },
  "d1_databases": [{ "binding": "DB", "database_name": "vx-history" }]
}
```

Fill `ALLOW` ([`ALLOW`](../#allow-who-takes-part)), then:

```sh
bunx wrangler login
bunx wrangler deploy
```

The first deploy creates the D1 database `vx-history`.

</TabItem>
<TabItem label="Bun">

The numbers go in one SQLite file:

```sh
ALLOW='https://token.actions.githubusercontent.com:acme/app:ci.yml' \
AUDIENCE=https://history.example.com \
bunx @vzn/vx-history-server --db vx-history.sqlite --port 8080
```

It prints the address it listens on, `vx-history-server on http://0.0.0.0:8080/`.

`--db` (default `vx-history.sqlite`), `--port` (default 8080) and
`--host` (default `0.0.0.0`) set the file and where it listens.

</TabItem>
<TabItem label="Docker">

```sh
docker run -p 8080:8080 -v vx-history:/data -e ALLOW='…' -e AUDIENCE=https://history.example.com ghcr.io/vznjs/vx-history-server
```

The database is `/data/vx-history.sqlite`, on the volume. Or run it
beside the other two servers with
[Docker Compose](../#all-three-with-docker-compose): the `history`
service, on port 8082.

</TabItem>
</Tabs>

Put HTTPS in front of it: a CI token is a bearer token.

### 2. Point vx at it

```sh
bun add -d @vzn/vx-history @vzn/vx-ci
```

```ts title=".vx/workspace.ts"
import { defineWorkspace } from '@vzn/vx/config'
import { github } from '@vzn/vx-ci'
import { vxHistory } from '@vzn/vx-history'

export default defineWorkspace({
  plugins: [
    github(), // on GitLab, gitlab()
    vxHistory({
      url: 'https://history.example.com', // or VX_HISTORY_URL
      issuer: 'https://token.actions.githubusercontent.com',
      repository: 'acme/app',
    }),
  ],
})
```

`url` is https (http only to `127.0.0.1`, `::1` or `localhost`). `issuer`
and `repository` must match your `ALLOW` entry. Run `vx lock`
and commit.

### 3. Let CI jobs prove who they are

<Tabs syncKey="ci">
<TabItem label="GitHub Actions">

```yaml title=".github/workflows/ci.yml"
permissions:
  contents: read
  id-token: write
```

</TabItem>
<TabItem label="GitLab CI">

```yaml title=".gitlab-ci.yml"
vx:
  id_tokens:
    VX_HISTORY_TOKEN:
      aud: https://history.example.com
```

</TabItem>
</Tabs>

Then push. vx prints nothing about the history when it works. When the
server refuses, it says so once, in the server's words, and the run
orders its tasks as it would without one.

## How a run uses it

- **At the start**, it asks for the numbers of its tasks: its own
  branch's first, then the branch it merges into, then the default
  branch's. It does not wait for them: it starts on what this machine
  knows and re-orders the waiting tasks when they arrive.
- **At the end**, it sends the numbers of the tasks it ran, once. With
  [distributed task execution](../../distributed-task-execution/), the
  run that hands out the tasks sends them, with each worker's measurements.
- **Off CI** there is no token. A run then reads from a server with
  `READ_ACCESS=public`, and sends nothing.

A task's numbers belong to its command and `env.define`. Change the
command and the task starts fresh. Change its inputs or dependencies
and it keeps them.

`vxHistory()` also works with no server, from this machine's history
alone, or from a file a CI cache carries between runs.

Those options, and `assume` for tasks it has never seen, are on its
[reference page](../../../plugins/vx-history/).

## Settings

| Setting | Default | What it sets |
| --- | --- | --- |
| `ALLOW` | empty: refuse every request | who takes part, each `issuer:owner/repo:workflow` ([`ALLOW`](../#allow-who-takes-part)) |
| `READ_ACCESS` | unset: every request needs a CI token | `public`: a request with no token reads a repository `ALLOW` names, and writes nothing |
| `AUDIENCE` | Workers: the URL it is reached at. Bun and Docker: required | the `aud` a CI token must name |
| `TIMING_DAYS` | 30 | days a task's row is kept after its last report |

On Workers, each setting is a var in `wrangler.jsonc`.

## What it keeps

One row per issuer, repository, branch and task hash, stored as they
are, so the table reads plainly. Each report updates the row:

- `durationMs` and `cores`: `old × 0.7 + new × 0.3`. A task that got
  slower is followed within about three runs, and one odd run moves it
  30%.
- `rssBytes`: `max(new, old × 0.9)`. Planning needs the peak, and the
  decay lets a task that shrank come down.
- `runs`: how many reports made the row.

It keeps no log, no list of runs and no raw samples. A row not reported
for `TIMING_DAYS` is deleted by the first upload of each day.

## API

All under `/v1`
([PROTOCOL.md](https://github.com/vznjs/vx/blob/main/packages/vx-history-server/PROTOCOL.md)):

| Route | Does |
| --- | --- |
| `POST /v1/timings/upload` | `{ timings: [{ hash, durationMs, cores?, rssBytes? }] }`, up to 10 000, each added to the token's branch's row; `204` |
| `POST /v1/timings/query` | `{ issuer, repository, refs, hashes }`, 1 to 8 refs and up to 10 000 hashes: each hash's row in the first ref that holds one |
| `GET /v1/capabilities` | `{ maxUploadTimings, maxQueryHashes, maxQueryRefs }` |

A run asks once, with every hash. A query answers
`{ timings: { <hash>: { durationMs, cores, rssBytes, runs } } }`; a hash
no ref holds is left out. Every refusal is `{ code, message }`.

To mount it in a server of your own:

- `createHistoryServer({ store, authorize, timingDays? })` returns a
  `fetch` handler;
- `sqliteStore(db)` keeps the rows in any SQLite that `bun:sqlite` or D1
  serves.

The [README](https://github.com/vznjs/vx/tree/main/packages/vx-history-server#api)
lists the whole API.
