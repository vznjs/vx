A fresh CI runner remembers no earlier run. The history server remembers for all of them, so each run starts its longest tasks first.

```sh
bunx @vzn/vx-history-server --db vx-history.sqlite --port 8080
```

<Levels />

<Diagram {...historyLoop} />

<Concept term="Critical path">
  The longest line of tasks that wait on each other. A run can end no sooner than it, so vx starts
  it first. To find it, vx needs each task's time.
</Concept>

<Aside>
  History changes when tasks start and whether a flaky task is retried. A wrong or missing number
  never changes a task's result or what is cached.
</Aside>

## Deploy it

<Tabs syncKey="server-host">
<TabItem label="Cloudflare Workers">

The numbers go in a D1 database.

```sh
mkdir vx-history-server && cd vx-history-server
bun add @vzn/vx-history-server
```

```jsonc title="wrangler.jsonc"
{
  "name": "vx-history-server",
  "main": "node_modules/@vzn/vx-history-server/src/worker.ts",
  "compatibility_date": "2026-10-01",
  "vars": { "ALLOW": "https://token.actions.githubusercontent.com:acme/app:ci.yml" },
  "d1_databases": [{ "binding": "DB", "database_name": "vx-history" }]
}
```

```sh
bunx wrangler login
bunx wrangler deploy
```

The first deploy creates the D1 database `vx-history`. It fits Cloudflare's free plan.

</TabItem>
<TabItem label="Bun">

The numbers go in one SQLite file:

```sh
ALLOW='https://token.actions.githubusercontent.com:acme/app:ci.yml' \
AUDIENCE=https://history.example.com \
bunx @vzn/vx-history-server --db vx-history.sqlite --port 8080
```

```ansi
[38;2;34;197;94m✓[0m [1mvx-history-server[0m  listening on [38;2;6;182;212mhttp://0.0.0.0:8080/[0m
```

The green line means it is up.

</TabItem>
<TabItem label="Docker">

```sh
docker run -p 8080:8080 -v vx-history:/data -e ALLOW='…' -e AUDIENCE=https://history.example.com ghcr.io/vznjs/vx-history-server
```

The database is `/data/vx-history.sqlite`, on the volume. Or run it beside the other two with [Docker Compose](../#run-all-three-with-docker-compose): the `history` service, on port 8082.

</TabItem>
</Tabs>

Check it answers:

```sh
curl http://localhost:8080/v1/capabilities   # Workers: your workers.dev URL
```

```json
{"maxUploadTimings":10000,"maxQueryHashes":10000,"maxQueryRefs":8}
```

Those are its limits: the server is up. Put HTTPS in front of it.

## Point vx at it

<Steps>

1. Add the plugins:

   ```sh
   bun add -d @vzn/vx-history @vzn/vx-ci
   ```

2. Name the server in `.vx/workspace.ts`:

   ```ts title=".vx/workspace.ts" ins={3,8-12}
   import { defineWorkspace } from '@vzn/vx/config'
   import { github } from '@vzn/vx-ci'
   import { vxHistory } from '@vzn/vx-history'

   export default defineWorkspace({
     plugins: [
       github(), // on GitLab, gitlab()
       vxHistory({
         url: 'https://history.example.com',
         issuer: 'https://token.actions.githubusercontent.com',
         repository: 'acme/app',
       }),
     ],
   })
   ```

3. Let each CI job ask for its token:

   <Tabs syncKey="ci">
   <TabItem label="GitHub Actions">

   ```yaml title=".github/workflows/ci.yml"
   permissions:
     contents: read
     id-token: write
   ```

   </TabItem>
   <TabItem label="GitLab CI">

   ```yaml title=".gitlab-ci.yml"
   vx:
     id_tokens:
       VX_HISTORY_TOKEN:
         aud: https://history.example.com
   ```

   </TabItem>
   </Tabs>

4. Run `vx lock`, commit and push.

</Steps>

vx prints nothing about the history when it works. When the server refuses, vx says so once, in the server's words, and orders tasks as it would without one.

`issuer` and `repository` must match your `ALLOW` entry. Every `vxHistory()` option, and how it works with no server, is on [its page](../../../plugins/vx-history/).

<Takeaway>give every CI runner the timings of the runs before it.</Takeaway>

## How a run uses it

- **At the start**, it asks for its tasks' numbers: its own branch's first, then the branch it merges into, then the default branch's. It does not wait: it starts on what it knows and re-orders when they arrive.
- **At the end**, it sends the numbers of the tasks it ran, once.
- **Off CI**, there is no token. A run reads from a server with `READ_ACCESS=public` and sends nothing.

<Quiz q="You add a file to @demo/ui's inputs. Does @demo/ui#build lose its history?">
  No. A task's numbers belong to its command and `env.define`. Inputs and dependencies can change;
  a new command starts fresh.
</Quiz>

<Takeaway>know when the history is read, written and reset.</Takeaway>

<Deeper level="patterns" title="Common setups">

### Laptops order by CI's times

Set `READ_ACCESS=public` on the server. A laptop reads CI's timings and never sends its own.

<Takeaway>order local runs by what CI measured.</Takeaway>

### Distributed task execution

The run that hands out the tasks sends the numbers, with each worker's measurements. Workers send nothing themselves.

<Takeaway>keep one history for runs spread over many machines.</Takeaway>

### Keep rows longer

A task that runs rarely, such as a weekly release, can outlive the 30-day default. Raise it:

```sh
TIMING_DAYS=90
```

<Takeaway>keep timings for tasks that run less than once a month.</Takeaway>

</Deeper>

<Deeper level="details" title="Every setting, what it keeps, the API">

### Server settings

| Setting | Default | What it does | Example |
| --- | --- | --- | --- |
| `ALLOW` | required | who takes part ([`ALLOW`](../#say-who-takes-part-allow)) | `https://token.actions.githubusercontent.com:acme/app:ci.yml` |
| `AUDIENCE` | Workers: the URL it is reached at. Bun and Docker: required | the `aud` a CI token must name, read as its origin | `https://history.example.com` |
| `READ_ACCESS` | unset: every request needs a token | `public`: a request with no token reads a repository `ALLOW` names | `public` |
| `TIMING_DAYS` | 30 | whole days a row is kept after its last report | `90` |
| `DB` | | Workers: the D1 database binding | `vx-history` |
| `--db` | `vx-history.sqlite` | Bun: the SQLite file | `--db /var/lib/vx-history.sqlite` |
| `--port` | 8080 | Bun: the port it listens on | `--port 9000` |
| `--host` | `0.0.0.0` | Bun: the address it listens on | `--host 127.0.0.1` |

A bad value stops the Bun server before it listens:

```ansi title="TIMING_DAYS=0"
[38;2;239;68;68m✗[0m [1mvx-history-server[0m  TIMING_DAYS: a whole number of days, got 0
```

### What it keeps

One row per issuer, repository, branch and task, stored plainly. Each report updates the row:

| Number | Update | Why |
| --- | --- | --- |
| `durationMs`, `cores` | `old × 0.7 + new × 0.3` | follows a task that got slower within about three runs; one odd run moves it 30% |
| `rssBytes` | `max(new, old × 0.9)` | planning needs the peak; the decay lets a task that shrank come down |
| `slowMs` | `max(new, old × 0.9)` of the duration | how slow a task gets, which the average hides |
| `runs` | `+ 1` | how many reports made the row |

A report that would move the row under 5%, with no new memory peak, is not written, unless the row is a day old.

It also keeps a **flaky record** per repository: only the cache keys that failed, each marked flaky once it passed on a retry or a later run. A run retries a task that flaked on another machine.

It keeps no log, no list of runs and no raw samples. A row or key not reported for `TIMING_DAYS` is deleted by the first upload of each day.

### API

All under `/v1` ([PROTOCOL.md](https://github.com/vznjs/vx/blob/main/packages/vx-history-server/PROTOCOL.md)):

| Route | Does |
| --- | --- |
| `POST /v1/timings/upload` | `{ timings: [{ hash, durationMs, cores?, rssBytes? }], outcomes?: [{ hash, key, outcome }] }`, up to 10 000 each, into the token's branch; `204` |
| `POST /v1/timings/query` | `{ issuer, repository, refs, hashes }`, 1 to 8 refs and up to 10 000 hashes: each hash's row in the first ref holding one, and the flaky ones |
| `GET /v1/capabilities` | `{ maxUploadTimings, maxQueryHashes, maxQueryRefs }`, also sent as `vx-max-*` headers on every answer |

A query answers `{ timings: { <hash>: { durationMs, cores, rssBytes, slowMs, runs } }, flaky: [<hash>] }`. Every refusal is `{ code, message }`:

```json
{"code":"forbidden","message":"acme/other is not in this server's ALLOW"}
```

To mount it in your own server, `createHistoryServer({ store, authorize, timingDays? })` returns a `fetch` handler, and `sqliteStore(db)` keeps the rows in any SQLite that `bun:sqlite` or D1 serves.

The [README](https://github.com/vznjs/vx/tree/main/packages/vx-history-server#api) lists the whole API.

</Deeper>
