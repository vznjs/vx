`@vzn/vx-cache-server` is the remote cache you host. `vxCache()` from
`@vzn/vx-cache` points vx at it.

It keeps task results in one bucket, Cloudflare R2 or any S3 bucket, and
nothing else: no database, and no state on the server itself.

[Remote cache](../../remote-cache/) walks through the whole setup on
Cloudflare. This page is the reference: every way to host it, every
setting, and how it stores results.

## Deploy

<Tabs syncKey="server-host">
<TabItem label="Cloudflare Workers">

Results go in R2.

```sh
mkdir vx-cache-server && cd vx-cache-server
bun add @vzn/vx-cache-server
```

```jsonc title="wrangler.jsonc"
{
  "name": "vx-cache-server",
  "main": "node_modules/@vzn/vx-cache-server/src/worker.ts",
  "compatibility_date": "2026-10-01",
  "vars": { "ALLOW": "" },
  "r2_buckets": [{ "binding": "BLOBS", "bucket_name": "vx-cache" }]
}
```

Fill `ALLOW` ([`ALLOW`](../#allow-who-takes-part)), then:

```sh
bunx wrangler login
bunx wrangler deploy
```

The first deploy creates the R2 bucket `vx-cache`. Each setting below
is a var in `wrangler.jsonc`.

</TabItem>
<TabItem label="Bun">

Results go in any S3-compatible bucket:

```sh
ALLOW='https://token.actions.githubusercontent.com:acme/app:ci.yml' \
AUDIENCE=https://cache.example.com \
S3_BUCKET=vx-cache S3_ENDPOINT=https://s3.example.com \
S3_ACCESS_KEY_ID=… S3_SECRET_ACCESS_KEY=… \
bunx @vzn/vx-cache-server --port 8080
```

```ansi
[38;2;34;197;94m✓[0m [1mvx-cache-server[0m  listening on [38;2;6;182;212mhttp://0.0.0.0:8080/[0m
```

`--port` (default 8080) and `--host` (default `0.0.0.0`) set it.

A server keeps no state of its own, so you can run as many as you like
over one bucket, behind a load balancer.

</TabItem>
<TabItem label="Docker">

```sh
docker run -p 8080:8080 -e ALLOW='…' -e AUDIENCE=https://cache.example.com -e S3_BUCKET=… -e S3_ENDPOINT=… \
  -e S3_ACCESS_KEY_ID=… -e S3_SECRET_ACCESS_KEY=… ghcr.io/vznjs/vx-cache-server
```

Or run it beside the other two servers with
[Docker Compose](../#all-three-with-docker-compose): the `cache`
service, on port 8081.

</TabItem>
</Tabs>

Put HTTPS in front of it: a CI token is a bearer token.

To check it answers, ask for its limits:

```sh
curl https://cache.example.com/v1/capabilities
```

```json
{"code":"bad_request","message":"vx-issuer and vx-repository: the issuer's and the repository's hashes (PROTOCOL.md § Keys)"}
```

That refusal means it is up and has an `ALLOW`. A Worker with `ALLOW`
empty says `ALLOW is empty: set it to the CI workflows this server
serves` instead.

The Bun server and its image do not start without an `ALLOW`.

## Settings

| Setting | Default | What it sets |
| --- | --- | --- |
| `ALLOW` | required (a Worker without it refuses every request) | who takes part, each `issuer:owner/repo:workflow` ([`ALLOW`](../#allow-who-takes-part)) |
| `READ_ACCESS` | unset: every request needs a CI token | `public`: a request with no token, such as a laptop's, reads a repository `ALLOW` names, and writes nothing |
| `AUDIENCE` | Workers: the URL it is reached at. Bun and Docker: required | the `aud` a CI token must name |
| `S3_BUCKET`, `S3_ENDPOINT`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | | the bucket (Bun and Docker), as Bun's S3 client reads them |
| `MAX_CHECK_HASHES` | 500 (6 on Workers) | how many lookups one check may make |
| `MAX_UPLOAD_BYTES` | 100 MB | the largest result it takes |

vx asks the server for its limits once per run and stays within them.
On Workers each lookup is one subrequest, so a higher
`MAX_CHECK_HASHES` must fit your Cloudflare plan.

## Point vx at it: `vxCache()`

```sh
bun add -d @vzn/vx-cache @vzn/vx-ci
```

```ts title=".vx/workspace.ts"
import { defineWorkspace } from '@vzn/vx/config'
import { vxCache } from '@vzn/vx-cache'
import { github } from '@vzn/vx-ci'

export default defineWorkspace({
  plugins: [
    github(),
    vxCache({
      url: 'https://cache.example.com', // or VX_CACHE_URL
      issuer: 'https://token.actions.githubusercontent.com',
      repository: 'acme/app',
    }),
  ],
})
```

| Option | Default | What it sets |
| --- | --- | --- |
| `url` | `VX_CACHE_URL` | the server's URL: https, http only to `127.0.0.1`, `::1` or `localhost`; a redirect is not followed |
| `issuer` | required | your CI's token issuer: `https://token.actions.githubusercontent.com`, `https://gitlab.com` or your GitLab's URL |
| `repository` | required | the repository, `org/name`, as `ALLOW` names it |
| `timeoutMs` | 30 000 | how long one read or check may take, in ms (above 0, up to 2³¹−1) |
| `uploadTimeoutMs` | 60 000 | how long one upload may take, in ms (above 0, up to 2³¹−1) |
| `headers` | none | headers sent on every request, for a proxy in front of the server |

`github()` or `gitlab()` from `@vzn/vx-ci` tells the cache which branch
a CI run is on. Without one, a CI run reads only the checked-out branch
and the default branch.

For a proxy such as Cloudflare Access, pass its service token:

```ts
vxCache({
  url: 'https://cache.example.com',
  issuer: 'https://token.actions.githubusercontent.com',
  repository: 'acme/app',
  headers: {
    'CF-Access-Client-Id': process.env.CF_ACCESS_CLIENT_ID,
    'CF-Access-Client-Secret': process.env.CF_ACCESS_CLIENT_SECRET,
  },
})
```

An unset value is left out. The `authorization` header stays the CI
token's.

The workers of a [distributed task execution](../../distributed-task-execution/)
run send the headers too, so give their job the same secrets.

### Tokens

Each CI job needs a token for the server's URL:

<Tabs syncKey="ci">
<TabItem label="GitHub Actions">

```yaml title=".github/workflows/ci.yml"
permissions:
  contents: read
  id-token: write
```

vx asks GitHub for the token and asks again before it expires. A job
without `id-token: write` warns and only reads.

</TabItem>
<TabItem label="GitLab CI">

```yaml title=".gitlab-ci.yml"
vx:
  id_tokens:
    VX_CACHE_TOKEN:
      aud: https://cache.example.com
```

</TabItem>
</Tabs>

Off CI there is no token. A run then reads from a server with
`READ_ACCESS=public` and uploads nothing.

Any other server refuses the first read. vx says so once, and the run
goes on with its local cache. A refused write turns off uploads only.

With [distributed task execution](../../distributed-task-execution/),
the run lends its token to its workers, so they read and write where the
run does.

## Expiry

The server never deletes anything. Give the bucket a lifecycle rule
that deletes results by age instead. On R2, one day:

```sh
bunx wrangler r2 bucket lifecycle add vx-cache all '' --expire-days 1
```

On S3, put the same rule in the bucket's lifecycle configuration. A run
that misses an expired result runs the task and stores it again.

## How it stores results

A result's name in the bucket is
`<hash(issuer)>/<hash(repository)>/<hash(branch)>/<key>`.

Each hash is the first 128 bits of a SHA-256, in hex, so the bucket
names no repository and no branch. One repository never reads another's
results.

A result is never rewritten: a second upload of the same key keeps the
first bytes.

A download through Workers goes through Cloudflare's cache: after R2
serves a result once, that data center answers it without R2.

An upload of a result R2 expired drops the copy in the data center it
reaches.

Whether a result exists is asked of R2 alone, so every data center agrees.

## API

Turbo's routes under `/v1`, each read naming the branches it reads
([PROTOCOL.md](https://github.com/vznjs/vx/blob/main/packages/vx-cache-server/PROTOCOL.md)):

| Route | Does |
| --- | --- |
| `GET /v1/artifacts/<hash>` | one result's bytes, its branch in `vx-scope` |
| `HEAD /v1/artifacts/<hash>` | whether a branch holds it, and its size |
| `PUT /v1/artifacts/<hash>` | one result's bytes, to the token's branch |
| `POST /v1/artifacts` | `{ hashes, scopes }`: each hash's size and the first branch holding it |
| `GET /v1/capabilities` | the limits |

A branch on the wire is its hash, the first 128 bits of the ref's
SHA-256 as 32 lowercase hex characters (`refs/heads/main` is
`f921bd05e68b03740c450e565e0e6173`). A plain ref is refused with `400`.

Any server that speaks the protocol can stand in for this one.

To mount it in a server of your own, `createCacheServer({ blobs, authorize, limits? })`
returns a `fetch` handler over your bucket.

The [README](https://github.com/vznjs/vx/tree/main/packages/vx-cache-server#api)
lists the whole API.
