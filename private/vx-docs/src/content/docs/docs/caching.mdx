Run a build twice. The second time, vx does no work: it puts back what the first run made.

```sh
vx run build
vx run build
```

<Concept term="Cache">
  A store of task results that vx keeps in `.vx/cache`. When a task has run before with the same
  inputs, vx copies the result from here instead of running it.
</Concept>

## Turn it on

Tell vx three things about the task: what it **reads** (`inputs`), what it **writes** (`outputs`), and `cache: true`.

```ts title="packages/app/vx.config.ts" mark={8-14}
import { defineProject } from '@vzn/vx/config'

export default defineProject({
  tasks: {
    build: {
      dependsOn: ['^build'],
      exec: { command: 'vite build' },
      inputs: {
        files: ['src/**', 'index.html'],
      },
      outputs: {
        files: ['dist/**'],
      },
      cache: true,
    },
  },
})
```

<Takeaway>cache any task: list what it reads and writes, add `cache: true`.</Takeaway>

## How vx decides

<Concept term="Cache key">
  A short code vx computes from everything a task reads: its files, its config and the keys of the
  tasks it depends on. Same inputs, same key.
</Concept>

<Diagram {...cacheKey} />

Before running a task, vx computes its key. A key it has stored is a **hit**: vx restores the outputs. A new key is a **miss**: the task runs, then vx stores its outputs.

<Quiz q="You edit README.md, which the build does not list in inputs. Does the build run again?">
  No. The key holds only what the task lists, so the key stays the same and the build is a hit. If
  the build does read that file, add it to `inputs.files`.
</Quiz>

<Takeaway>predict when a task runs and when it is skipped.</Takeaway>

<Deeper level="patterns" title="Common setups">

### A file at the workspace root

A task that reads a shared file outside its project lists it under `workspaceFiles`:

```ts mark={3}
inputs: {
  files: ['src/**', 'index.html'],
  workspaceFiles: ['tsconfig.base.json'], // from the workspace root
},
```

### An environment variable

A task whose result depends on a variable keys on it with `inputs.env` and passes it with `exec.env`:

```ts mark={1,4}
exec: { command: 'vite build', env: { passThrough: ['NODE_ENV'] } },
inputs: {
  files: ['src/**'],
  env: ['NODE_ENV'],
},
```

### Tests and lint: nothing to store

A task that writes no files still caches its pass. Give it an empty output list:

```ts mark={3}
test: {
  exec: { command: 'vitest run' },
  inputs: { files: ['src/**'] },
  outputs: { files: [] },
  cache: true,
},
```

<Aside type="tip" title="Not sure the list is complete?">
  Add [`exec.sandbox`](../../docs/sandboxing/) with `allow.read` listing the same
  files. A workspace read outside it fails the task and names the file.
</Aside>

<Takeaway>cache builds that read shared files and variables, and tests that write nothing.</Takeaway>

</Deeper>

<Deeper level="details" title="What the key holds">

A task with no `cache: true` is keyed on its `inputs` all the same, so a
cached task behind it re-runs when they change. One that declares no
`inputs` has no key, and every task behind it misses.

| The key                | Holds                                                                                   |
| ---------------------- | --------------------------------------------------------------------------------------- |
| Always in it           | the keys of the tasks it depends on, the task's config, arguments after `--` |
| In, with a lockfile plugin | the package's `package.json` and its own dependencies from the lockfile ([Lockfiles](../lockfiles/)) |
| Always excluded        | an untracked `node_modules` git does not ignore (an install), `.git`, `.vx/cache`, `.vx/projects.lock`, `vx.lock.json`, `.vx/.gitattributes`, `.vx/.gitignore`, `.vx/dependencies.lock`, `.vx/tmp` (restore staging), the temps a killed write leaves (`.vx/projects.lock.tmp-*`, `.vx/dependencies.lock.tmp-*`, `vx.lock.json.tmp-*`), each at the project's root only, the task's own outputs, except a file git tracks (a committed output stays in the key: by what git holds while its bytes are ones a build keyed by that version left on this machine, and a miss writes git's version back first, so a build that rewrites it with new bytes each time still hits; a hand edit keys by its bytes), a nested project's files |
| Excluded unless named  | files git ignores, an ignored `node_modules` included: a broad glob like `src/**` skips them, an exact path or a glob whose fixed part git ignores (`.env.local`, `node_modules/.prisma/client/**`) keys them |
| In, when you say so    | a tool's version: `inputs.workspaceRuntime: ['node -v']` runs once per run at the root and adds its output to the key; `runtime` runs in the package |
| Out, when you say so   | a dependency only for order: `inputs.tasks: []`, as the [dev task](../dev-servers/) does |

Every part, in order: [Caching in depth](../../caching/).

</Deeper>

<Deeper level="details" title="What happens to outputs">

- Declared outputs are wiped before every run that writes the cache.
- A hit rewrites only the files that differ from the entry, then removes
  the ones it does not hold, so `dist/` ends as the cache stored it. A
  hit that finds them already as stored writes nothing.
- A restore writes only files the task's `outputs` declare.
- Every output named by path must be written, and at least one output
  must match; a wildcard may match nothing beside one that did. Otherwise
  the task fails once the command exits 0, and nothing is saved
  ([fix](../../docs/troubleshooting/)).

  ```ansi title="outputs: { files: ['build/index.js'] }, but vite writes dist/"
  [2m┌─[0m [1m[38;2;192;132;252m@demo/ui[0m[2m#[0m[1m[38;2;244;114;182mbuild[0m [2m>[0m $ vite build
  [36mvite v7.1.5 [32mbuilding for production...[36m[39m
  transforming...
  [32m✓[39m 1 modules transformed.
  rendering chunks...
  computing gzip size...
  [2mdist/[22m[36mindex.js  [39m[1m[2m0.06 kB[22m[1m[22m[2m │ gzip: 0.08 kB[22m
  [32m✓ built in 44ms[39m
  [0m[1m[38;2;234;179;8m[vx][0m[2m @demo/ui#build: outputs matched no files (build/index.js) — the command exited 0 but never wrote it, so the task fails and nothing is cached: write it, or fix the pattern[0m
  [2m└─[0m [1m[38;2;192;132;252m@demo/ui[0m[2m#[0m[1m[38;2;244;114;182mbuild[0m [2m──[0m [2m(1.64s)[0m [1m[38;2;239;68;68mfailed (exited 0, no file matched build/index.js)[0m
  ```

- A failed task is never saved.
- `--force` runs everything and replaces what the local cache holds (a remote keeps the keys it has); `--no-cache` ignores it.

</Deeper>

<Deeper level="details" title="Every verdict vx why prints">

| The verdict line says | It means |
| --- | --- |
| `cache key changed: env MODE, file packages/app/src/index.ts` | those inputs moved (three named, then a count); the lines below show each |
| `cache key changed between the previous run and this one (inputs differ)` | the key moved and neither entry kept its components (pruned, or a failed run saved none) |
| `` never cached: this task declares no `inputs`, so each run derives a new key; declare its `inputs` `` | the task itself declares no `inputs`, so its key is new every run |
| `` never cached: its key includes //#stamp, which declares no `inputs`, so each run derives a new key; declare inputs on //#stamp `` | a task this key includes declares no `inputs`, so the key is new every run; declare them on that task |
| `cache key unchanged — this run was served from cache, nothing re-ran` | a hit |
| `cache key unchanged — the previous run on this key failed and saved nothing, so there was nothing to hit` | a failure saves no entry |
| `cache key unchanged — re-executed because this run did not read the cache (--force, or a --cache-policy without read)` | the run's policy read no cache |
| `cache key unchanged — re-executed because this run did not use the cache (--no-cache, or a --cache-policy without read or write)` | the run used no cache |
| `cache key unchanged — the previous run on this key did not save its result (…), so there was nothing to hit` | the previous run withheld its save and said why (an input edited while it ran) |
| `cache key unchanged — no entry for this key was in the cache when it ran (pruned or evicted), so it executed and saved one` | the entry was gone |
| `cache key unchanged — the previous run on this key executed but no entry for it is in the cache (its save failed, or it was pruned since), so there was nothing to hit` | the previous run's save failed, or a prune took the entry |
| `cache key unchanged — the previous run on this key built on a dependency it left out (…), so it saved nothing and there was nothing to hit` | the previous run left that dependency out, and saves nothing built on one |
| `cache key unchanged — the previous run on this key did not write the cache (--no-cache, or a --cache-policy without write), so there was nothing to hit` | the previous run's policy wrote no cache |
| `cache key unchanged — re-executed on the same key though this run read the cache; vx cannot name the cause` | none of the above; vx cannot name the cause |
| `cache key unchanged — re-executed on the same key (--no-cache / --force, or unrelated)` | no invocation recorded this run's cache policy, so vx cannot rule the flags out |
| `cache key unchanged — this run recorded no cache outcome, so whether it re-ran is unknown` | vx does not guess |
| `` this task declares no `cache: true` — it runs on every invocation; a change to its inputs still re-runs the tasks that depend on it `` | not cached at all |
| `` this task declares no `cache: true` — it runs on every invocation; it declares no `inputs` either, so each run derives a new key and every task that depends on it misses; declare its `inputs` (and `outputs` with `cache: true` to cache it too) `` | not cached, and no task depending on it can hit |
| `this task was skipped: it needs another platform, so it recorded no cache key` | it waits for a worker of that platform |
| `this task never ran: … did not pass, so it recorded no cache key` | a task it depends on failed or was skipped |
| ``this task's cache key could not be derived, so its command never ran (…)`` | the line names the `vx last` command that shows why |
| `this task hit the cache and its restore failed, so it recorded no cache key` | the restore was refused or failed; the line in its log says why |
| `this task is persistent: it records no cache key` | a server or watcher has no key to compare |
| `no prior run for this (project, task)` | nothing to compare with yet |

</Deeper>
