```sh

```

<Concept term="Cache">
  A store of task results that vx keeps on your machine. When a task has run before with the same
  inputs, vx copies the result from here instead of running it.
</Concept>

## Turn it on

Tell vx three things about the task: what it **reads**, what it **writes**, and `cache: true`.

```ts title="packages/ui/vx.config.ts" mark={7-9}
import { defineProject } from '@vzn/vx/config'

export default defineProject({
  tasks: {
    build: {
      exec: { command: 'vite build' },
      inputs: { files: ['src/**', 'vite.config.ts'] },
      outputs: { files: ['dist/**'] },
      cache: true,
    },
  },
})
```

| Line | Tells vx | vx uses it to |
| --- | --- | --- |
| `inputs.files` | the files the command **reads** | build the task's key |
| `outputs.files` | the files the command **writes** | store them, and put them back |
| `cache: true` | remember this task | skip it on a key it stored |

Globs start at the project's folder: `src/**` is `packages/ui/src/**`.

<Concept term="Lock">
  What `vx lock` writes: `.vx/projects.lock` and a `vx.lock.json` beside each config. Every run reads
  them instead of your configs, so run `vx lock` after each config change and commit them.
</Concept>

```sh
vx lock
```

<Takeaway>cache any task: list what it reads and writes, add `cache: true`, run `vx lock`.</Takeaway>

## Outputs must exist

Declared outputs are a promise. When the command ends:

- a plain path, like `dist/index.js`, **must exist**;
- a path with a trailing slash, like `dist/`, must be a folder;
- a wildcard, like `coverage/**`, may match nothing;
- but **at least one** declared output must exist.

Here the config says `dist/main.js`, but vite writes `dist/index.js`:

```sh
vx run @demo/ui#build
```

<Deeper level="patterns" title="Common setups">

### Lint and tests: nothing to store

A task that writes no files still caches its pass. Give it an empty `outputs.files`:

```ts title="packages/ui/vx.config.ts" mark={4}
lint: {
  exec: { command: 'oxlint src' },
  inputs: { files: ['src/**'] },
  outputs: { files: [] },
  cache: true,
},
```

```ansi
[2m$[0m vx run @demo/ui#lint

[2m┌─[0m [1m[38;2;192;132;252m@demo/ui[0m[2m#[0m[1m[38;2;232;121;249mlint[0m [2m>[0m $ oxlint src
Found 0 warnings and 0 errors.
Finished in 7ms on 1 file with 96 rules using 4 threads.
[2m└─[0m [1m[38;2;192;132;252m@demo/ui[0m[2m#[0m[1m[38;2;232;121;249mlint[0m [2m──[0m [2m(2ms)[0m [2mup-to-date[0m
```

The second run is **up-to-date**: oxlint does not start until a file in `src/` changes.

### Tests next to the code

A `!` glob keeps test files out of the build's key, so editing a test does not rebuild:

```ts mark={2}
build: {
  inputs: { files: ['src/**', '!src/**/*.test.ts', 'vite.config.ts'] },
}
```

### A shared file at the workspace root

`workspaceFiles` takes paths from the workspace root, for a file outside the project:

```ts mark={3}
inputs: {
  files: ['src/**', 'vite.config.ts'],
  workspaceFiles: ['tsconfig.base.json'],
},
```

### An environment variable

`inputs.env` puts a variable's value in the key. `exec.env.passThrough` hands it to the command. List it in both:

```ts mark={1,4}
exec: { command: 'vite build', env: { passThrough: ['MODE'] } },
inputs: {
  files: ['src/**', 'vite.config.ts'],
  env: ['MODE'],
},
```

### A tool's version

`workspaceRuntime` runs a command once per run and puts what it prints in the key. A new Node version then rebuilds:

```ts mark={3}
inputs: {
  files: ['src/**'],
  workspaceRuntime: ['node --version'],
},
```

### A tool that reads its last output

vx empties `dist/` before a build runs. `clean: false` keeps it, for a tool that reads its own last result:

```ts mark={1}
outputs: { files: ['dist/**'], clean: false },
```

<Aside type="caution">
  With `clean: false`, a stale file left in `dist/` is stored too, and every machine gets it back.
</Aside>

<Aside type="tip" title="Not sure the inputs are complete?">
  Add [`exec.sandbox`](../sandboxing/) with `allow.read` listing the same files. A workspace read
  outside it fails the task and names the file.
</Aside>

<Takeaway>cache lint and tests, shared files, variables and tool versions.</Takeaway>

</Deeper>


This demo cache is tiny, so the sizes are too. Use your own numbers.

### Empty it

With no flag, `vx cache clean` removes everything this workspace cached, and its run history:

```ansi
[2m$[0m vx cache clean

[38;2;34;197;94m✓[0m [1mvx cache clean[0m  [38;2;203;213;225mfreed 496 KB[0m

  [38;2;203;213;225m.vx/cache[0m
  [38;2;203;213;225m/root/.vx/3e72a2ed9be15889/cache[0m

  [38;2;203;213;225mrun history cleared too: vx last and vx why start over[0m
```

The next run builds from scratch and stores again. `vx last` and `vx why` start over.

### Clean on a schedule

No run evicts, so put the clean where it runs on its own: a weekly CI job, or a cron line on your machine:

```sh
0 9 * * 1 cd ~/work/demo && vx cache clean --older-than 30d --max-size 10G
```

With both flags, the age cut runs first, then the size cap.

### Free every workspace's cache

`--global` clears the stores of every workspace on this machine, under `~/.vx`, and this workspace's run history, so `vx last` and `vx why` start over:

```sh
vx cache clean --global --dry
```

<Quiz q="You build a branch, leave it for two weeks, then come back. vx cache clean --older-than 30d ran in between. Is the build still cached?">
  Yes. Its entries were used 14 days ago, under the 30-day cutoff, so they stay. The next run prints
  **up-to-date** or **restored-local**.
</Quiz>

<Takeaway>keep the cache under an age or a size, preview it first, or empty it.</Takeaway>

<Deeper level="details" title="Every caching field">

Each field sits in a task in `vx.config.ts`. A task with `cache: true` also needs `exec`, `inputs` and `outputs`.

- `cache` · default `false`<br/>`true` stores the result and skips the task on a stored key
- `inputs.files` · required<br/>globs from the project folder; `!` removes; `src` means all of `src/`
- `inputs.workspaceFiles` · default `[]`<br/>the same, from the workspace root
- `inputs.env` · default `[]`<br/>variables whose values go in the key (not passed to the command)
- `inputs.runtime` · default `[]`<br/>commands run in the project; what they print goes in the key
- `inputs.workspaceRuntime` · default `[]`<br/>commands run once at the root; what they print goes in the key
- `inputs.tasks` · default all it depends on<br/>whose keys go in this key; `[]` keeps the order only
- `inputs.stability.strategy` · default `'immutable'`<br/>which writes to an input during the run count: `'immutable'` any, `'mutable'` new bytes only, `'unchecked'` none
- `inputs.stability.severity` · default `'warn'`<br/>on such a write: `'warn'` skips the save, `'error'` fails the task
- `outputs.files` · required<br/>globs of what the command writes; `[]` for none
- `outputs.workspaceFiles` · default `[]`<br/>outputs outside the project, from the workspace root
- `outputs.clean` · default `true`<br/>empty the outputs before a run; `false` keeps them

`.vx/workspace.ts` can set `outputs.clean` and `inputs.stability` for every task. A task's own value wins.

The workspace settings that move the cache:

- `cache.dir`<br/>where the cache lives. Unset, the index sits in `.vx/cache` and the entries in `~/.vx/<id>/cache`, shared by every checkout. Set, the folder you name holds both.
- `history.retention` · default `30d`<br/>how much run history a clean with a bound keeps.

Every field of every task: [Tasks](../tasks/).

</Deeper>

<Deeper level="details" title="What the key holds">

A task with no `cache: true` is keyed on its `inputs` all the same, so a cached task behind it re-runs when they change.

One that declares no `inputs` has no key, and every task behind it misses. `inputs: { files: [] }` still gives a key.

- **Always in it:** the keys of the tasks it depends on, the task's config, the arguments after `--`.
- **In, with a lockfile plugin:** the package's `package.json` and its own dependencies from the lockfile ([Lockfiles](../lockfiles/)).
- **In, when you say so:** a tool's version. `inputs.workspaceRuntime: ['node -v']` runs once per run at the root; `runtime` runs in the package.
- **Out, when you say so:** a dependency only for order, `inputs.tasks: []`, as the [dev task](../dev-servers/) does.
- **Excluded unless named:** files git ignores, an ignored `node_modules` included. A broad glob like `src/**` skips them.
- **Named, they are in:** an exact path or a glob whose fixed part git ignores (`.env.local`, `node_modules/.prisma/client/**`) keys them.
- **The task's own outputs** are out, except a file git tracks. That one stays in the key by what git holds, and a miss writes git's version back first.
- **A nested project's files** are out. A leading `**` passes over them; a glob that names its way into one (`*/dist/**`, a root `packages/**/*.ts`) is refused by `vx lock`.
- **Always excluded:** `.git`, an install's `node_modules` (untracked, not ignored), and vx's own files at the project's root.
- **vx's own files:** `.vx/cache`, `.vx/tmp`, and the lock files `vx lock` writes (`.vx/projects.lock`, `.vx/dependencies.lock`, `vx.lock.json`, `.vx/.gitattributes`, `.vx/.gitignore`).
- **And their temp copies** a killed `vx lock` leaves behind: `.vx/projects.lock.tmp-*`, `.vx/dependencies.lock.tmp-*`, `vx.lock.json.tmp-*`.

Every part, in order: [Caching in depth](../../caching/).

</Deeper>

<Deeper level="details" title="What happens to outputs">

- Declared outputs are emptied before every run that writes the cache.
- A hit rewrites only the files that differ from the entry.
- Then it removes the files the entry does not hold, so `dist/` ends as the cache stored it.
- A hit that finds the outputs already as stored writes nothing: **up-to-date**.
- A restore writes only files the task's `outputs` declare.
- A plain path must exist when the command ends, and at least one declared output must. A wildcard may match nothing ([fix](#outputs-must-exist)).
- A failed task is never saved.
- A file git tracks is never deleted, even when an output glob matches it.
- Outputs ignore `.gitignore`: `dist/` is stored even when git ignores it.
- `--force` runs everything and replaces what the local cache holds (a remote keeps the keys it has). `--no-cache` ignores the cache.

</Deeper>

<Deeper level="details" title="Every verdict vx why prints">

The `verdict` line falls in one of four groups.

### The key changed

An input moved, so the task ran. This is the usual verdict.

- `cache key changed: env MODE, file packages/ui/src/index.ts`<br/>those inputs moved (three named, then a count); the lines below show each
- `cache key changed between the previous run and this one (inputs differ)`<br/>the key moved and neither entry kept its components (pruned, or a failed run saved none)

### Never cached

The task, or one it depends on, has no `inputs` or no `cache: true`, so it runs every time.

- `` never cached: this task declares no `inputs`, so each run derives a new key; declare its `inputs` ``<br/>the task itself declares no `inputs`, so its key is new every run
- `` never cached: its key includes //#stamp, which declares no `inputs`, so each run derives a new key; declare inputs on //#stamp ``<br/>a task this key includes declares no `inputs`, so the key is new every run; declare them on that task
- `` this task declares no `cache: true` — it runs on every invocation; a change to its inputs still re-runs the tasks that depend on it ``<br/>not cached at all
- `` this task declares no `cache: true` — it runs on every invocation; it declares no `inputs` either, so each run derives a new key and every task that depends on it misses; declare its `inputs` (and `outputs` with `cache: true` to cache it too) ``<br/>not cached, and no task depending on it can hit

### Same key, ran anyway

The key matched, but no stored result could be used. The line says why.

- `cache key unchanged — this run was served from cache, nothing re-ran`<br/>a hit
- `cache key unchanged — the previous run on this key failed and saved nothing, so there was nothing to hit`<br/>a failure saves no entry
- `cache key unchanged — re-executed because this run did not read the cache (--force, or a --cache-policy without read)`<br/>the run's policy read no cache
- `cache key unchanged — re-executed because this run did not use the cache (--no-cache, or a --cache-policy without read or write)`<br/>the run used no cache
- `cache key unchanged — the previous run on this key did not save its result (…), so there was nothing to hit`<br/>the previous run withheld its save and said why (an input edited while it ran)
- `cache key unchanged — no entry for this key was in the cache when it ran (pruned or evicted), so it executed and saved one`<br/>the entry was gone
- `cache key unchanged — the previous run on this key executed but no entry for it is in the cache (its save failed, or it was pruned since), so there was nothing to hit`<br/>the previous run's save failed, or a prune took the entry
- `cache key unchanged — the previous run on this key built on a dependency it left out (…), so it saved nothing and there was nothing to hit`<br/>the previous run left that dependency out, and saves nothing built on one
- `cache key unchanged — the previous run on this key did not write the cache (--no-cache, or a --cache-policy without write), so there was nothing to hit`<br/>the previous run's policy wrote no cache
- `cache key unchanged — re-executed on the same key though this run read the cache; vx cannot name the cause`<br/>none of the above; vx cannot name the cause
- `cache key unchanged — re-executed on the same key (--no-cache / --force, or unrelated)`<br/>no invocation recorded this run's cache policy, so vx cannot rule the flags out
- `cache key unchanged — this run recorded no cache outcome, so whether it re-ran is unknown`<br/>vx does not guess

### No key to compare

This run made no key, or there is no earlier run.

- `this task was skipped: it needs another platform, so it recorded no cache key`<br/>it waits for a worker of that platform
- `this task never ran: … did not pass, so it recorded no cache key`<br/>a task it depends on failed or was skipped
- ``this task's cache key could not be derived, so its command never ran (…)``<br/>the line names the `vx last` command that shows why
- `this task hit the cache and its restore failed, so it recorded no cache key`<br/>the restore was refused or failed; the line in its log says why
- `this task is persistent: it records no cache key`<br/>a server or watcher has no key to compare
- `no prior run for this (project, task)`<br/>nothing to compare with yet

</Deeper>

<Deeper level="details" title="Every vx cache clean option">

```sh wrap
vx cache clean [--older-than <duration>] [--max-size <size>] [--global] [--dry] [--format pretty|json] [--cache-dir <path>]
```

- **no flag:** removes the whole cache, `.vx/cache` and this workspace's store `~/.vx/<id>/cache`.
- `--older-than <duration>`: drops entries last used before then. `30d`, `24h`, `60m`, `30s`.
- `--max-size <size>`: then drops the least recently used until under the size. `500M`, `5G`, `1T`.
- `--dry`: says what would go and deletes nothing.
- `--global`: with no bound, also clears every other workspace's store under `~/.vx`.
- `--format json`: one object with `dry`, `evicted`, `bytesFreed`, `orphans`, `orphanBytes`, `historyRows`, `historyBytes`.
- `--cache-dir <path>`: the cache a run with the same flag uses.

The rules:

- `m` is minutes. `1M` is refused, since some tools read it as a month.
- A size needs a unit: `--max-size 10` is refused. Units count in 1024s.
- A zero bound is refused. To remove everything, drop the flag.
- An entry may stay up to an hour past `--older-than`: vx records a use at most once an hour.
- A clean with a bound also drops run history older than `history.retention`.
- A clean waits for a `vx run` on the same workspace to end first.
- `.vx/workspace.ts` and the lock files are never touched.

The command in full: [`vx cache clean`](../../cli/cache/).

</Deeper>

<Deeper level="details" title="When it goes wrong">

- **A task came from the cache after you changed a file.** That file is
  not in `inputs.files`: add it.
- **To catch the next one,** use [`exec.sandbox`](../../docs/sandboxing/)
  with reads granted no wider than the inputs: it refuses that read and names the file.
- **A task runs every time.** It needs `cache: true`. If it has that, a
  task it depends on may have no `inputs`: give that task `inputs` too.
  `vx-migrate` leaves a `TODO(vx-migrate)` where it could not decide.
- **`dist/` is empty after a build tool's incremental run.** Its state
  file sits outside `dist/`, so it thinks the build is done. Add that
  file to `outputs.files`, or move it inside `dist/`.
- **A cache hit shows only part of a long log.** It replays the first
  and last 8 Mi characters (8 MiB of ASCII) of a task's output.

`vx why` needs one task that has run. Name the project when the task is in several:

```ansi title="vx why build"
[38;2;239;68;68m✗[0m [1mvx why[0m  [38;2;203;213;225m"build" ran in 2 projects — pick one[0m

  [38;2;203;213;225m@demo/ui#build[0m
  [38;2;203;213;225m@demo/web#build[0m
```

<Takeaway>fix a stale hit, a task that never hits, and a `vx why` that refuses.</Takeaway>

</Deeper>
