```ts title=".vx/workspace.ts"

  url: 'https://vx-cache-server.acme.workers.dev',
  issuer: 'https://token.actions.githubusercontent.com',
  repository: 'acme/app',
})
```

<Concept term="Remote cache">
  A [cache](../caching/) on a server, shared by every machine. vx asks it when the cache on this
  machine misses, and uploads each result it makes.
</Concept>

## How a run uses it

<Diagram {...remoteCache} />

vx asks the cache on this machine first, the remote second. A task runs only when both miss. Uploads happen in the background.

<Aside type="tip">
  A remote that is down never fails a run. vx says so once, then runs the task as if there were no
  remote.
</Aside>

<Quiz q="The cache server is down during a pull request's run. What happens?">
  The run goes on. vx prints one warning, turns the remote off for that run, and runs the tasks the
  local cache does not have.
</Quiz>

<Takeaway>predict where each task's result comes from: this machine, the server, or a fresh run.</Takeaway>

## Set it up

<Concept term="Cache server">
  `@vzn/vx-cache-server`: a small server you host. It keeps results in one bucket and stores no
  secret.
</Concept>

You need vx running on [CI](../ci/) and a Cloudflare account. To host it on Bun or Docker with S3 instead, see [Cache server](../servers/cache/).

<Steps>

1. **Deploy the server.** Install it in a folder of its own:

   ```sh
   mkdir vx-cache-server && cd vx-cache-server
   bun add @vzn/vx-cache-server
   ```

   `ALLOW` says who may use it. Here: every run of `acme/app`'s `ci.yml` on GitHub Actions.

   ```jsonc title="wrangler.jsonc" mark={5}
   {
     "name": "vx-cache-server",
     "main": "node_modules/@vzn/vx-cache-server/src/worker.ts",
     "compatibility_date": "2026-10-01",
     "vars": { "ALLOW": "https://token.actions.githubusercontent.com:acme/app:ci.yml" },
     "r2_buckets": [{ "binding": "BLOBS", "bucket_name": "vx-cache" }]
   }
   ```

   ```sh
   bunx wrangler login
   bunx wrangler deploy
   ```

   wrangler creates the bucket and prints the URL, such as `https://vx-cache-server.acme.workers.dev`.

2. **Check it answers.**

   ```sh
   curl https://vx-cache-server.acme.workers.dev/v1/capabilities
   ```

   It refuses a request from outside vx. The refusal proves it is up:

   ```json
   {"code":"bad_request","message":"vx-issuer and vx-repository: the issuer's and the repository's hashes (PROTOCOL.md § Keys)"}
   ```

   Seeing `ALLOW is empty` instead? Fill in `ALLOW` and deploy again.

3. **Point vx at it.**

   ```sh
   bun add -d @vzn/vx-cache
   ```

   ```ts title=".vx/workspace.ts" ins={2,10-14}
   import { defineWorkspace } from '@vzn/vx/config'
   import { vxCache } from '@vzn/vx-cache'
   import { github } from '@vzn/vx-ci'
   import { bun } from '@vzn/vx-lockfile'

   export default defineWorkspace({
     plugins: [
       bun(),
       github(),
       vxCache({
         url: 'https://vx-cache-server.acme.workers.dev',
         issuer: 'https://token.actions.githubusercontent.com',
         repository: 'acme/app',
       }),
     ],
     pipelines: {
       pr: { tasks: ['lint', 'test', 'build'], affected: true },
       main: { tasks: ['lint', 'test', 'build'] },
     },
   })
   ```

   `issuer` and `repository` match your `ALLOW`. `github()` tells the cache which branch a run is on. The `pipelines` stay as [CI](../ci/) set them. Run `vx lock` and commit.

4. **Let CI jobs prove who they are.** Allow the job to ask for a token:

   ```yaml title=".github/workflows/ci.yml" ins={6}
   jobs:
     ci:
       runs-on: ubuntu-latest
       permissions:
         contents: read
         id-token: write
   ```

   vx asks GitHub for the token itself. Nothing goes in your secrets.

5. **Push.** The first run on `main` uploads (`↑`). The next pull request downloads (`↓`).

</Steps>

<Takeaway>share every CI result across your whole team, with no token stored anywhere.</Takeaway>

## Who reads and who writes

<Concept term="CI token">
  A short-lived ID card your CI hands each job (OIDC). It names the repository, the workflow and the
  branch. The server reads it and decides what the job may do.
</Concept>

<Diagram {...branchReads} />

| Run | Reads | Writes |
| --- | --- | --- |
| push to `main` | `main` | `main` |
| pull request #12 from `feat-x` | `PR #12`, then `feat-x`, then `main` | `PR #12` only |
| merge queue into `main` | `main` | `main` |
| `pull_request_target`, `issue_comment`, `workflow_run` | as its pull request | nothing |
| a laptop | nothing, unless the server sets `READ_ACCESS=public` | nothing |
| another repository | refused | refused |

The server decides this from the token. No option in your config can change it.

<Quiz q="A pull request builds broken code. Can main's next run download that broken build?">
  No. A pull request writes only its own results (`PR #12`), never a branch. `main` never reads
  them, so code that is not merged never reaches `main`'s runs.
</Quiz>

<Takeaway>tell, for any run, which results it can see and which it can change.</Takeaway>

<Deeper level="patterns" title="Common setups">

### Your laptop

A laptop has no CI token. By default it reads nothing from the server and uses its own cache.

To let anyone who can reach the server read from it, set `READ_ACCESS` to `public` beside `ALLOW`. Writes still need a CI token.

To keep the server private, put Cloudflare Access (or another proxy) in front of it and pass its service token:

```ts title=".vx/workspace.ts" mark={5-8}
vxCache({
  url: 'https://vx-cache-server.acme.workers.dev',
  issuer: 'https://token.actions.githubusercontent.com',
  repository: 'acme/app',
  headers: {
    'CF-Access-Client-Id': process.env.CF_ACCESS_CLIENT_ID,
    'CF-Access-Client-Secret': process.env.CF_ACCESS_CLIENT_SECRET,
  },
})
```

<Takeaway>give laptops read access, publicly or behind your own login.</Takeaway>

### GitLab CI

`ALLOW` names the CI file as the workflow: `https://gitlab.com:acme/app:.gitlab-ci.yml`. Name a token `VX_CACHE_TOKEN`, with the server's URL as its audience:

```yaml title=".gitlab-ci.yml"
vx:
  id_tokens:
    VX_CACHE_TOKEN:
      aud: https://vx-cache-server.acme.workers.dev
```

```ts title=".vx/workspace.ts" ins={1,4,6}
import { gitlab } from '@vzn/vx-ci'

plugins: [
  gitlab(),
  vxCache({
    issuer: 'https://gitlab.com', // or your GitLab's URL
    repository: 'acme/app',
    url: 'https://vx-cache-server.acme.workers.dev',
  }),
]
```

<Takeaway>run the same cache from GitLab pipelines.</Takeaway>

### A CI job that only reads

A job that should never upload, such as a nightly check, sets the remote to read-only:

```sh
vx run test --cache-policy=remote:r
```

<Takeaway>keep any job from writing to the shared cache.</Takeaway>

### Delete old results

The server never deletes anything. Give the bucket an expiry rule. This one deletes each result a day after it was written:

```sh
bunx wrangler r2 bucket lifecycle add vx-cache all '' --expire-days 1
```

<Takeaway>keep the bucket small without touching the server.</Takeaway>

### Entries over 1 GiB

A remote takes an entry up to 1 GiB, unpacked. A bigger one stays on the machine that built it, and vx says once that it was not sent. To share bigger entries, raise the ceiling for every machine:

```ts title=".vx/workspace.ts" ins={4-6}
import { defineWorkspace } from '@vzn/vx/config'

export default defineWorkspace({
  cache: {
    artifactCeiling: '4GiB',
  },
})
```

<Aside type="caution">
  A machine with a lower ceiling treats a bigger entry as a miss and runs the task. Set the same
  value everywhere.
</Aside>

The cache server takes uploads up to 100 MB, compressed. Raise its `MAX_UPLOAD_BYTES` for bigger ones ([Settings](../servers/cache/#server-settings)).

<Takeaway>share large build outputs, such as app bundles or images.</Takeaway>

### Other remote caches

Already run a Turborepo, Nx or Bazel cache? Keep it:

<Tabs>
  <TabItem label="Turborepo">
    ```sh
    bun add -d @vzn/vx-migrate
    bunx turbo login && bunx turbo link        # stores a token and a team
    export TURBO_TOKEN=… TURBO_TEAM=…
    ```

    Declare `plugins: [turboCache()]` from `@vzn/vx-migrate`. It reads Turbo's own variables.

    On GitHub Actions, `turboCache({ oidc: true })` with `id-token: write` trades the job's token for
    a short-lived one, so no token is stored.

    On a laptop it asks for a read-only token once and keeps it in the OS keychain.
  </TabItem>
  <TabItem label="Nx">
    `nxCache()` from `@vzn/vx-migrate` does the same for a self-hosted Nx cache.
  </TabItem>
  <TabItem label="Bazel">
    A Bazel remote cache (NativeLink, BuildBuddy, Buildbarn, bazel-remote) works through `reapi()`
    from `@vzn/vx-reapi`:

    ```ts title=".vx/workspace.ts"
    import { defineWorkspace } from '@vzn/vx/config'
    import { reapi } from '@vzn/vx-reapi'

    export default defineWorkspace({
      plugins: [reapi({ endpoint: process.env.REAPI_ENDPOINT })], // grpcs://cache.example.com:443
    })
    ```
  </TabItem>
  <TabItem label="Your own">
    Any backend is [a plugin](../writing-plugins/#your-own-cache).
  </TabItem>
</Tabs>

Each plugin's options are on its page: [`@vzn/vx-migrate`](../../plugins/vx-migrate/), [`@vzn/vx-reapi`](../../plugins/vx-reapi/).

<Takeaway>move to vx without giving up the cache you already run.</Takeaway>

<Deeper level="details" title="Every option">

### `vxCache()` options

| Option | What it does | Default |
| --- | --- | --- |
| `url` | The server's URL, without `/v1`. `https` only; `http` only to `127.0.0.1`, `::1` or `localhost`. No `?query` or `#fragment`. | `VX_CACHE_URL` |
| `issuer` | Your CI's token issuer: `https://token.actions.githubusercontent.com`, `https://gitlab.com` or your GitLab's URL. | required |
| `repository` | The repository, `org/name`, as `ALLOW` names it. | required |
| `timeoutMs` | How long a read or check waits for an answer, in ms; one unanswered is asked once more before the remote turns off. A download then must bring at least 1 MiB a second. | `30000` |
| `uploadTimeoutMs` | The same for an upload: at least 1 MiB a second, then an answer within this time. | `60000` |
| `retries` | How many times a request answered `5xx` or `429`, or cut off, is sent again (0 to 10), 1 s, 2 s, … apart. | `2` |
| `headers` | Headers sent on every request, for a proxy in front of the server. An unset value is left out. `authorization`, `content-type`, `content-length` and `vx-*` are refused. | none |

| Variable | What it does |
| --- | --- |
| `VX_CACHE_URL` | The server's URL when `url` is not set. |
| `VX_CACHE_TOKEN` | The job's token on GitLab CI (an `id_tokens` entry). |

A redirect is not followed: it fails the request and names where it pointed. The workers of a [Distributed task execution](../distributed-task-execution/) run send the same headers, so give their job the same secrets.

### Workspace settings for remotes

In `.vx/workspace.ts`, under `cache`:

| Setting | What it does | Default |
| --- | --- | --- |
| `policy` | Which layers a run reads and writes, such as `'local:rw,remote:r'`. Same as `--cache-policy` or `VX_CACHE_POLICY`. | every layer reads and writes |
| `artifactCeiling` | The largest entry, unpacked, a remote stores or a hit unpacks. Same on every machine. `VX_CACHE_ARTIFACT_CEILING`. | `'1GiB'` |
| `upload.failures` | Which runs keep a failed task's log and outputs in the remote: `'ci'`, `'local'` or `'always'`. | `'ci'` |
| `concurrency.download` | Downloads at once. `--cache-concurrency-download`. | min(96, max(cores × 3, 64)) |
| `concurrency.upload` | Uploads at once, per remote. `--cache-concurrency-upload`. | min(96, max(cores × 3, 64)) |
| `download` | Which results of tasks run on other machines land here. See [Remote execution](../remote-execution/). | `'all'` |

Off CI (`CI` unset), vx never writes the remote unless `--cache-policy`, `VX_CACHE_POLICY` or `cache.policy` names it. Each setting is also in the [workspace reference](../../schema/workspace/#settings).

### Cache scopes and tokens

Each read names the refs the run reads, its own first. A pull request writes only its merge ref, `refs/pull/<n>/merge`. The server answers from the first branch that holds the result.

On CI, `github()` or `gitlab()` ([`@vzn/vx-ci`](../../plugins/vx-ci/)) names the branches. Without one, a run reads the checked-out branch, then the default branch:

| Run | Branches read, in order |
| --- | --- |
| push to `main` | `refs/heads/main` |
| pull request #12 from `feat-x` | `refs/pull/12/merge, refs/heads/feat-x, refs/heads/main` |
| merge queue into `main` | `refs/heads/main` |
| laptop on `feat-x` | `refs/heads/feat-x, refs/heads/main` |

`vxCache()` sends each branch as a hash, so no branch name leaves the machine. `turboCache()` sends them in `x-artifact-read-scopes`.

For a server that ignores that header (Vercel), `turboCache({ scope: 'key' })` adds the branch to each key. Branches stay apart, but nothing enforces it.

[Branch caches a server enforces](../../blog/branch-caches-a-server-enforces/) shows the server side.

### When it does not work

vx says what went wrong once, then runs on without the remote:

```ansi
[1m[38;2;234;179;8m[vx][0m plugin '@vzn/vx-cache': download e04649970f18ba23 from https://vx-cache-server.acme.workers.dev failed: HTTP 401: no bearer token: a read with no token was refused; remote cache off for this run
```

| Message | Cause | Fix |
| --- | --- | --- |
| `no bearer token` on CI | the job cannot ask for a token | add `id-token: write` (GitHub) or `VX_CACHE_TOKEN` (GitLab) |
| `no bearer token` on a laptop | expected | see [Your laptop](#your-laptop) |
| `403` | the repository or workflow is not in `ALLOW`, or does not match `repository` | fix `ALLOW` or `vxCache({ repository })` |

A refused write turns off uploads only. A server that does not answer in time, or is not found, turns the remote off for the run.
