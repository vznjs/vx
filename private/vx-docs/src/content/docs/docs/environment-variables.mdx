<Concept term="Environment variable">
  A name with a text value that a program reads when it starts, like `API_URL=https://api.demo.dev`.
  Your shell and your CI set them.
</Concept>

## Give a task a variable

Past a small essential allowlist (below), a task sees only the variables you pass it.

Name the variable in `exec.env.passThrough`. vx copies its value from your shell when the task starts:

```ts title="packages/web/vx.config.ts" mark={7}
import { defineProject } from '@vzn/vx/config'

export default defineProject({
  tasks: {
    test: {
      exec: {
        command: 'vitest run',
        env: { passThrough: ['API_URL'] },
      },
      inputs: { files: ['src/**'] },
      outputs: { files: [] },
      cache: true,
    },
  },
})
```

`PATH`, `HOME`, `CI` and a few more reach every task without a word from you. The full list is under **Details**.

<Takeaway>hand any shell or CI variable to a task by name.</Takeaway>

## Re-run when a value changes

<Concept term="Cache key">
  A short code vx computes from everything a task reads. Same key, vx replays the stored result.
  New key, the task runs. See [Caching](../caching/).
</Concept>

`passThrough` gives the value to the command. It does **not** put it in the key. Add the name to `inputs.env` and a new value means a new key:

<Compare leftTitle="passThrough only" rightTitle="passThrough + inputs.env">
<div slot="left">

```ts
exec: { command: 'vitest run', env: { passThrough: ['API_URL'] } },
inputs: { files: ['src/**'] },
```

New `API_URL` → **up-to-date**, old result.

</div>
<div slot="right">

```ts
exec: { command: 'vitest run', env: { passThrough: ['API_URL'] } },
inputs: { files: ['src/**'], env: ['API_URL'] },
```

New `API_URL` → the test **runs**.

</div>
</Compare>

Why two lists? A token changes nothing a task makes. Keying on it would make every laptop and CI miss each other's cache.

<Quiz q="GH_TOKEN lets a task download packages. Each machine has its own token. Which lists does it go in?">
  `passThrough` only. The task needs it, but the files it makes are the same with any token. In
  `inputs.env`, each machine would get its own key and never share a cache.
</Quiz>

<Takeaway>tell vx which variables change a task's result, so a new value never replays an old one.</Takeaway>

## Write a value in the config

A value that never changes between machines goes in `exec.env.define`. The command gets it, and the key sees it, because it is part of the config:

```ts title="packages/web/vx.config.ts" mark={4}
build: {
  exec: {
    command: 'vite build',
    env: { define: { NODE_ENV: 'production' } },
  },
  inputs: { files: ['src/**', 'index.html'] },
  outputs: { files: ['dist/**'] },
  cache: true,
},
```

Edit `'production'` and the next run builds again.

<Takeaway>pin a variable to one value for every machine, with no shell setup.</Takeaway>

## Hide a secret

vx prints a secret's value as `***`, in the live output and in everything it stores:

```ansi title="DEPLOY_TOKEN is masked by its name"
[2m$[0m DEPLOY_TOKEN=tok_9f8e7d6c5b vx run deploy

[2m┌─[0m [1m[38;2;244;114;182m@demo/web[0m[2m#[0m[1m[38;2;244;114;182mdeploy[0m [2m>[0m $ echo "uploading with $DEPLOY_TOKEN"
uploading with ***
[2m└─[0m [1m[38;2;244;114;182m@demo/web[0m[2m#[0m[1m[38;2;244;114;182mdeploy[0m [2m──[0m [2m(14ms)[0m [2msuccess[0m
```

The name holds `TOKEN`, so vx masks it with no setup. A secret named otherwise goes in `exec.env.secret`:

```ts mark={2}
exec: {
  command: 'bunx wrangler deploy',
  env: { passThrough: ['CF_API'], secret: ['CF_API'] },
},
```

<Aside type="caution" title="Masking is for logs">
  A task you pass a secret to can still read it. Pass a secret only to the task that needs it.
</Aside>

<Takeaway>pass tokens to a task without them landing in logs or the cache.</Takeaway>

## Pick the right list

| List                   | The command sees it | The key sees it | Use it for                                                    |
| ---------------------- | ------------------- | --------------- | ------------------------------------------------------------- |
| `exec.env.passThrough` | yes                 | no              | tokens and machine-specific values (`GH_TOKEN`, `API_URL`)    |
| `inputs.env`           | no                  | yes             | with `passThrough`: a variable that changes the result        |
| `exec.env.define`      | yes                 | yes             | a fixed value written in the config (`NODE_ENV: 'production'`) |
| `exec.env.secret`      | —                   | —               | a secret whose name vx does not mask by itself                |

Try it: type a variable and answer three questions. The config it needs appears below.

<Deeper level="patterns" title="Common setups">

### A Vite public variable

Vite writes `VITE_*` values into the bundle. Pass it **and** key on it, or a new URL ships the old bundle:

```ts mark={1,2}
exec: { command: 'vite build', env: { passThrough: ['VITE_API_URL'] } },
inputs: { files: ['src/**', 'index.html'], env: ['VITE_API_URL'] },
outputs: { files: ['dist/**'] },
cache: true,
```

`vx lock` warns about a passed `VITE_`, `NEXT_PUBLIC_` or `NODE_ENV` variable that `inputs.env` leaves out.

### A publish token

A token changes no file the task makes. Pass it, do not key on it:

```ts
publish: {
  dependsOn: ['build'],
  exec: { command: 'bun publish', env: { passThrough: ['NPM_TOKEN'] } },
},
```

`NPM_TOKEN` holds `TOKEN`, so its value prints as `***`.

### One helper for both lists

A config is TypeScript. A small function returns both lists:

```ts title="packages/web/vx.config.ts"
import { defineProject } from '@vzn/vx/config'

const keyed = (...names: string[]) => ({
  exec: { command: 'vite build', env: { passThrough: names } },
  inputs: { files: ['src/**', 'index.html'], env: names },
})

export default defineProject({
  tasks: {
    build: { ...keyed('VITE_API_URL', 'VITE_SENTRY_DSN'), outputs: { files: ['dist/**'] }, cache: true },
  },
})
```

### A setting for one run

Every vx setting has a `VX_` variable. Set it for one command:

```sh
VX_RUN_CONCURRENCY=50% vx run test
VX_CACHE_POLICY=local:rw,remote:r vx run build
```

A flag beats its variable. The variable beats `.vx/workspace.ts`.

### Variables for a pipeline

A [pipeline](../ci/) sets variables for vx and its plugins with `env`. Tasks do not see them:

```ts title=".vx/workspace.ts" mark={9}
import { defineWorkspace } from '@vzn/vx/config'
import { dte } from '@vzn/vx-dte'

export default defineWorkspace({
  plugins: [dte({ relay: 'https://relay.example.com' })],
  pipelines: {
    ci: {
      tasks: ['lint', 'test', 'build'],
      env: { VX_DTE_RELAY: 'https://relay-eu.example.com' },
    },
  },
})
```

<Takeaway>set up public bundler values, publish tokens and per-run settings without guessing.</Takeaway>

</Deeper>

`vite build` writes `NODE_ENV` into the bundle. Pass it only, and the

stands in for `vite` and prints the mode. Pick a tab.

<Deeper level="details" title="What every task gets">

Every task gets these variables, so everyday CLI tools work:

- `PATH`, `HOME`, `SHELL`, `USER`, `LOGNAME`
- `TMPDIR`, `TEMP`, `TMP`
- `LANG`, `LC_ALL`, `LC_CTYPE`
- `TERM`, `COLORTERM`, `FORCE_COLOR`, `NO_COLOR`
- `CI`, `NODE_OPTIONS`, `COREPACK_HOME`, `PNPM_HOME`
- `RUSTUP_HOME`, `CARGO_HOME`, `GOPATH`, `GOMODCACHE`, `GOCACHE`
- `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME`,
  `XDG_RUNTIME_DIR`

None of them is in the key: `PATH` and `HOME` differ on every machine. If one changes your output (`NODE_OPTIONS`, `LANG`), add it to `inputs.env`.

vx also sets:

| Variable           | Value                                                                    |
| ------------------ | ------------------------------------------------------------------------ |
| `VX_RUN_WORKSPACE` | the workspace root                                                       |
| `VX_RUN_TASK`      | the `project#task` running                                               |
| `VX_RUN_TREE`      | a token per task, so a stop also ends a daemon the task started          |
| `FORCE_COLOR`      | `1`, unless `FORCE_COLOR` or a non-empty `NO_COLOR` already reaches the task |
| `npm_execpath`     | your package manager, so a tool that calls it back finds it              |

A `vx run` inside a task of the same workspace is refused: use `dependsOn`. The package's own `node_modules/.bin`, then the workspace root's, come first on `PATH`.

Nothing else from your shell reaches a task. When a failed task's output names a variable your shell holds, vx prints the `[vx]` line from frame 1.

</Deeper>

<Deeper level="details" title="Every field">

### `exec.env.passThrough`

Names copied from vx's environment when the task starts. Default `[]`. Not in the key.

- Exact names only: `NEXT_PUBLIC_*` and `!NAME` are refused.
- A shell variable name: letters, digits and `_`, not starting with a digit.
- An unset name stays unset in the task.

### `exec.env.define`

Name and value pairs, both strings. Default `{}`. In the key, as part of the config.

```ts
env: { define: { NODE_ENV: 'production', TZ: 'UTC' } },
```

`define` beats `passThrough`, which beats the essential list. A task run on another machine gets the same values.

### `exec.env.secret`

Names whose values vx prints as `***`. Default `[]`. Exact names, no wildcard. Needed only for a name vx does not mask by itself (`GH_PAT`, `NPM_AUTH`).

### `inputs.env`

Names whose values go in the key. Default `[]`. It does not pass the value to the command.

- Unset, empty and `'x'` are three different keys.
- A value that is not valid UTF-8 fails the run, naming the variable, never its value.
- `vx why` names a changed variable. A masked one shows as hashes.

### `pipelines.<name>.env`

Name and value pairs set before the pipeline's plugins start. For vx and plugins only: every task reads them as unset. A variable already set in your shell wins.

### Where `***` appears

A value is masked when its name holds `TOKEN`, `SECRET`, `KEY`, `PASSWORD`, `PASSWD`, `PASSPHRASE` or `CREDENTIAL`, ends in `_PASS`, or is in `exec.env.secret`.

- Names ending `_FILE`, `_PATH` or `_DIR` are not masked by name.
- A value shorter than 6 characters is not masked (`run.secrets.minLength`).
- vx masks task output, the cached copy a hit replays, `vx show`, `vx why`, `vx last`, telemetry and error lines.

Full rules: [the `exec` reference](../../schema/exec/).

</Deeper>

<Deeper level="details" title="Every VX_ variable">

Each one sets one [workspace setting](../../schema/workspace/). An empty one is ignored. A bad value stops vx before any task runs:

```ansi title="a value its setting does not take"
[2m$[0m VX_RUN_TIMEOUT=soon vx run test
[38;2;239;68;68m✗[0m [1mvx run[0m  [38;2;203;213;225mVX_RUN_TIMEOUT must be a duration like '500ms', '30s' or '5m', at most 24 days (got soon)[0m
```

**Run**

| Variable                         | What it sets                                                       | Default                     |
| -------------------------------- | ------------------------------------------------------------------ | --------------------------- |
| `VX_RUN_CONCURRENCY`             | tasks at once: a number or `'50%'` of the cores                    | the cores vx may use        |
| `VX_RUN_SCHEDULE`                | which ready task starts first                                      | `most-work`                 |
| `VX_RUN_TIMEOUT`                 | a task's time limit when it has no `exec.timeout`; `--timeout` beats it              | none                        |
| `VX_RUN_RETRIES`                 | re-runs of a failed task, for tasks without `exec.retries`         | `0`                         |
| `VX_RUN_FAIL_FAST`               | stop everything at the first failure                               | `false`                     |
| `VX_RUN_OUTPUT_LOGS`             | which task output prints: `full`, `errors-only`, `hash-only`, `none` | `errors-only` on CI       |
| `VX_RUN_BRANCH`                  | the branch a run records in its history                            | git's branch                |
| `VX_RUN_KILL_GRACE`              | time between SIGTERM and SIGKILL                                   | `2s`                        |
| `VX_RUN_PLUGIN_TIMEOUT`          | how long a plugin may take to finish at the run's end              | `3s`                        |
| `VX_RUN_LOGS_CAPTURE_HEAD`       | start of a task's output kept for replay                           | `8MiB`                      |
| `VX_RUN_LOGS_CAPTURE_TAIL`       | end of a task's output kept for replay                             | `8MiB`                      |
| `VX_RUN_LOGS_FAILED_HEAD`        | start of a failed attempt's output kept                            | `8KiB`                      |
| `VX_RUN_LOGS_FAILED_TAIL`        | end of a failed attempt's output kept                              | `56KiB`                     |
| `VX_RUN_SECRETS_MIN_LENGTH`      | shortest secret value vx masks                                     | `6`                         |
| `VX_RUN_RULES_EXCLUSIVE_OUTPUTS` | refuse two tasks whose outputs overlap                             | `true`                      |

**Cache**

| Variable                        | What it sets                                                  | Default                      |
| ------------------------------- | ------------------------------------------------------------- | ---------------------------- |
| `VX_CACHE_DIR`                  | where the cache lives                                         | `.vx/cache`                  |
| `VX_CACHE_POLICY`               | which caches a run reads and writes (`local:rw,remote:r`)     | every cache reads and writes |
| `VX_CACHE_SCOPE`                | the branch a remote cache keeps entries under                 | the branch's                 |
| `VX_CACHE_DOWNLOAD`             | which remote hits land on disk: `all`, `toplevel`, `none`     | `all`                        |
| `VX_CACHE_CONCURRENCY_DOWNLOAD` | remote downloads at once                                      | 64 to 96, by cores           |
| `VX_CACHE_CONCURRENCY_UPLOAD`   | uploads at once, per remote                                   | 64 to 96, by cores           |
| `VX_CACHE_CONCURRENCY_RESTORE`  | local hits restoring at once                                  | twice `run.concurrency`      |
| `VX_CACHE_STORE_EMBEDDINGS`     | largest entry kept inside the cache index                     | `32KiB`                      |
| `VX_CACHE_STORE_DECOMPRESS`     | keep a larger entry as plain files                            | `true`                       |
| `VX_CACHE_ARTIFACT_CEILING`     | largest entry a remote cache stores                           | `1GiB`                       |

**Inputs, history, lock, watch**

| Variable                       | What it sets                                                   | Default     |
| ------------------------------ | -------------------------------------------------------------- | ----------- |
| `VX_BASE_BRANCH`               | your main branch, for `--affected` and cache scope             | `origin/HEAD`'s branch |
| `VX_AFFECTED_BASE`             | the commit a bare `--affected` compares with                   | merge base  |
| `VX_INPUTS_STABILITY_STRATEGY` | what an input written during the command means for the save    | `immutable` |

| `VX_WATCH_POLL_INTERVAL`       | how often a polling `vx watch` looks                           | `250ms`     |

| `VX_CACHE_URL`                             | [`@vzn/vx-cache`](../../plugins/vx-cache/)       | the cache server's URL; stands in for `url`        |
| `VX_CACHE_TOKEN`                           | `@vzn/vx-cache`                                  | GitLab: the CI token the cache server checks       |
| `VX_HISTORY_URL`                           | [`@vzn/vx-history`](../../plugins/vx-history/)   | the history server's URL; stands in for `url`      |
| `VX_HISTORY_TOKEN`                         | `@vzn/vx-history`                                | GitLab: the CI token the history server checks     |

</Deeper>

<Deeper level="details" title="Other variables vx reads">

| Variable                                               | What vx does with it                                         |
| ------------------------------------------------------ | ------------------------------------------------------------ |
| `NO_COLOR`, `FORCE_COLOR`                              | turn vx's colours off or on                                  |
| `CI`                                                   | a truthy value picks the CI output                           |
| `GITHUB_ACTIONS`                                       | wraps each task's output in a collapsible group              |
| `GITHUB_ACTIONS`, `GITLAB_CI`, `BUILDKITE`, `CIRCLECI` | names the CI provider in the run's history                   |
| `CLAUDE_CODE_TMPDIR`, `CLAUDE_TMPDIR`                  | where a sandboxed task's temp folder goes                    |

vx sets these for itself and removes them at start; do not set them: `VX_HANDED_OFF`, `VX_SIGNAL_RELAY`, `VX_JIT_TIERED`, `VX_IGNORED_SIGNALS`.

</Deeper>

<Deeper level="details" title="When it goes wrong">

- **A variable is empty inside the command.** Past a small essential
  allowlist (`PATH`, `HOME`, `CI` and a few more), vx passes only what
  you list. Add the name to `exec.env.passThrough`.

</Deeper>
