One CI job is too slow for your build? Hand its tasks to more machines. You still start one job and get one result.

```sh
vx run build test lint --all
```

<Levels />

<DteSpread />

Press the buttons to replay real runs. Each bar is a task on the worker that ran it. A task the cache already has never needs a worker.

<Concept term="Worker">
  A CI machine that joins your run, takes tasks, runs them and hands back what they made. vx starts
  workers for you, and stops them when the work runs out.
</Concept>

<Quiz q="Every task changed. Why does the run end later with 3 workers allowed than with 2?">
  `@demo/web#test` waits for `@demo/ui#build`. That path (outlined) takes as long as it takes, on
  any number of machines. The third worker only added a warm-up.

  The run's own `best` line says so: 2 machines end as soon.
</Quiz>

<Takeaway>predict which tasks need a worker, and why more workers is not always faster.</Takeaway>

## What happens in one run

<Walkthrough title="One run of build test lint, step by step">
<Frame title="1. Your CI job plans">

Workers dial out to the [relay](../servers/dte/), since a CI machine takes no incoming call. The relay passes orders and status. Files go through the [remote cache](../remote-cache/).

<Concept term="Relay">
  A small server that passes messages between your run and its workers. It reads nothing it passes:
  every message is encrypted end to end. You host it: [DTE server](../servers/dte/).
</Concept>

<Takeaway>follow a task from your CI job to a worker and back, and read who ran it.</Takeaway>

## Watch it on your machine

`local()` starts each worker as a process in its own git worktree. No CI, no relay:

```ts title=".vx/workspace.ts" ins={2,8-11}
import { defineWorkspace } from '@vzn/vx/config'
import { dte, local } from '@vzn/vx-dte'
import { bun } from '@vzn/vx-lockfile'

export default defineWorkspace({
  plugins: [
    bun(),
    dte({
      workers: { linux: { machines: { cpu2: { max: 3, cpu: 2, memory: '8GB' } } } },
      adapter: local({ prepare: 'bun install' }),
    }),
  ],
})
```

```sh
bun add -d @vzn/vx-dte
vx lock
git add -A
VX_DTE_RUN=$(uuidgen) vx run build test lint --all
```

`VX_DTE_RUN` names the run and turns distribution on. Workers see what git tracks, so `git add` new files first.

<Takeaway>see tasks spread over workers on your laptop ([full guide](try-on-your-machine/)).</Takeaway>

## Set it up on GitHub Actions

You need vx on CI ([CI](../ci/)) and a [remote cache](../remote-cache/) every job can reach.

<Steps>

1. **Deploy the relay.** Follow [DTE server](../servers/dte/). Its URL looks like `https://vx-dte-server.acme.workers.dev`. Leave `ALLOW` for step 4.

2. **Declare `dte()`.**

   ```sh
   bun add -d @vzn/vx-dte
   ```

   ```ts title=".vx/workspace.ts" ins={4,12-18}
   import { defineWorkspace } from '@vzn/vx/config'
   import { vxCache } from '@vzn/vx-cache'
   import { github as ci } from '@vzn/vx-ci'
   import { dte, github } from '@vzn/vx-dte'
   import { bun } from '@vzn/vx-lockfile'

   export default defineWorkspace({
     plugins: [
       bun(),
       ci(),
       vxCache({ url: 'https://vx-cache-server.acme.workers.dev', issuer: 'https://token.actions.githubusercontent.com', repository: 'acme/app' }),
       dte({
         relay: 'https://vx-dte-server.acme.workers.dev',
         workers: {
           linux: { machines: { cpu4: { max: 8, cpu: 4, memory: '16GB' } } },
         },
         adapter: github(),
       }),
     ],
   })
   ```

   One **worker type**, `linux`, of up to 8 `cpu4` machines: 4 cores and 16 GB each, as GitHub's `ubuntu-latest` has for a public repository. vx plans by these numbers, so declare what your runners really have.

3. **Let vx write the workflows.**

   ```sh
   vx lock
   vx dte init
   ```

   ```ansi
   [1m[38;2;6;182;212mvx dte init:[0m[2m wrote .github/workflows/ci.yml[0m
   [1m[38;2;6;182;212mvx dte init:[0m[2m wrote .github/workflows/vx-worker.yml[0m

   [38;2;6;182;212mNext:[0m
   [38;2;6;182;212m  1. Let these workflows use the relay at https://vx-dte-server.acme.workers.dev: set its ALLOW.[0m
   [38;2;6;182;212m     Its ALLOW (a plain var, no secret): https://token.actions.githubusercontent.com:acme/app:ci.yml https://token.actions.githubusercontent.com:acme/app:vx-worker.yml[0m
   [38;2;6;182;212m  2. A remote cache the run and the workers share: workers hand back outputs only through it. https://vznjs.github.io/vx/docs/remote-cache/[0m
   [38;2;6;182;212m  3. Commit .github/workflows/ci.yml, .github/workflows/vx-worker.yml, .vx/workspace.ts and the lock (vx lock), and push.[0m
   [38;2;6;182;212m  How a run spreads over workers: https://vznjs.github.io/vx/docs/distributed-task-execution/[0m
   ```

   `ci.yml` runs `vx run`. `vx-worker.yml` is each worker's job: check out, install, `vx dte worker`. Run `vx dte init` again after you change `workers`.

4. **Let the workflows in.** Put the `ALLOW` line it printed into the relay's settings, and deploy the relay again ([how](../servers/dte/#say-who-may-use-it)).

5. **Push** the two workflows, `.vx/workspace.ts` and the lock. The run's log and job summary show each worker beside its tasks.

</Steps>

In a terminal, `vx dte init` asks which tasks to run. Otherwise name them in the last line of `ci.yml`:

```yaml title=".github/workflows/ci.yml"
      - run: bun vx run build test ${{ github.event_name == 'pull_request' && '--affected' || '--all' }}
```

<Takeaway>spread every push of your repository over CI machines ([step by step](spread-ci-over-machines/)).</Takeaway>

### One task on another machine

Run CI on Alpine, but Playwright on Ubuntu: give Ubuntu its own type, and name it on the task with `exec.worker`.

```ts title=".vx/workspace.ts"
workers: {
  alpine: { machines: { cpu4: { max: 8, cpu: 4, memory: '16GB' } } },
  ubuntu: { machines: { cpu4: { max: 2, cpu: 4, memory: '16GB' } } },
},
```

```ts title="apps/web/vx.config.ts" mark={1}
e2e: { exec: { command: 'playwright test', worker: 'ubuntu' } },
```

The other tasks go to the first type that fits, so a type listed last gets only what no other can take. On your machine `worker` is ignored. It never changes a cache key ([guide](run-a-task-on-its-own-machine/)).

### A bigger machine for heavy tasks

List two machines under one type. vx learns what each task uses, and starts the big one only for a task that filled a small one last time:

```ts title=".vx/workspace.ts" mark={5}
workers: {
  linux: {
    machines: {
      cpu4: { max: 8, cpu: 4, memory: '16GB' },
      cpu16: { max: 2, cpu: 16, memory: '64GB', runsOn: 'ubuntu-latest-16-cores' },
    },
  },
},
```

`runsOn` is the runner label `vx dte init` writes for it ([guide](add-bigger-machines/)).

### macOS workers

A machine with a `platform` takes the tasks whose `exec.platforms` name it:

```ts title=".vx/workspace.ts"
mac: { machines: { m1: { max: 2, cpu: 3, memory: '7GB', platform: 'darwin-arm64' } } },
```

`vx dte init` runs it on `macos-latest`.

### GitLab

`gitlab()` triggers a pipeline of your `.gitlab-ci.yml` for each wave of workers, with the job's own `CI_JOB_TOKEN`. `vx dte init` writes the file.

```ts title=".vx/workspace.ts"
dte({
  relay: 'https://relay.example.com',
  workers: { linux: { machines: { small: { max: 4, cpu: 2, memory: '8GB' } } } },
  adapter: gitlab({ tags: { 'linux.small': ['saas-linux-small-amd64'] } }),
}),
```

<Aside type="caution" title="GitLab refuses triggers by default">
  Set Settings > CI/CD > Variables > "Minimum role to use pipeline variables" to **Developer**, or
  every trigger fails.
</Aside>

### Workers you start yourself

With no `adapter`, vx starts nothing. Start the run, then each worker with the same `VX_DTE_RUN`:

```sh
VX_DTE_RUN=run-42 VX_DTE_SECRET=$KEY vx run build --all
VX_DTE_RUN=run-42 VX_DTE_SECRET=$KEY vx dte worker
```

A worker started before its run says the relay has no live run.

<Takeaway>run tasks where they fit: changed ones only, on another OS, on a bigger box, on GitLab or on your own machines.</Takeaway>

</Deeper>

<Deeper level="details" title="Every option of dte()">

```ts
dte({ workers, adapter, relay, token, unmeasured, headers })
```

| Option | What it does | Default |
| --- | --- | --- |
| `workers` | the worker types, in order of preference. Each is `{ machines }` | none: only workers that join on their own |
| `adapter` | how workers start: `github()`, `gitlab()`, `local()`, `docker()` | none: vx starts no worker |
| `relay` | the relay's base URL, `http(s)`, without `/v1`. `VX_DTE_RELAY` beats it | the adapter's own (`local()`, `docker()`) |
| `token` | the relay's bearer token. Asked again a minute before it expires | `VX_DTE_TOKEN` |
| `unmeasured` | `{ cpu, memory }`: what a task with no history uses, for the plan | the measured tasks' mean |
| `headers` | headers on every call to the relay, for a proxy in front of it | none |

An unknown key is refused. With an `adapter`, at least one machine needs `max` above 0. The same options, with every plugin's, are on [Plugins](../plugins/).

**Each machine** in `workers.<type>.machines.<name>`, named `<type>.<name>` in the output (`linux.cpu4`):

| Field | What it does | Default |
| --- | --- | --- |
| `cpu` | its cores, which vx plans by until the worker reports its own | required |
| `memory` | bytes, or `'16GB'`, `'512MiB'` | required |
| `max` | how many one run may start | no cap |
| `platform` | `linux-x64`, `linux-arm64`, `darwin-x64` or `darwin-arm64`; a worker of another is refused | this machine's, not checked |
| `runsOn` | the CI runner label `vx dte init` writes for it | a GitHub runner of its platform, such as `ubuntu-latest` |

Names use letters, digits, `_` and `-`.

**Adapters:**

| Adapter | Starts each worker as | Options |
| --- | --- | --- |
| `github()` | a job of `vx-worker.yml`, dispatched by the run (up to 256) | `workflow`: the worker file in `.github/workflows` (default `vx-worker.yml`); `env`: variables every worker gets, no secrets |
| `gitlab()` | a job of a pipeline of `.gitlab-ci.yml` (up to 200) | `tags`: runner tags by machine, `{ 'linux.small': ['…'] }` |
| `local()` | a process in its own git worktree | `prepare`: a shell line each worktree runs first, such as `bun install` |
| `docker()` | a container held to the machine's `cpu` and `memory` | `image` (required): one with Bun and git; `prepare` |

`github()` needs `GITHUB_TOKEN` with `actions: write`, and `id-token: write` for its workers.

**Environment variables:**

| Variable | Read by | Means |
| --- | --- | --- |
| `VX_DTE_RUN` | run, worker | the run's id. Set, it turns distribution on. GitHub and GitLab name the run themselves |
| `VX_DTE_RELAY` | run, worker | the relay URL; beats `relay` |
| `VX_DTE_SECRET` | run, worker | the run's shared key. Needed with no adapter and no GitHub |
| `VX_DTE_TOKEN` | run, worker | the relay's bearer token, when `token` is unset |
| `VX_DTE_WORKER` | worker | its name, set by the adapter that started it |

**Task fields** that decide where a task runs (see [Tasks](../tasks/)):

| Field | On workers |
| --- | --- |
| `exec.worker` | runs only on that worker type. An unknown type stops the run before any task starts |
| `exec.platforms` | runs only on a machine of one of these platforms |
| `exec.remote: false` | still runs on a worker: no task runs on your CI job |
| `exec.sandbox` | the same sandbox, built on the worker |
| `exec.timeout` | counts from the task's start on its worker, not from the wait |

</Deeper>

<Deeper level="details" title="Rules for where a task runs">

### What runs where

- Every task runs on a worker, an interactive one too. Only cache hits restore on your CI job.
- A task goes to a worker only when one of its cores is free and its memory fits.
- Of equal choices, a task goes to the busiest worker, so workers fill and the rest leave.
- A task no worker can take, such as one whose `exec.platforms` no machine offers, stops the run before any task starts.
- A task that reads what an uncached task left on another kind of machine stops the run before any task starts. Cache the upstream, or run both alike.
- A server a task depends on (a persistent task) starts on that task's worker, and stops when no task there needs it.
- A worker that is idle, and that the rest of the run cannot keep busy, leaves.
- A worker stopped with Ctrl-C leaves the run; its tasks run again on another worker.
- A task that reads a file git does not track fails, naming the file: no worker has it.

</Deeper>

| `probe` | what the run knew at its start: tasks to run, misses already known |
| `asked` | when vx asked for each worker, and the run's estimate then |
| `ideal` | the best end the allowed workers could give |
| `perfect` | the end if no task waited: the longest path of tasks that wait on each other |
| `drift` | how far the run ended past both |
| `best` / `any` | the fewest machines of your sizes, or of any size, that end as soon |

</Deeper>

<Deeper level="details" title="How it stays private">

- The relay reads nothing. The run and each worker agree on keys made for that session only ([Noise](https://noiseprotocol.org/noise.html)), through the relay.
- On GitHub Actions, each side proves it is a job of your repository with its CI token (OIDC). No secret is stored anywhere.
- Elsewhere, the run and each worker share `VX_DTE_SECRET`. A side without it cannot finish the handshake.
- A message the relay changes drops its worker; one it replays is dropped.
- Files never cross the relay: they go through your remote cache.

</Deeper>
