Already run a Bazel worker pool? Point vx at it, and your builds run there instead of on your laptop.

```sh
vx run deploy --dry   # where would each task run?
```

<Levels />

<Walkthrough title="One workspace, two places to run">
<Frame title="1. Add the pool to .vx/workspace.ts">

```ts title=".vx/workspace.ts" ins={6-11}
import { defineWorkspace } from '@vzn/vx/config'
import { reapi } from '@vzn/vx-reapi'

export default defineWorkspace({
  plugins: [
    reapi({
      endpoint: process.env.REAPI_ENDPOINT, // grpcs://host:443
      execute: true,
      platform: { OSFamily: 'Linux', 'container-image': 'docker://oven/bun:1.4' },
      capacity: 64,
    }),
  ],
})
```

<Concept term="REAPI">
  Bazel's Remote Execution API: one wire for a remote cache and a pool of workers. NativeLink,
  BuildBuddy and Buildbarn speak it.
</Concept>

## Send tasks to your pool

Install the plugin and add it to `.vx/workspace.ts`, as in step 1 above.

```sh
bun add -d @vzn/vx-reapi
```

<Diagram {...remoteExecution} />

- `execute: true` turns on running. Without it, `reapi()` is only a [remote cache](../remote-cache/).
- `platform` picks the worker: its OS and image. The image needs `/bin/sh` and your tools.
- `capacity` is how many tasks run on the pool at once, on top of your own cores.

<Takeaway>run your builds on the pool you already pay for, with one block of config.</Takeaway>

## See where each task runs

`--dry` plans the run and runs nothing. The **worker** column is the answer:

| Worker says | The task runs |
| --- | --- |
| **vx/reapi** | on a worker in your pool |
| **local** | on this machine |
| **—** | nowhere: it has nothing to do here |

<Quiz q="A task has no cache: true. Where does it run?">
  Here. A worker gets only the files a task lists in `inputs`, and only a cached task describes
  them. vx never sends a task a worker could not reproduce.
</Quiz>

<Takeaway>check any task's destination before a single command runs.</Takeaway>

## Keep a task here

Some tasks need this machine: a Docker socket, a VPN, a device. Pin them with `exec.remote: false`:

```ts title="apps/web/vx.config.ts" mark={3}
deploy: {
  dependsOn: ['build'],
  exec: { command: 'wrangler pages deploy dist', remote: false },
},
```

vx keeps these here on its own, and every task that depends on them:

<Compare leftTitle="Goes to the pool" rightTitle="Stays here">
<div slot="left">

- a task with `cache: true`
- whose `inputs` list what it reads

</div>
<div slot="right">

- `exec.remote: false`

- a dev server (`persistent`)

</div>

<Takeaway>keep deploys and local-only tasks home, and send the rest away.</Takeaway>

## Give workers node_modules

A worker starts empty: no `node_modules`. Make the install a task that runs **only** on the pool:

```ts title="vx.config.ts" mark={3}
install: {
  exec: { command: 'bun install --frozen-lockfile', remote: 'only' },
  inputs: { files: ['package.json', 'bun.lock', 'packages/*/package.json'] },
  outputs: { files: ['node_modules/**'] },
  cache: true,
},
```

```ts title="packages/ui/vx.config.ts" mark={2}
build: {
  dependsOn: ['^build', '//#install'],
  exec: { command: 'vite build' },
  inputs: { files: ['src/**', 'index.html'] },
  outputs: { files: ['dist/**'] },
  cache: true,
},
```

- The install runs on a worker, once per lockfile change.
- Its files stay in the pool. Builds get them there; your disk never sees them.
- With no pool, `remote: 'only'` does nothing, and builds use your own `node_modules` (step 3 above: **noop**).

<Takeaway>run every build on a clean worker, with packages built for its OS.</Takeaway>

<Deeper level="patterns" title="Common setups">

### A hosted pool with an API key

A hosted server reads its key from a header. Keep the key in CI's secrets:

```ts title=".vx/workspace.ts"
reapi({
  endpoint: 'grpcs://remote.buildbuddy.io:443',
  headers: { 'x-buildbuddy-api-key': process.env.BB_KEY! },
  execute: true,
  platform: { OSFamily: 'Linux', 'container-image': 'docker://oven/bun:1.4' },
  capacity: 80,
})
```

### A server behind your own CA, or mutual TLS

Give the PEM files. Bazel users know these as `--tls_certificate`, `--tls_client_certificate` and `--tls_client_key`:

```ts
reapi({
  endpoint: 'grpcs://reapi.internal:8980',
  tlsCertificate: 'certs/ca.pem',
  tlsClientCertificate: 'certs/client.pem',
  tlsClientKey: 'certs/client.key',
  execute: true,
})
```

### A value a worker needs

A worker gets no environment from your machine. Give it a value one of two ways:

```ts mark={2,4-5}
build: {
  exec: { command: 'vite build', env: { define: { NODE_ENV: 'production' }, passThrough: ['API_URL'] } },
  inputs: {
    files: ['src/**'],
    env: ['API_URL'],
  },
},
```

`define` sends a fixed value. A name in both `passThrough` and `inputs.env` sends this machine's value.

<Aside type="caution" title="Secrets stay home">
  A value sent to a worker is stored in the pool, readable by anyone who can name it. A task that
  reads a secret takes `exec.remote: false`.
</Aside>

### When the pool is busy

`queueTimeoutMs` gives a task back to this machine if no worker starts it in time:

```ts mark={4}
reapi({
  endpoint: process.env.REAPI_ENDPOINT,
  execute: true,
  queueTimeoutMs: 1000,
})
```

<Deeper level="details" title="Every option">

### `reapi()` options

| Option | What it does | Default |
| --- | --- | --- |
| `endpoint` | The server: `grpcs://host:port`, `grpc://` for plaintext, or `unix:`/`dns:`/`ipv4:`/`ipv6:` targets | unset: the plugin does nothing |
| `execute` | Run tasks on the pool, not only cache there. A boolean only | `false` |
| `platform` | REAPI platform properties that pick a worker (`OSFamily`, `container-image`, …). String values | none |
| `capacity` | Tasks on the pool at once; a positive integer | unset: pool tasks share your local slots |
| `queueTimeoutMs` | Longest wait for a worker to start a task; past it, the task runs here | unset: the task's `exec.timeout` bounds it |
| `executeTimeoutMs` | Longest a started task may run on a worker; `exec.timeout` wins | `600000` (10 minutes) |
| `instanceName` | The REAPI instance name, for a server that hosts several | none |
| `headers` | gRPC metadata on every call, such as an API key | none |
| `tls` | Force TLS on or off | on, except `grpc://`, `http://` and `unix:` |
| `tlsCertificate` | PEM file of a private CA that signed the server | system roots |
| `tlsClientCertificate`, `tlsClientKey` | PEM files for mutual TLS, set as a pair | none |
| `toolName`, `toolVersion` | What the server's UI shows as the client | `vx`, `0.0.0` |
| `correlatedInvocationsId` | Groups several runs as one build in the server's UI | none |
| `metaTimeoutMs` | Deadline for small calls (lookups, existence checks) | `min(callTimeoutMs, 15000)` |
| `callTimeoutMs` | Deadline for one file transfer | `30000` |
| `chunkBytes` | Upload chunk size | `65535` |

A bad endpoint, header name or unreadable PEM file stops the run at startup, naming the option. A TLS endpoint needs a host name, not an IP.

### `exec.remote`

| Value | The task |
| --- | --- |
| `true` (default) | may go to the pool when it can |
| `false` | always runs here, and so do the tasks that depend on it |
| `'only'` | runs only on the pool; here it does nothing. Needs `cache: true` |

`exec.remote` is never in the cache key: the same task hits the same entry wherever it ran.

### What always stays here

- A task with no `cache: true`: it has no described inputs to send.
- A dev server (`exec.persistent`) and everything that depends on it: a worker cannot reach its port.
- A sandboxed task (`exec.sandbox`) and its dependants: workers do not enforce the sandbox.
- A task whose key reads a tool's version (`inputs.runtime`, `inputs.workspaceRuntime`): the answer is this machine's.

### What a worker gets

- The files `inputs` lists, plus the outputs of the tasks it depends on.
- `exec.env.define` values, and `inputs.env` names that are also in `exec.env.passThrough`.
- `FORCE_COLOR` and `NO_COLOR`, so its output matches a local run.
- Nothing else: not `PATH`, not `HOME`, no other variable.

### What happens when

- A server that only caches: one warning, every task runs here.
- No worker starts a task within `queueTimeoutMs`: it runs here. An `'only'` task fails instead.
- A dropped connection: vx re-attaches to the running task instead of starting it again.
- A task already run on the pool with the same key: vx skips the worker and replays the result.
- Uploads chunk at 65535 bytes (`SAFE_CHUNK_BYTES`), the size no Bun http2
  stall has been seen at. A larger `chunkBytes` that stalls retries once at
  that size before the task fails.

Every wire detail: [`@vzn/vx-reapi`](../../plugins/vx-reapi/).
