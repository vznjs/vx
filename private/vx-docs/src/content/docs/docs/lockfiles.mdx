---
title: Lockfiles
description: Key each package on its own dependencies with your package manager's plugin.
---

import { Tabs, TabItem } from '@astrojs/starlight/components'

Add the plugin for your package manager. Without one, no lockfile or
`package.json` is in any key, so an install re-runs nothing.

`^build` also needs it to know which package depends on which. Without
it, vx refuses a `^` and names the plugin to add.

<Tabs syncKey="pm">
  <TabItem label="Bun">
    ```ts title=".vx/workspace.ts"
    import { defineWorkspace } from '@vzn/vx/config'
    import { bun } from '@vzn/vx-lockfile'

    export default defineWorkspace({ plugins: [bun()] })
    ```
  </TabItem>

  </TabItem>

Then each package is keyed on its own dependencies, `^build` follows what
the manager installed, and `--affected` follows both. `pnpm({ scope:
'workspace' })` keys the whole file instead.

Add a dependency to `@demo/web` only, and only its build runs again;
`@demo/ui` is a hit (`local 1✓ 1↑`):

```sh
cd packages/web && bun add nanoid && cd ../..
vx lock
vx run build --all
```

<details>
<summary>What each plugin adds to a key</summary>

| Plugin   | A package's key includes                                                              | Install-wide, for every package |
| -------- | ------------------------------------------------------------------------------------- | ------------------------------- |
| `pnpm()` | every package it reaches, by name, version and resolved peers, with integrity and any patch; under `nodeLinker: hoisted`, every peer variant of each | every top-level field but `importers`, `packages`, `snapshots`, `patchedDependencies`, `catalogs` and `overrides` (`settings`, `onlyBuiltDependencies`, …) |
| `bun()`  | the same, through Bun's hoisted layout; a peer reaches every installed copy of its name | every top-level field but `workspaces`, `packages`, `catalog`, `catalogs`, `overrides` and `patchedDependencies` (`trustedDependencies`, …) |
| `npm()`  | the same, from `npm-shrinkwrap.json` or `package-lock.json` versions 2 and 3                                | the `lockfileVersion`; root `overrides` reach a package through the entries they force |
| `yarn()` | the same, from a berry lockfile, each entry with every field but its dependency lists; a yarn 1 lockfile records no workspaces, so every package's key includes the whole file | `__metadata`'s `version` and `cacheKey`, and the root workspace's entry (its `dependenciesMeta`) through the root's closure |

Every package's key also holds the root package's own dependencies.
Their bins run from the root `node_modules/.bin`, on every task's
`PATH`.

So bumping a root devDependency re-runs every package.
A workspace package the root depends on is the root's dependency only.
Another package that loads it names it in its own `package.json`.

Without that, it neither builds after it nor includes its key, and
`--affected` leaves it out.

Each plugin also puts its manager's install settings in every task's
key, and adds a package's manifest (`package.json`, or under `pnpm()` a
`package.json5` or `package.yaml`) to its tasks' inputs:

| Plugin | Install settings in the key |
| --- | --- |
| `pnpm()` | `pnpm-workspace.yaml` except `patchedDependencies`, `overrides` and the catalogs (the lockfile records their effect per package), `.npmrc`, the root manifest's `pnpm` field |
| `bun()` | `bunfig.toml`, `.npmrc` |
| `npm()` | `.npmrc` |
| `yarn()` | `.yarnrc.yml`, `.yarnrc` and `.npmrc` (yarn 1), the root `package.json`'s `workspaces.nohoist`, `installConfig`, `resolutions` and dependency ranges |

A yarn 1 lockfile records no workspaces, so `yarn()` reads which package
depends on which from the workspaces' `package.json` files.

Under pnpm's `excludeLinksFromLockfile`, the lockfile leaves out every
`link:` dependency. `pnpm()` reads those from `package.json`, and every
package's key holds every package's dependencies.

`vx why` names the part `plugin @vzn/vx-lockfile/pnpm`. An unreadable
lockfile stops the run and names the install to re-run. An import you
never declared is in no package's key.

</details>
