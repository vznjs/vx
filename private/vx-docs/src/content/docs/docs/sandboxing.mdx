A cache is only as right as a task's inputs. Put the task in a box: it sees only the files you grant, and vx names every file it reached for outside them.

```ts mark={3-8}
exec: {
  command: 'vite build',
  sandbox: {
    allow: {
      read: ['.'],
      write: ['dist/'],
    },
  },
},
```

<Concept term="Sandbox violation">
  A file, folder or host a sandboxed task tried to use without a grant. vx lists each one under
  **SANDBOX VIOLATIONS** and fails the task, so a wrong result is never cached.
</Concept>

## Turn it on

Add `sandbox` to a task's `exec`. An empty one, `sandbox: {}`, grants nothing in the workspace: not even the task's own folder.

So most blocks start the same way, and grow from the report:

```ts mark={5-6}
exec: {
  command: 'vite build',
  sandbox: {
    allow: {
      read: ['.'],
      write: ['dist/'],
    },
  },
},
```

| Grant | What it opens |
| --- | --- |
| `read: ['.']` | the whole project, read-only. Before it, only `node_modules` is readable. |
| `write: ['dist/']` | one folder to write. Before it, only the task's own temp folder. |
| `network: ['registry.npmjs.org']` | one host. Before it, none. |

<Aside type="note">
  `outputs` and `inputs` grant nothing. The sandbox reads only `allow`, so a folder the task writes
  goes in both `allow.write` and `outputs.files`.
</Aside>

<Takeaway>sandbox any task: start from `read: ['.']` and its output folder, then add what the report names.</Takeaway>

## Read the report

A failed sandboxed task ends with three parts. Each tells you one thing:

```ansi
[0m[2m├─[0m [1m[38;2;239;68;68mSANDBOX VIOLATIONS (2)[0m [2m────────────────────────────────────[0m

access(/repo/packages/web/vite.config.ts) = -1 ENOENT  [/repo/packages/web/vite.config.ts]
access(/repo/packages/web/package.json) = -1 ENOENT  [/repo/packages/web/package.json]

[2mfix: exec.sandbox.allow: { read: ['package.json', 'vite.config.ts'] }[0m
[2mand, if the output depends on them, inputs.files: ['package.json', 'vite.config.ts'][0m
```

1. **The violations**: what the task did, and the full path in `[ ]`.
2. **`fix:`** the grants that would have let it, ready to paste.
3. **`and, if the output depends on them`**: the same files as inputs, so an edit to them runs the task again.

```ts
read: ['vite.config.ts'],
inputs: { files: ['src/**'] },
```

The build reads the config. An edit to it is a cache **hit**: the old `dist/` comes back.

</div>
<div slot="right">

```ts
read: ['vite.config.ts'],
inputs: { files: ['src/**', 'vite.config.ts'] },
```

<Quiz q="A test runner reads fixtures/ but its result never depends on their content. Which line do you add?">
  Only the grant, `read: ['fixtures/']`. Skip the input line: an input re-runs the task on every
  edit, and this one would never change the result.
</Quiz>

<Takeaway>turn any violation into a grant, and decide whether it also belongs in the key.</Takeaway>

## What a task can see

<Diagram {...sandboxWalls} />

- **Its project**: only what `allow` grants.
- **Other projects**: hidden. A task reads another project only through the outputs of a task it `dependsOn`.
- **The machine** (`/usr`, `~/.cache`, the system `node`): readable, and never in the key.
- **Credential stores** (`~/.ssh`, `~/.aws`, `~/.npmrc`): denied, unless `allow.read` names one.

<Takeaway>predict what a sandboxed task can read before you run it.</Takeaway>

## Let it reach the network

A sandboxed task reaches no host until you list it. A call anywhere else is refused, and named:

```ansi title="vx run @demo/web#ping"
[2m$[0m vx run @demo/web#ping

[2m┌─[0m [1m[38;2;244;114;182m@demo/web[0m[2m#[0m[1m[38;2;244;114;182mping[0m [2m>[0m $ curl -sS -o /dev/null https://example.com
curl: (56) CONNECT tunnel failed, response 403
[2m├─[0m [1m[38;2;239;68;68mSANDBOX VIOLATIONS (1)[0m [2m────────────────────────────────────[0m

deny network-outbound example.com:443 (host is not on the allow list)

[2mfix: exec.sandbox.allow: { network: ['example.com'] }[0m

[2m└─[0m [1m[38;2;244;114;182m@demo/web[0m[2m#[0m[1m[38;2;244;114;182mping[0m [2m──[0m [2m(69ms)[0m [1m[38;2;239;68;68mfailed (exit 56, 1 sandbox violation)[0m
```

Grant hosts by name. A `*.` prefix covers subdomains:

```ts mark={3}
sandbox: {
  allow: {
    network: ['registry.npmjs.org', '*.sentry.io'],
  },
},
```

<Takeaway>see every host a task calls, and allow exactly those.</Takeaway>

<Deeper level="patterns" title="Common setups">

### A dev server and its end-to-end tests

The server binds a port with `localBinding`. Its test reaches it with `localhost:<port>`:

```ts
dev: {
  exec: {
    command: 'vite --port 5173 --strictPort',
    persistent: { readyWhen: 'Local:' },
    sandbox: { allow: { read: ['.'], write: ['node_modules/.vite/'], localBinding: [5173] } },
  },
},
e2e: {
  dependsOn: ['dev'],
  exec: {
    // Playwright empties its output folder first: give it one inside the grant.
    command: 'playwright test --output test-results/run',
    sandbox: { allow: { read: ['.'], write: ['test-results/'], network: ['localhost:5173'] } },
  },
},
```

A bare `localhost` reaches no port: name the one you need.

<Takeaway>run a server and its tests both sandboxed.</Takeaway>

### Silence a noisy tool

Some tools touch a file they do not need, under a new random name each run. `ignore` drops that line from the report:

```ts
sandbox: {
  allow: { read: ['.'], write: ['dist/'] },
  ignore: { write: ['*.bun-build'] },
},
```

`ignore` grants nothing: the file stays refused. Use it only when the task's result does not need the file.

<Takeaway>keep the report to the violations that matter.</Takeaway>

### Publish with a token

A publish needs the token in `~/.npmrc`, a credential store. Name it to open it:

```ts
publish: {
  exec: {
    command: 'npm publish',
    sandbox: { allow: { read: ['.', '~/.npmrc'], network: ['registry.npmjs.org'] } },
  },
},
```

<Takeaway>open one credential store for the one task that needs it.</Takeaway>

### Block one host

`deny.network` wins over `allow.network`. Allow every subdomain, then take one back:

```ts
sandbox: {
  allow: { read: ['.'], network: ['*.example.com'] },
  deny: { network: ['telemetry.example.com'] },
},
```

<Takeaway>allow a family of hosts and keep one out.</Takeaway>

### Close off the machine

By default `/usr` and `~/.cache` are readable and outside the key. `hermetic: true` closes them too. Grant the tool you run, and key it with `inputs.runtime`:

```ts
exec: {
  command: 'vite build',
  sandbox: {
    hermetic: true,
    allow: {
      read: ['.', '/opt/node-22/'], // the node vite runs on
      write: ['dist/', 'node_modules/.vite-temp/'],
    },
  },
},
```

Grant a tool's libraries with it: `ldd $(command -v node)` lists them. vx still grants the shell the command runs in.

<Takeaway>build with only the tools you named, nothing from the host.</Takeaway>

### Read another project

A task never reads another project's sources. It reads the outputs of the tasks it depends on, and its key already moves with them. `^build` is the `build` of each project this one depends on:

```ts title="packages/web/vx.config.ts"
build: {
  dependsOn: ['^build'],
  exec: {
    command: 'vite build',
    sandbox: { allow: { read: ['.'], write: ['dist/', 'node_modules/.vite-temp/'] } },
  },
},
```

<Takeaway>share files between projects through task outputs.</Takeaway>

### Run inside a container

As root in a container, the sandbox cannot start (`write /proc/self/uid_map: Operation not permitted`). Run as a normal user, or accept a weaker sandbox:

```ts
sandbox: { weakerWhenNested: true, allow: { read: ['.'], write: ['dist/'] } },
```

<Takeaway>sandbox tasks on a CI runner that is itself a container.</Takeaway>

<Deeper level="details" title="Every option">

### Every field

```ts
sandbox: {
  allow: { /* what the task may do, below */ },
  deny: { network: [] },
  ignore: { read: [], write: [], systemInfo: [], network: [] },
  hermetic: false,
  weakerWhenNested: false,
  weakerNetworkIsolation: false,
}
```

| Field | What it does |
| --- | --- |
| `allow` | What the task may read, write and reach. Every key below. Default: nothing. |
| `deny` | Hosts refused even when `allow.network` matches them. Takes `network` only. Default: none. |
| `ignore` | Violations left out of the report, by `read`, `write`, `systemInfo`, `network`. Grants nothing. Default: none. |
| `hermetic` | Refuse reads outside the workspace too, except `allow.read` and the shell. Default: `false`. |
| `weakerWhenNested` | Linux: a weaker sandbox when vx itself runs in a container or sandbox. Without it, nesting fails the task. Default: `false`. |
| `weakerNetworkIsolation` | macOS: the network goes through a host proxy, for lower overhead and weaker isolation. Default: `false`. |

An unknown key is refused when the config loads: a typo never confines a task more than you meant.

### What you can grant

Every key of `allow`. Each grant is the task's own, never shared with the run's other tasks.

Every key starts closed: no paths, no hosts, `false`.

| Key | Grants, and an example |
| --- | --- |
| `read` | paths or globs: project-relative, absolute or `~/`. `read: ['.', '~/.cache/ms-playwright']` |
| `write` | paths or globs; a folder ends in `/` or is a glob. A write grant is readable too. `write: ['dist/', 'coverage/']` |
| `network` | `true`, or a list of hosts; `localhost:4173` reaches a server on this machine. `network: ['*.sentry.io']` |
| `localBinding` | `true` to bind localhost ports (Linux needs no grant); a port list also makes them reachable from outside. `localBinding: [5173]` |
| `unixSockets` | `true`, or socket paths (Linux: any path). `unixSockets: ['/var/run/docker.sock']` |
| `systemInfo` | system info names a tool asks for. `systemInfo: ['vfs.disk-space']` |
| `machLookup` | macOS services a tool looks up. `machLookup: ['com.apple.FSEvents']` |
| `pty` | a terminal, for a tool that needs one. `pty: true` |
| `gitConfig` | write the repository's `.git/config`, for this task only. `gitConfig: true` |

`deny` takes `network`, the same host patterns, plus a bare `*` (every host). `ignore` takes patterns per kind of violation; relative ones start at the project folder.

### Paths

- **Relative** paths start at the project folder. `~/` is your home. `~user/` is refused.
- **Globs** work in `read` and `write`. `[id]` is a character class: grant `pages/\\[id\\].tsx` escaped.
- **A literal write path is a file.** vx creates it empty before the task starts. Spell a folder `coverage/`, or the task's `mkdir` fails.
- **A write glob outside the project** covers only files there when the task starts on Linux. Grant its folder instead.

<Aside type="caution" title="On Linux a file write grant opens its folder">
  `write: ['out.txt']` opens the whole folder that holds it. vx flags any other file the task
  touches there. Keep outputs in a folder of their own.
</Aside>

### Hosts

- A host is `example.com`, `*.example.com`, either with a port (`example.com:443`), or `localhost:<port>`.
- A scheme, a path, a host with no dot, `*` or `*.com` in `allow.network` is refused by `vx lock`.
- `network: true` reaches every host another task of the run lists, and none in a run that lists none.
- A refused request fails the task even when the tool survived it.

### The project wall

A task never reaches another project, or a workspace root file you did not grant. The two sides of the wall answer differently:

| `@demo/web#build` touches | What happens |
| --- | --- |
| `../ui/src/index.ts`, another project | hidden: no file, and no violation |
| `README.md`, its own file, not granted | a violation: the task fails |

A refused write outside the project names the folder to grant, or the file itself when that folder holds the project (a root `bun.lock`).

Under the host's temp directory, it names `$TMPDIR` instead: the task's own temp folder, empty at its start.

### What vx denies by default

Inside the workspace, everything the task was not granted. Outside it, the stores where tools keep credentials, such as:

- `~/.ssh`, `~/.gnupg`, `~/.git-credentials`
- `~/.aws`, `~/.kube`, `~/.docker/config.json`
- `~/.npmrc`, `~/.bunfig.toml`, the browsers' profiles

The [full list](../../schema/sandbox/) lives in the config reference. A grant naming one opens it for that task. What the sandbox stops, and what it does not: [Security model](../../security/).

### Requirements & platform support

| Platform | Needs |
| --- | --- |
| Linux | `bubblewrap` (`bwrap`), `socat` and `ripgrep` (`rg`). vx names an undeclared read itself (Linux 5.5), or with `strace`. |
| macOS | The system sandbox, built in. Its report can miss a line under load; the refusal never does. |

`vx info` says whether this machine can sandbox.

- A task with no command (a group task) cannot be sandboxed.
- On macOS, a task that runs its own sandbox cannot be sandboxed: one cannot nest in another.
- A task with `interactive` cannot take a `sandbox`.
- A persistent task (a dev server) runs inside the same walls, but nothing traces it: a refused read is `ENOENT`, named nowhere. Run its command once as a normal sandboxed task to see what it was refused.
- On Linux, a tool that only checks a path exists (`existsSync`, `test -e`) is not traced: it sees the file as missing, and no violation names it.

### Common problems

- **`write /proc/self/uid_map: Operation not permitted`.** You are root in a container. Run as a normal user, or set `weakerWhenNested: true`.
- **`File exists` or `Not a directory` from the task's own `mkdir`.** A write grant with no trailing slash is a file. Write `'coverage/'`.
- **A file the task creates later is refused on Linux** ("Read-only file system") under a glob outside the project (`~/.cache/tool/*.log`). Grant its folder: `'~/.cache/tool/'`.
- **`bun build --compile --target=…` fails on a fresh machine** ("Network error downloading executable"). Grant `network: ['registry.npmjs.org']` and `write: ['~/.bun/install/cache/', '.*.tmp/**']`.
- **`next build` with `output: 'standalone'` writes `node_modules/.bun/…` under the app.** Next looks for the lockfile, which the sandbox hides. Grant it: `read: ['.', '../../bun.lock']`, keyed with `inputs.workspaceFiles: ['bun.lock']`.
- **`read packages/ui (linked at …/node_modules/@x/ui), and its key includes no task of packages/ui`.** The task imports a sibling its key never sees. Depend on a task of it (`dependsOn: ['^build']`), or grant and key the files: the `fix:` line names both.
- **`exit 127` under `hermetic: true`.** The tool's runtime or its libraries are outside the grants. Grant the runtime's folder and what `ldd` lists.
