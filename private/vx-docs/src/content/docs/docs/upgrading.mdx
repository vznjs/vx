<Concept term="Breaking change">
  A change in a release that can stop your setup working until you edit something. Until 1.0, any
  release can hold one. Each is listed below with the fix.
</Concept>

## Upgrade in three steps

<Steps>

1. Run `vx upgrade` in the workspace. It installs the release with your package manager, moves every `@vzn` plugin to the same version, then runs `vx lock`.

2. Pick your old version in [the release list](#what-changed-in-each-release) and make each change it shows. Check yours with `vx --version`.

3. Commit `package.json`, your lockfile and `.vx/`. Everyone and CI then install the same vx.

</Steps>

<Quiz q="A teammate on 0.0.658 pulls your commit but does not install. What happens on their next vx run?">
  If the release changed the lock's format, their vx refuses it: `.vx/projects.lock was written by a
  newer vx … upgrade vx`. One `bun install` gives them the pinned vx, and the run works.
</Quiz>

<Takeaway>move a workspace to a new vx and keep the whole team on it.</Takeaway>

A new vx means new keys, so nothing old is reused. Each task runs once and is stored again. A release never replays what an older vx stored.

<Aside type="tip" title="Free the space later">
  Entries from the old vx stay on disk. `vx cache clean --older-than 7d` drops the ones no run has
  used for a week.
</Aside>

<Takeaway>expect one full run after an upgrade, and know why it is safe.</Takeaway>

<Deeper level="patterns" title="Common setups">

### Pick a release

`vx upgrade` takes a version. A lower one goes back:

```sh
vx upgrade 0.0.659    # or v0.0.659
```

### A global vx beside the project's

Inside a project, a global `vx upgrade` moves both to one version: the project's first, then the global. `vx upgrade -g` moves only the global one and never touches `package.json`.

### A registry mirror

vx installs from the registry your package manager already uses: `@vzn:registry` or `registry` in `.npmrc`, `npm_config_registry`, or `bunfig.toml`. Nothing extra to set.

### CI

CI installs what the lockfile pins, so a commit from step 3 is the whole CI upgrade. Its first run builds every task once, like yours did.

<Takeaway>pin a release, move a global vx, and upgrade behind a company mirror.</Takeaway>

</Deeper>

<Deeper level="details" title="What vx upgrade does, exactly">

| Your vx was installed…  | `vx upgrade` runs                                        |
| ----------------------- | -------------------------------------------------------- |
| in a project            | its package manager's add, same field: `bun add @vzn/vx@<v> --dev` |
| with `bun add -g`       | `bun add -g @vzn/vx@<v>`                                 |
| with `pnpm add -g`      | `pnpm add -g @vzn/vx@<v>`                                |
| with `npm install -g`   | `npm install -g --prefix <prefix> @vzn/vx@<v>`           |
| with `yarn global add`  | `yarn global add @vzn/vx@<v>`                            |
| as a binary, by hand    | downloads the release and replaces itself                |

- **Plugins move too.** Every `@vzn/vx-*` plugin in the same `package.json` installs at the same version.
- **The download is checked.** A hand-installed binary checks npm's signature and the file's hash first. Any mismatch refuses, and nothing is replaced.
- **A broken binary is undone.** The new vx must answer `--version` within 10 s, or the old one comes back and the command exits 1.
- **The lock follows.** After an install inside a workspace, the new vx runs `vx lock`. If that fails, it prints `vx lock failed: run vx lock`.
- **Already there.** On the version you run, it prints `already at <version>` and downloads nothing.

| Exit code | When |
| --- | --- |
| `0` | installed, or already at that version |
| `1` | anything refused or undone: no network, a directory it cannot write, a bad signature, a binary that does not start, a failed install |

Every message and edge rule: [the `vx upgrade` reference](../../cli/upgrade/).

</Deeper>

### After v0.0.659

#### Plan as JSON with vx run --dry --format json

`vx run --dry=json` → `vx run --dry --format json`; `--dry=pretty` → `--dry`; pipeline `dry: 'json'` → `dry: true, format: 'json'`.

#### Give each vx lock --check problem its error code

Vx lock --check --format json problems are \{ code, message \} objects, not strings.

#### A run refuses a config edited since vx lock

After editing a `vx.config.ts`, run `vx lock` before `vx run`, `vx show`, `vx why` or `vx pipeline`: the run now refuses with `VX_E_LOCK`, naming the file, instead of running the config the lock holds.

#### Sandboxed tasks no longer read credential stores

A sandboxed task no longer reads browser profiles, `~/.config/sops/age`, `~/.config/rclone`, `~/.my.cnf`, `~/.password-store` or `~/.sentryclirc`.

A task that needs one names it in `exec.sandbox.allow.read`.

Variables whose names hold `PASSPHRASE` or end in `_PASS` are now masked in output.

#### Run history starts empty once

The local index schema is v58: it resets once, so the run history starts empty.

Nothing to do. `vx last` and `vx why` show only runs made after the upgrade. A piped run prints the Tasks header once.

#### Write locks git merges cleanly

.vx/projects.lock is version 9 and .vx/dependencies.lock version 6. Run `vx lock` once to rewrite both.

#### A --force run replaces the entry its key held

A `--force` run now replaces the local entry under its key. A custom cache layer drops `kept()` and `stampWritten()`: vx no longer calls them.

#### A --filter that matches nothing refuses the run

A `--filter` that matches no project, an exclusion too, now refuses the run even when another filter matched. Fix or remove it in your CI scripts and pipelines.

#### Fail a task whose declared output path matched nothing

A declared output that matches no files fails the task instead of warning.

An output named by path (`dist/index.js`, `dist`) must exist. A wildcard (`dist/**`) may match nothing, as long as one output matched.

Run your tasks once after upgrading. A task that fails with `outputs matched no files (<glob>)` needs that glob fixed to match what the command writes, or removed from `outputs.files`.

#### Replace --continue with --fail-fast

`--continue` is gone: use `--fail-fast`. Rename each one you use:

- `--continue` → `--fail-fast`
- `run.continue` → `run.failFast`
- `VX_RUN_CONTINUE` → `VX_RUN_FAIL_FAST`
- pipeline key `continue` → `failFast`
- `RunOptions.continueMode` → `failFast`

Replace each use:

- `--continue=never` or `run.continue: 'never'`: use `--fail-fast` or `run.failFast: true`. Tasks still running are now killed.
- `--continue`, `--continue=always`: remove it. A failed task's dependents never run now.
- `--continue=deps-ok`: remove it. That is the default.

#### Drop the lock merge driver, name it .vx/projects.lock

.vx/projects.lock.jsonl is now .vx/projects.lock (run vx lock); vx lock --merge is removed.

Delete the old lock, the old attributes file and the merge driver, then lock again:

```sh
git rm .vx/projects.lock.jsonl .vx/.gitattributes
git config --remove-section merge.vx-lock
vx lock
git add .vx
```

`vx lock` writes `.vx/.gitattributes` only when none exists, so the old one goes first. After a merge conflict in a lock, run `vx lock` and commit.

#### Forwarded args reach one task, CI prints failed tasks only

Args after `--` go to one task in one project. A run with `--affected`, several tasks, or a filter that picks the task in two projects is refused.

Run each task on its own: `vx run test --filter ui -- --watch`.

On CI a run prints only failed tasks. To see every task, pass `--output-logs full` or set `VX_RUN_OUTPUT_LOGS=full`.

#### Refuse two tasks whose outputs can share a path

`vx lock` now refuses two tasks whose output globs can match one path, such as `*.js` beside `*b*`. Narrow one glob so the two tasks write no common path.

A cache scope reads the default key first and writes only its own key, locally and remotely.
